## Purpose / Big Picture

After this change, users can search Iwara videos directly in Theoria Codex, open Iwara video deep links into the app, browse Iwara creator uploads from post action sheets, and launch Iwara posts in Viewer with lazy post resolution for playable media URLs. The rollout is intentionally videos-first, so Iwara images stay out of scope for now.

## Surprises & Discoveries

- Observation: `api.iwara.tv/search` rejects `sort=recent` with HTTP 400 even though the web URL examples use `recent`; `sort=date` is the working API token.
  Evidence: browser-verified API requests on 2026-04-05.
- Observation: Iwara video search results do not include the expiring playable URL; `fileUrl` appears only on `GET /video/{id}`.
  Evidence: `GET https://api.iwara.tv/video/KH2f7fca2MCgZ8` returned `fileUrl`, while search/list payloads exposed only `file` metadata.
- Observation: Creator profile browsing can avoid username resolution after the first post parse because creator video paging only needs the user UUID.
  Evidence: profile pages call `GET /profile/{username}` first, then `GET /videos?user=<uuid>&sort=date&page=<n>&rating=all`.
- Observation: The stable autogenerated video thumbnail shape was `https://i.iwara.tv/image/thumbnail/<fileId>/<fileId>.jpg`; path-based date folders were not required for the tested public payloads.
  Evidence: direct HTTP checks against sample Iwara file IDs on 2026-04-05.
- Observation: `RTK.md` was referenced by repo instructions but was not present in the working tree during implementation.
  Evidence: repository root lookup on 2026-04-05; implementation followed `AGENTS.md` and `PLANS.md`.

## Decision Log

- Decision: Ship Iwara as a videos-only source in this rollout.
  Rationale: The current query model has no source-specific type selector, and the product direction explicitly chose videos first.
  Date/Author: 2026-04-05 / Codex
- Decision: Generalize the existing Rule34 lazy viewer refresh flow instead of adding a second Iwara-only resolution path.
  Rationale: Iwara has the same shape of problem: search cards are cheap to fetch, while full playback/download URLs require `resolvePost`.
  Date/Author: 2026-04-05 / Codex
- Decision: Use best-effort trending tags derived from the recent public video feed.
  Rationale: Iwara exposes tag search but no dedicated trending-tag endpoint that matches the app contract.
  Date/Author: 2026-04-05 / Codex

## Outcomes & Retrospective

Iwara is now integrated as a real videos-first source. Search mode can query Iwara videos with `Newest`, `Popular`, and `Top`, creator action sheets can open Iwara upload pages, deep links for `iwara.tv/video/<id>` route into the app, and unresolved Iwara posts lazily resolve before Viewer playback or device download. The rollout also extended source-aware tag normalization and recommendation training so Iwara tags behave like the other underscore-oriented booru-style sources.

## Context and Orientation

The app is an Android Compose application in `app/`, with shared source contracts in `core-domain/`, persistence in `core-data/`, stub adapters in `core-stubs/`, and real source integrations in `core-sources/`. Search, Viewer, and creator-profile surfaces are already implemented for other sources, and Iwara must plug into those existing seams instead of adding a new browsing model.

The most relevant files for this work are:

## Plan of Work

First, add `SourceKey.IWARA` and update every exhaustive source-specific branch in domain, data, stubs, real-source runtime, and app metadata. Then implement `IwaraSourceAdapter` with public JSON endpoints for search, tag autocomplete, resolve-by-id, creator video paging, and best-effort trending tags, followed by source-layer tests.

Next, wire the adapter into the real registry and create Iwara stub fixtures so the stub runtime stays valid after the enum expansion. After the source layer is stable, integrate Iwara into creator browsing and generalize lazy viewer/download resolution so unresolved Iwara video posts can resolve into playable/downloadable media on demand.

Finally, add Iwara post deep links, update repo docs, and run the targeted Gradle validation commands.

## Validation and Acceptance

Acceptance is satisfied when:

- Iwara appears as a source in Search runtime exposure.
- Source-mode Iwara search returns videos for text queries and respects `Newest`, `Popular`, and `Top`.
- Opening an Iwara video in Viewer resolves to a playable media URL.
- Long-pressing an Iwara post exposes a creator button and opens creator uploads.
- Saving/downloading an unresolved Iwara post resolves first and queues the download.
- `iwara.tv/video/<id>/...` links open in-app and resolve successfully.

## Idempotence and Recovery

All changes are additive. If Iwara API behavior shifts during implementation, the adapter should fail with typed source errors instead of crashing. Stub fixtures and tests should remain runnable offline regardless of live API drift.

## Artifacts and Notes

Known live API shapes verified during planning:

- Search: `GET https://api.iwara.tv/search?type=videos&page=0&query=wuthering%20waves&sort=views`
- Resolve: `GET https://api.iwara.tv/video/KH2f7fca2MCgZ8`
- Creator profile: `GET https://api.iwara.tv/profile/mmdparadaise`
- Creator videos: `GET https://api.iwara.tv/videos?rating=all&sort=date&page=0&user=<uuid>`
- Tags: `GET https://api.iwara.tv/tags?query=wu&page=0`

## Interfaces and Dependencies

Add `SourceKey.IWARA` and implement:

    class IwaraSourceAdapter(
        private val httpClient: SourceHttpClient,
        private val gson: Gson = Gson(),
    ) : SourceAdapter, CreatorPostsSourceAdapter

The adapter must:

- search videos via `/search?type=videos`
- resolve posts via `/video/{id}`
- page creator uploads via `/videos?user=<uuid>`
- autocomplete tags via `/tags?query=...`
- derive trending tags from recent public videos
