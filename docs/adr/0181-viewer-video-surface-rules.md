# 0181. Viewer video pages pick their stream once, preload only cache-backed streams, and render subtitles outside the video frame

Status: Accepted

## Context
Viewer video pages sit on a pooled ExoPlayer, an Android PlayerView and Picture-in-Picture, each with constraints that only show on device: system calls on every recomposition, preloading streams nothing would keep, subtitle clipping in zoomed video, and a letterboxed PiP transition.

## Decision
- `ViewerVideoPlayer` builds `viewerPlayback` inside a `remember` keyed on media, source, quality, quality height and stream label, because the metered-network check (`isMediaNetworkMetered`) is a system call and must run when the page picks its stream, not on every recomposition.
- Two quality values apply: the quality preference (`rememberViewerVideoQuality`) starts from the saved default and a quality picked in the playback menu becomes the new default; the picked rendition height (`qualityHeight`) belongs to the current media only and resets when the selected media changes.
- A page that is not active renders only its loading preview unless it is preloading and `playback.readsAheadFreely()`. A stream the shared cache does not keep (an episode, any HLS or DASH rendition) does not load ahead of a swipe, because nothing would keep what it read for the page to play and an episode's links expire.
- A video page's loading preview, the post's poster and usually the provider's first-frame thumbnail, stands in only for a page that starts at 0, and only until its player renders a frame, active or not. A page that resumes partway (`ViewerVideoPositions.position` above 0, even an episode that will start over, which then shows black until its first frame) or whose video is already under way (`ViewerVideoStart.underWay`, a stream switch or retry) shows black until its frame renders, because a poster there reads as a frame-0 flash followed by a jump. `ViewerVideoPositions` holds snapshot state so a page redraws once its position is saved. A swipe destination stays preloaded (`ViewerSwipeController.loadTarget`) until the settle finishes, even when the swipe is cancelled, so the recoiling neighbour keeps its frame. Only the current media gets the picked rendition height, so a destination preloads the rendition it will play. Its timeline starts at the start position: `ViewerVideoState` is seeded with it, `ViewerPendingTimeline` takes the position, and the binding and player listener refresh position together with duration (`ViewerVideoState.updateProgress`).
- A resumed page shows the frame it was left on instead of black, so a swipe back shows it from its first pixel, including while a non-preloading page is inactive. The frame is requested when a swipe commits away from the current video (`ViewerSwipeController.settleTo` calls the context's `onLeave`, which runs `ViewerVideoPositions.captureLeaving` and with it the active page's `captureResumeFrame`), only while the player is ready at a position past 0, so a seek still under way never pairs old pixels with its new position. It cannot wait for the release: the page is removed once it scrolls out of view, before the commit, and its TextureView has already dropped its texture by then. The copy is an asynchronous `PixelCopy` of the last buffer queued to the TextureView's `SurfaceTexture`, at most 1080 px on its long edge, tagged with the player's position and duration at the request. `TextureView.getBitmap` gave the same pixels but held the UI thread 14–74 ms on the API 36 emulator whatever the size, waiting for the RenderThread to finish the frame in flight, on the first frame of the settle; `PixelCopy` returns in about 0.2 ms and delivers 4–10 ms later, well before the release. A copy that arrives after its page released, or after a newer request for the same video, is dropped. The video keeps playing through the settle (about 0.4 s), so the first save after a capture snaps forward by up to 1 s (`VIEWER_RESUME_FRAME_DRIFT_MS`) back to the captured position, and the exact seek renders the frame the cover shows, within a frame of the copied buffer; a release further on or behind it (a short clip that ended and restarts from 0) drops the frame. Later saves keep the frame only while they equal the capture, so a peek that binds the page at its frame and cancels keeps it for the next peek. The frame covers the page while its saved position equals the capture and the player has not rendered its first frame. An episode left within its end margin, or reaching it before the release, keeps no frame and keeps its release position, since it starts over (ADR 0177). The poster still stands in only for a start at 0, and a page already under way stays black. `ViewerVideoPositions` keeps the four most recently left frames within its retained posts, about 10 MB at most.
- Playback commands apply at once, using `owner.lifecycle.currentState.isAtLeast(STARTED)`, because adding the lifecycle observer replays ON_START/ON_RESUME only while the host is started.
- Picture-in-Picture binds with `state.view.takeUnless { fillScreen }`: in Fill mode the PlayerView's bounds can differ from the video's frame (which sets the PiP aspect ratio), so no `sourceRectHint` is passed, to stop Android letterboxing the transition.
- `bindViewerSubtitleOverlay`/`attachViewerSubtitleView` hide the PlayerView's built-in subtitle view and attach a Viewer-owned `SubtitleView` outside `exo_content_frame`, so `RESIZE_MODE_ZOOM` never clips cues off-screen. Cues go through `sanitizeViewerSubtitleCue`, which strips embedded colours and background boxes but keeps placement, emphasis and bitmap cues.

## Consequences
Metered checks and cache decisions are cheap and stable per page; episodes and adaptive streams start loading only when selected. Any new preloading must go through `readsAheadFreely` rather than a list of sources.
