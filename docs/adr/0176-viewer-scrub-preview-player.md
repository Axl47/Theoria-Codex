# 0176. Scrub previews come from a paused, video-only player that seeks to keyframes and stops between drags

Status: Accepted

## Context

Dragging a video timeline shows a frame near the finger: in a short clip the nearest keyframe within a small window, else a frame just before the finger; in a longer video the nearest keyframe. Media3's `FrameExtractor` had to be rebuilt per drag, its one process-wide player refuses a request while a cancelled one still decodes, and it always prepares and decodes 0:00 before its first seek, about 340 ms before a drag's first request. A paused request also keeps filling socket buffers (about 2 MB) on the link the next seek needs.

## Decision

- `ScrubPreviewPlayer` replaces `FrameExtractor`: it seeks as soon as the stream's index is read and keeps its decoder and GL pipeline across drags. Its renderer, software decoder, HDR and rotation handling and pixel read follow `FrameExtractor`'s (HDR input is read as SDR and rotation is applied as an effect, because frames never reach a display surface).
- Once the stream's index is read, the preview seeks with `scrubPreviewSeekParameters`. In a clip up to 30 s long (`NEAR_FINGER_PREVIEW_MAX_US`, compared with the unrounded duration) that is the nearest keyframe within 1% of the duration either side (`SCRUB_SNAP_FRACTION`, shared with Instant Seek's scrubbing in ADR 0119), else the window's start, at most 1% of the timeline before the finger; a short clip with one keyframe would otherwise preview, and then play from, its first frame wherever the finger is. Longer videos seek to the closest keyframe: a window that misses every keyframe decodes from the keyframe before it on the software decoder, and on the test emulator a 60 s 1080p clip with keyframes 10 s apart (x264's default spacing) took up to 1.4 s per preview (AVC and HEVC alike) instead of a keyframe's tens of milliseconds, so a moving finger would rarely see a frame. Within 30 s the cost stays bounded by the clip's own length and its encoder's keyframe spacing.
- A target waits in `ScrubFrameMatcher` until the stream's index is read, since only then do seeks resolve to keyframes. A late timeline from a stopped stream is ignored. Frames are matched to seeks, not to positions, because a seek renders whichever frame follows the position it resolved to (or the last frame near the end), at any frame spacing, and a seek to the player's current position renders nothing and reports nothing. `PreviewRenders` counts the renderer's position resets as generations and tags each rendered frame with its generation by timestamp; a frame whose timestamp is no longer the latest render is dropped as stale. After each seek a `PlayerMessage` on the playback looper (handled right after the seek) reports the generation the seek left, with the seek's token from `ScrubFrameMatcher`. The request is answered by the frame of that generation or a later one: at once when the shown frame already has it (including a seek that moved nothing), else when it arrives. A later generation can only come from Media3 resetting the renderer again at the position the seek left (a pending discontinuity, such as a trimmed clip's preroll, read on its next work pass), because a seek of ours changes the token. Generations are written and read on the playback thread; the GL thread reads only the latest render. A settle or frame from an earlier request's seek never answers a newer one. `ScrubPreviewPlayer` (as a `ScrubFrameSource`), the matcher and `ViewerScrubPreviews` are all used on the main thread.
- Between drags `idle()` stops the player (no request stays open) while foreground mode keeps the decoder. The next `frameAt` sets the media item again and prepares it, which re-reads the index and signals when seeks resolve to keyframes again.
- `previewLoadControl` buffers 1 s: a keyframe needs little more than itself, and a second covers decoders that hold frames for reordering.
- The GL read returns rows bottom-up, so a `MatrixTransformation` flips the frame vertically.
- `PreviewFrameRenderer` uses Media3's library-internal `PlaybackVideoGraphWrapper` (`@SuppressLint("RestrictedApi")`), the same setup `FrameExtractor` uses to render decoded frames into an effect chain. The pinned Media3 version keeps it stable, and a changed signature fails compilation on upgrade.
- `rememberViewerScrubPreviews` extracts at the size the popup actually shows (`viewerScrubFrameSize` in pixels, rounded down to even width and height with `Int.even()`, since video encoders and effects expect even dimensions).
- `ViewerScrubPreviews` keeps one frame source (a `ScrubPreviewPlayer`) per stream location, built on the first drag and kept idle between drags until `close`, or until a drag fails or times out (`SCRUB_FRAME_TIMEOUT_MS`); the next drag then starts afresh. Frame requests drop subtitles and separate audio tracks.
- `followScrubTargets` handles targets one at a time, so one frame is pending at a time, and only the newest target may publish. Separately, a direct `ScrubFrameSource.frameAt` cancels any request still pending on that source. The first target (where the finger landed) is extracted at once; later ones only after the finger rests on them for `SCRUB_FRAME_SETTLE_MS` (80 ms).
- `seekReleased` idles the preview before seeking, because until its request closes what it read is uncommitted and its cache lock makes the player download those bytes again. The two players work on separate threads, so this makes the hand-over likely, not certain. When the last published frame is the release target's, playback seeks to that frame's time with `SHOWN_FRAME_SEEK`, a keyframe up to 1 ms after it, else exactly (a keyframe's time is truncated to milliseconds, so an exact seek there would decode from the keyframe before it); otherwise the seek is exact. Seek parameters are restored afterwards.
- `ViewerVideoState.release`: after an instant-seek drag (`scrubTo`) the release seek is exact and reads on from the keyframe the drag showed; otherwise the previews may land it on the frame their popup shows.
- Previews are created only for single-file videos (`previewsScrubFrames`: progressive streams for which `readsAheadFreely()` holds) and only while the timeline is shown. Matching tags frames by their period-relative timestamp, which a manifest's later periods or non-zero start would break, and nothing saves a manifest on the device. They read through the shared cache so a release plays from bytes they fetched; a stream the cache does not keep would fetch every frame twice.

## Consequences

The first request of a drag no longer pays the 0:00 prepare. Upgrading Media3 may break the renderer at compile time; that is intended.
