# 0218. A saved search is edited in Search and updated in place, starting its new posts over

Status: Accepted

## Context

A saved search could only be renamed. Search already restores a saved query and has every control for tags, groups, sources, filters and sort, so a second editor would duplicate it. A saved search's identity (id, name, place in the list, save date) is what the Searches collection, its exclusions and its new-post marks hang on, while its marks describe the results of one particular query.

## Decision

- The rename dialog's Edit search (`SavedSearchNameDialog` `onEdit`, reached through `SavedSearchActions`) keeps a name typed in the dialog first, then hands the saved search to `TheoriaShell.editSavedSearch`, which closes the management sheet, sends `SearchAction.EditSavedSearch` and switches to Search.
- `SearchViewModel` owns the edit (`SearchUiState.editingSavedSearchId`). `EditSavedSearch` restores the saved query as the draft the way a historical search does; only when Search accepts it with its whole scope (every source available; a Multi-Search missing one is refused rather than edited down to the rest) does it mark the edit, in the same state write as the draft, ask the route to open the composer (`SearchEffect.OpenComposer`) and run the draft. Because draft and edit start together, any earlier result on screen counts as a pending change until the edit's own run lands. The edit lives in the view model, so it survives rotation, but not in saved state: after process death Search may restore a different query (it never persists a Multi-Search), so no edit is offered against it. Opening another search (`ApplyHistoricalQuery`, `ApplyTagSearch`) or stepping history ends the edit.
- Every path that closes the composer ends the edit first, synchronously (`SearchChromeState.closeComposer`, `applyDraft`, and the typed gallery ID that opens the Viewer in `SearchRoute`), so leaving Search right after closing cannot strand it. Nothing is saved on the way out, so backing out leaves the saved search as it was. Filter and sort open from the composer's menu, over the composer, so they can be edited without closing it.
- While editing, the composer's saved-search action (`ComposerSavedSearchAction`) is Update “name” on its own row instead of Save (`composerSavedSearches`). It saves the applied search, the one whose results are on screen, like Save does, so it is enabled only once the edit has run: not while the draft differs from the applied search or a live run is waiting (ADR 0139), and not while the applied search still replays as the saved one. Unlike Save it needs no included tag, since a pin from Recents may have none. When another saved search already replays as the applied search, Update stays off and the composer names that search. Tapping Update closes the composer, which ends the edit, so the confirmation or a storage error shows in the app's snackbar instead of under the sheet; the confirmation appears only when the search actually changed.
- `SavedSearchRepository.update` replaces only the search and keeps id, name, save date and place, under the same lock and snapshot write as `rename`. Edits compare searches by what they replay (`replaysAs`): the mode-normalized query and kind, plus the set of sources for a Multi-Search (Search and the Searches collection sort them before running); not the stored hash, which can differ for the same search, nor a Unified search's sources, which Recents records but replay ignores. An update to a search that replays as the one it holds writes nothing and returns false. An update that replays as another saved search is refused with that search's name, so edits never create a second pin for one search and nothing is merged or removed; the composer checks the same rule first so the refusal is only a backstop. `save` keeps its own `savedFor` match (stored hash and payload), which existing pins and Recents rely on; moving it to `replaysAs` is a separate change. Backup `merge` and `replaceAll` need nothing new: they replace by id, so an edited search restores as edited.
- A changed search starts its new posts over (`resetSavedSearchNewPosts`, given to `SavedSearchViewModel` as a callback, drops its marks and its check attempt), so the next check sets a fresh baseline for the new query instead of counting its results as new against the old one's. `SavedSearchNewPostsChecker.checkIfStale` reads the saved searches itself and, when a check lands, drops it if its claim (`attempts`) no longer stands, or if the stored saved search no longer holds the search it ran, then releasing its own claim, even after a failed fetch, so the edited search stays due. The first covers an edit landing after the check read the stored list; the second covers a queued search claimed after the edit's reset.
- The Searches collection reloads a saved search whose search changed (`SavedSearchesCodexViewModel`, ADR 0152), so it runs the edited query on its next load. Its header opens the same management sheet as Library and Search (`ShellOverlays.showSavedSearchManagement`).

## Consequences

Editing reuses Search entirely, at the cost of an edit mode that lives only as long as the composer stays open: closing the sheet to look at results, including by submitting the input, ends the edit unsaved. Results stay visible above the sheet (ADR 0137), which is where the edit is meant to be checked. An edited search shows no new posts until the next check after the edit.
