ExecPlan: Take video player work off the main thread

After this plan, creating, preparing, rebinding, cooling and releasing the feed's preview players no longer runs on the thread that draws the screen, so scrolling a grid of autoplaying videos cannot lose frames to player housekeeping. The plan starts with a measurement that decides whether the work is needed at all and how far it should go, because it touches playback, the one area where a regression is immediately visible.

Purpose / Big Picture

Every visible animated card in a feed plays at once. That is a product rule, and it means a scroll through a video-heavy feed continuously creates, starts, stops and recycles video players. The video library (Media3 ExoPlayer) gives each player an application thread: the one thread on which the app must make every call to that player and on which the player reports back. By default that is the main thread, which also draws the screen.

Decoding itself already happens elsewhere. What runs on the main thread is the housekeeping: building a player, handing it a video, attaching and detaching the drawing surface as cards scroll, stopping it, and releasing it, a call that waits for the decoder to shut down. The app already works around this by pooling players and spacing the expensive calls out with timers (60 ms between starts, 250 ms between cool-downs, one release per second). That keeps single frames from stacking several of these calls, but each call still lands on a frame.

When this plan is complete, feed preview players live on a dedicated player thread. The main thread only tells that thread what it wants (this video, on this surface, playing or paused) and receives state back (first frame shown, playing, size, error). The visible behaviour is unchanged: the same cards play at the same moments. The expected gain is fewer slow frames while scrolling video feeds, and the timers become a tuning choice instead of a necessity.

This plan may end at Phase 0. The audit that proposed it was a code read, not a measurement. If player housekeeping turns out to be a small share of main-thread time and of slow frames, the right outcome is to record that and stop.

Context And Orientation

  • Feed preview player: a muted, looping ExoPlayer that plays a card's video in the Search, For You, Creator and Codex grids.
  • Pool and lease: FeedPreviewPlayerPool owns preview players for the whole app. A card leases one while it is on screen and returns it when it scrolls away; the pool pauses it, later "cools" it (stops it and clears its video) and eventually releases it.
  • Surface: the buffer a player draws video frames into. The app uses TextureView, a view whose surface is composited by RenderThread like any other view content.
  • PlayerView: Media3's ready-made view that owns a TextureView, sizes it to the video and connects it to a player. It only accepts a player whose application thread is the main thread.
  • Autoplay contract: the macrobenchmark asserts that every visible video is playing during each gesture (24 prepares and 24 first frames in Search, 10 and 10 in the Viewer in the last recorded run). Any change here must keep that passing.

Player thread design (feed previews)

One HandlerThread, owned by VideoPlaybackInfrastructure, is the application thread for every preview player. The pool keeps its logic and moves onto that thread: its Handler parameter already exists, and its main-thread assertions become player-thread assertions.

The card no longer touches an ExoPlayer. It holds a small main-thread object, a preview session, with four operations and one state stream:

interface FeedPreviewSession {
    val state: StateFlow<FeedPreviewState>      // firstFrameShown, isPlaying, videoSize, durationMs, error
    fun attach(textureView: TextureView)        // main thread
    fun detach()                                // main thread
    fun setActive(active: Boolean)              // play or pause
    fun seekTo(positionMs: Long)                // for the feed-to-Viewer position handoff
    fun close()                                 // returns the lease
}

Each operation posts to the player thread, where the pool acquires the lease, prepares, plays, pauses and returns it. The listener that today writes Compose state from the main thread writes the StateFlow from the player thread instead.

Surface handling replaces PlayerView for cards, because PlayerView cannot take such a player. The session listens to the TextureView's surface callbacks on the main thread. When the surface becomes available it wraps it in a Surface and posts player.setVideoSurface(surface). When the view reports the surface is going away, it answers that it will release the texture itself, posts player.clearVideoSurface(), and releases the Surface and its texture only after the player thread confirms the player has let go. That ordering is the one new hazard, so it lives in one class with a state machine that is host-tested. Sizing the video to "fit" becomes a Compose aspect-ratio modifier driven by videoSize from the state.

Pacing. The spacing constants stay as they are in the first version. Once the calls are off the main thread they are measured again, and shortened only where that helps cards start sooner without hurting decoder availability. This plan does not promise to delete them.

What stays on the main thread: the TextureView itself and its composition by RenderThread. Whether TextureView is the right surface type is a separate question, not part of this plan.

Alternatives considered

AlternativeWhy not (for now)
Share one playback thread between preview players (setPlaybackLooper) to make create and release cheaper.All simultaneous previews would decode-feed on one thread, which risks the autoplay contract; it also leaves the calls on the main thread.
Move the Viewer player as well.It is one player, tied to a media session, picture-in-picture, rotation and a per-frame position read. Higher risk for less gain; revisit only with Phase 0 evidence.
Keep PlayerView and wrap the off-thread player in a forwarding player that reports the main looper.PlayerView would then call the real player from the main thread, which the player rejects.

Phases

Phase 0: Measure, then choose

GoalKnow how much main-thread time the player sections take per scenario and whether slow frames coincide with them.
MethodRun searchConcurrentAutoplayScroll, mixedMediaFiveFeedJourney and viewerRepeatedSwipes on the benchmark build. From each trace take, for the main thread only: the summed and worst duration of each TheoriaPreviewPlayer* and TheoriaViewerPlayer* section, the time spent attaching and detaching surfaces (add a temporary trace section around the playerView.player = … assignments if the existing ones do not cover it), and the number of slow frames that overlap any of them. Emulator first, for the method; then the same on the phone, because the emulator's decoders are not representative.
Decision rulePlayer thread if, on the phone, player sections overlap at least one in five slow frames in a feed scenario, or any single section regularly exceeds half a frame (about 4 ms at 120 Hz). Pre-build only if creation alone meets that bar. Otherwise stop. Record the numbers and the choice in the Decision Log.
Also verifyThe two Media3 facts in Context, by reading the 1.11.1 sources, and a ten-line spike proving a player on a background looper renders into a manually supplied TextureView surface.

Phase 1: Session and surface binding behind the existing behaviour

GoalCards use FeedPreviewSession and a plain TextureView, with players still on the main thread. This isolates the view change from the thread change.
AcceptanceHost tests for the surface state machine (available, destroyed, re-available, close during each). Macrobenchmark autoplay contract passes on the emulator. No visual difference in card sizing, first-frame reveal or thumbnail handoff, checked on fixture media.

Phase 2: Move the pool and its players to the player thread

GoalNo preview player call runs on the main thread.
AcceptanceIn a trace of searchConcurrentAutoplayScroll, the main thread contains zero TheoriaPreviewPlayer* sections; they appear on the player thread. Autoplay contract passes. Frame-time percentiles are no worse than before on the emulator. Opening the Viewer from a playing card continues from the card's position. Backgrounding and returning, rotating, and leaving a feed release every player (the active and total player counters in the trace return to their idle values).

Phase 3: Re-tune pacing

GoalSpacing constants reflect decoder limits, not main-thread protection.
AcceptanceEach changed constant has a before and after number for time to first frame and for decoder failures in the journey. Constants that show no benefit from changing stay.

Phase 4: Physical-device acceptance

GoalThe gain is real on hardware.
AcceptanceThree complete macrobenchmark runs of the same APK before and after on the phone, as AGENTS.md requires for performance acceptance, with the autoplay contract in each. This runs as part of the end-of-audit device session and needs the user's go-ahead.

  4. Phase 2: give VideoPlaybackInfrastructure the player HandlerThread; pass its handler to FeedPreviewPlayerPool; add .setLooper(playerThread.looper) in createPlayer(); rename checkMainThread() to assert the pool's handler thread. hasActiveViewerPlayer, which the pool reads to hold back releases while the Viewer plays, becomes a volatile or atomic read.

Idempotence And Recovery

No stored data is touched. Phases 1 and 2 are separate commits; reverting Phase 2 alone returns players to the main thread while keeping the session, and reverting both restores PlayerView. If the autoplay contract fails after Phase 2 and the cause is not found within one investigation, revert Phase 2 and record the trace. Temporary trace sections added in Phase 0 are removed before the plan closes unless Phase 2 keeps them. Benchmark output and traces under build/reports/ and macrobenchmark/build/outputs/ are pruned once their numbers are recorded here.
