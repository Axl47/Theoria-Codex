Purpose / Big Picture

Video and multi-page posts are where the app spends most of its data and where waiting is most visible. The audit in the "Performance Audit of App and CI" thread fixed several media items (A2 metered prefetch cap, A13 memory-only nearest neighbours, A14 offline save from cache, A15 shared ugoira metadata) but never measured buffering, seeking or paging. This plan adds numbers first, then fixes what the numbers show.

After round 1: hidden feed cards stop downloading when the Viewer opens, the Viewer caches the clip it plays instead of re-downloading it, gallery pages a prefetch already downloaded show without a network round trip, the next page is decoded before it is reached, far pages are warmed without full-size decodes, and a gallery's first page no longer shares the link with speculative downloads.

Terms. TTFF: time to first rendered video frame. Seek-to-resume: from a seek request until the player is ready to play at the target. Cache range lock: Media3's SimpleCache lets one writer at a time fill a range; a progressive player's open request locks from its read position to the end of the file, and any other reader of that range reads around the cache (downloads without caching). Warm (images): the file is in Coil's disk cache. Decoded: the bitmap is in Coil's memory cache.

Provider feeds can contain illegal content. Device work uses logs and generated media only: the benchmark never touches provider media, screenshots or recordings.

Measurement Harness

app/src/androidTest/java/com/theoriacodex/app/viewer/MediaBufferingBenchmarkTest.kt is an opt-in instrumented test (skipped unless -e mediaBench true). It drives the app's real feed and Viewer pools, shared video cache, ScrubFrameSource, a real ViewerViewModel with the route's prefetcher (viewerMediaPrefetcher) and planner (viewerPrefetchAction), and Coil's loader. BenchMediaServer.kt is a throttled HTTP/1.1 server inside the app process: one shared token bucket (default 16 Mbit/s), 100 ms before each response's headers, ranges, ETag/Last-Modified and 304s but no Cache-Control (an nginx origin's default). It records every byte written per path as an interval, so it reports total, unique and duplicate bytes, including responses still in flight.

scripts/media_bench_device.py run generates media with ffmpeg (4 × 15 s and 1 × 90 s 1080p H.264 at 4 Mbit/s with AAC; 80 JPEG pages of 1280×1808, about 410 KB each), builds and verifies the debug and test APKs (scripts/verify_device_apk.py), copies the media into the debug app's cache/media-bench through run-as, runs each scenario once per run in a fresh process, and writes medians to build/media-bench/<label>/results.json. record appends a round to the metrics file.

Why in-process loopback, not a host server. A first version served from the Mac through adb reverse. adb buffers far more than a phone's TCP window, so abandoned or paused progressive requests looked like 18.6 MB of background traffic where the loopback version shows 10.3 MB. Loopback socket buffers behave much like a phone's receive window.

Phases

Phase 0: Harness and baseline (done)

Commits a9069fac (share the route prefetcher, prefetch queue and scrub frame source so the benchmark runs production code) and 61759ea6 (benchmark). Baseline recorded as round 0 at 61759ea6.

Phase 1: Video – stop feed previews while a Viewer stream plays (done, 51ae87c0)

FindingAt Viewer open, feed players were paused but kept loading toward their buffer target with their connections open. The two warm cards downloaded their whole clips while hidden (10.3 MB). The opened clip's card held its cache range, so the Viewer read around the cache and re-downloaded that range on the next loop (0.8 MB).
ChangeViewerVideoPlayerPool.acquire calls VideoPlaybackInfrastructure.onViewerStreamAcquired, which stops every feed player (FeedPreviewPlayerPool.stopForViewer). Stopped players keep media, position and (keep-content player view) the last frame. A still-leased card resumes through resume; a bound idle slot re-prepares on its next lease.
ConstraintEvery visible feed card still autoplays: the feed is hidden while a Viewer stream exists, and cards re-prepare from the cache when shown.

Phase 2: Images – use cached images without revalidating (done, 1de77259)

FindingAll 41 displayed pages per run came from the network even though prefetch had already downloaded them: Coil revalidated each cached page (a 100 ms round trip, 304) because the origin sent validators but no freshness lifetime. Without validators it re-downloads them (21 MB duplicates in the first trial).
ChangerespectCacheHeaders(false) on the app ImageLoader; UndecodableImageEviction drops the disk entry of any load that fails for a non-network reason, so a bad cached body cannot stick.

Phase 3: Gallery – decode the next page before it is reached (done, cb6b539a)

FindingA page first prefetched while 2–3 away was only downloaded; its warmed state then made it terminal, so it was never decoded into memory as it came close. Only one displayed page per run was a memory hit.
ChangeviewerPrefetchAction marks static images within VIEWER_MEMORY_PREFETCH_DISTANCE as decodeKeys; the reducer re-queues a warmed image once if it is a decode key and not yet decoded; ViewerPrefetchResult.decoded records it.

Phase 4: Gallery – warm far pages without full-size decodes (done, 5ac2058f)

FindingFar neighbours (disk only) were still decoded at their original size, then discarded.
ChangeStatic images warmed for disk only decode subsampled to a 64 px edge; the full file is still written to the disk cache.

Phase 5: Viewer – load the first media before its neighbours (done, 237540b3, refined in 81935f4f)

FindingOpening a gallery started page 1 and two neighbour downloads at once on a shared link.
ChangePrefetch jobs wait until the session's first media is ready (or 1.5 s, or an error). The first version waited on every page; the interleaved run showed skimming dropping to 91% shown, because a page flipped past before it loaded held back the pages after it. Only the first media waits now. The benchmark reports MediaReady after each shown page, as the renderer does (2cf15750).

Phase 6: Viewer – decode downloaded pages outside the download slots (done, 31bad82f)

FindingPhase 3's decode-ahead jobs took one of the two prefetch slots on every page flip, halving download throughput while skimming (77–86% shown in a same-session run).
ChangeViewerViewModel.launchPrefetch runs a prefetch of already-warmed media without a semaphore permit. Skimming returned to 100% shown.

Surprises And Discoveries

  • Paused progressive players keep loading toward their buffer target with an open connection; the server keeps writing into socket buffers beyond what the player reads (about 2.3 MB per paused clip on loopback). Cached bytes after the run (5.2 MB of a 7.6 MB clip sent) showed the gap.
  • Media3 CacheDataSource reads around (without caching) any range another writer holds, re-checking every 100 KB. A paused feed player of the same clip, or a playing Viewer player ahead of a scrub preview, therefore makes the other reader's bytes uncacheable.
  • Scrub preview frames past the buffer cost about 0.9 MB each and do not warm the release seek, for that reason (the Viewer player's open request locks the rest of the file).
  • Coil 2 reports a revalidated (304) cached image as a network load; a revalidation per displayed page was invisible in the app but cost a full round trip.
  • Media3 1.11.1 defaults are already 1 s to start and 2 s after a rebuffer; the Viewer uses them.
  • Benchmark sessions drift: unchanged seek code measured 538 ms and 625 ms in two sessions, and skim shown ranged 77–91% for one build across sessions. Compare builds interleaved in one session.
  • Prefetch scheduling interacts with skimming in ways unit tests do not show: both "wait for the page on screen" and "decode in a download slot" were harmless while reading and harmful while skimming.

Decision Log

DecisionRationale
Benchmark in-process on the phone with generated media.Repeatable, no provider content, socket behaviour close to a phone link; the phone is the acceptance device.
Model an origin with validators but no Cache-Control.nginx's default for static files; many booru and gallery origins behave this way. With long max-age origins, Phase 2 changes nothing (and costs nothing).
Stop every feed player when a Viewer stream starts, not only the opened clip's.The feed is hidden; hidden players only spend data and decoders. Keep-content views keep their last frame, so nothing blanks.
Keep near-prefetch decodes at the original size.Pages reached by reading are shown from that bitmap, so pinch zoom stays sharp. Decoding at screen size would save memory for large Pixiv pages but soften zoom; left for a product decision.
Do not chunk progressive requests in round 1.Bounding cache locks would let scrub previews warm seeks and cap socket over-download, but it changes how the cache learns content length (offline save relies on it) and needs careful end-of-file handling. See opportunities.

Outcomes And Retrospective

Round 1 removed waste rather than tuning buffers. The two biggest effects were invisible in the app: hidden feed players downloading whole clips behind the Viewer, and a network round trip for every cached gallery page. Both came from defaults behaving as designed (a paused progressive player keeps its request open; Coil revalidates responses without a freshness lifetime). The measurements caught a regression in my own first version of "first media alone" (skimming fell to 77–91% shown) that unit tests could not have found; the fix restored 100%. Seeking and scrub previews are network-bound and limited by Media3's cache range locks; they need the structural change listed first below.

Remaining Opportunities (ranked)

  1. Bounded cache locks for streaming players (high impact, high effort). A playing Viewer player locks the rest of the file, so scrub preview frames (about 1 MB each past the buffer) are downloaded uncached and the release seek downloads them again (seek after scrub 495 ms; from cache it would be closer to 150 ms). The same lock costs the feed-to-Viewer handoff its remaining 0.46 MB of duplicates. Bounding each request (for example a Cache wrapper that clamps hole spans to a few MB) also caps how far an abandoned or paused request can over-download. Needs care: the cache learns a file's length only from unbounded requests (offline save relies on it), each chunk is a new range request, and end-of-file 416 handling must not loop.
  2. Viewer neighbour video prefetch on unmetered networks (high data impact, medium effort). Each neighbour video warms up to 24 MB, so opening one video can fetch about 48 MB the user may never watch. Not measured yet: add a Viewer swipe scenario, then try capping to the opening seconds (as metered already does) and compare swipe TTFF against bytes.
  3. Warm idle feed players while scrolling (medium). Round 1 stops feed players only while a Viewer stream plays. While scrolling the feed, the two warm idle players keep loading with open requests, which costs socket over-download for cards that left the screen (2–3 MB per clip on loopback). Needs a scrolling scenario.
  4. Scrub preview start (medium, low effort). Each drag builds a new FrameExtractor (about 300 ms of the 714 ms first frame) and every frame waits an 80 ms debounce, including the first. Keep one extractor per Viewer page for a short idle period or create it when the timeline appears, and skip the debounce for the first frame.
  5. Instant seek mode (medium, opt-in setting). With "instant seek" on, every drag movement issues an exact seek on the main player. Media3 1.11's setScrubbingModeEnabled is designed for this. Needs a scenario of rapid seeks.
  6. Gallery memory (medium for large Pixiv pages, product decision). Pages next to the current one are decoded at original size (sharp pinch zoom). Decoding at screen size, or 2× screen size, would cut peak memory for large originals; nhentai pages are already near screen size.
  7. Gallery window shape (low on this link). Skimming is already 100% at 16 Mbit/s. A forward-biased window (more ahead, fewer behind) and a third download slot only matter on slower links or larger pages; test at 4–8 Mbit/s before changing.

Idempotence And Recovery

  • The runner is safe to rerun: media generation and the device copy are skipped when unchanged (manifest of names and sizes); each run uses fresh URLs, and each scenario removes its video cache entries and gallery disk entries afterwards.
  • Only com.theoriacodex.debug and its test package are installed, after scripts/verify_device_apk.py checks the application ID and debug signing. Production com.theoriacodex is never touched.
  • To remove the benchmark media from the phone: adb -s <serial> shell run-as com.theoriacodex.debug rm -rf cache/media-bench.
  • Each change is one commit; revert any of them independently. Phase 3 changes Viewer state shape (ViewerPrefetchState.decoded, QueuePrefetch.decodeKeys); both have defaults.
