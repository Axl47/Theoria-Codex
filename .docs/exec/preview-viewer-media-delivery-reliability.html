Make Preview and Viewer media delivery faster and more reliable

This plan makes existing Pixiv, Gelbooru, NHentai, and Hitomi media appear with less avoidable waiting and recover cleanly when a request fails. It repairs generic retry, chooses the media nearest to the current Viewer position for prefetch, reuses one playback cache, distinguishes quality upgrades from failure fallbacks, bounds Pixiv Ugoira memory, and removes duplicate provider work without changing the app's simultaneous-autoplay contract.

Purpose / Big Picture

After this plan is complete, Preview cards use every already-known safe image candidate before giving up or contacting the provider again. Viewer opens immediately when the selected post already has usable media. Swiping warms the nearest media instead of unrelated entries at the beginning of the session. A failed image, video, animated WebP, GIF, or Pixiv Ugoira always offers a real retry that starts a new load, while provider-specific recovery can replace stale URLs in parallel.

Pixiv Ugoira no longer keeps an unbounded ZIP, duplicate archive entries, and every decoded frame in memory at once. Gelbooru retains its certificate-safe media normalization and uses the preview/sample/full data already returned by search. NHentai treats alternate extensions as failure fallbacks rather than quality upgrades. Hitomi retains its live gg.js CDN recovery while reusing the gallery manifest already fetched for Search when Viewer needs the full post.

Observable completion: on the isolated Debug app, open one representative result from each source, retry an induced first request failure, and swipe through adjacent media. The Viewer mounts without an unnecessary provider wait when media is already present; Retry visibly restarts every media kind; only adjacent media is prefetched; warm swipes reuse cached bytes; and Pixiv Ugoira remains within the configured archive and decoded-memory budgets.
Hard boundary: this plan does not repair duration enrichment, duration filtering, feed scrolling, reusable feed-player ownership, card viewport callbacks, or the active duration performance ExecPlan. Do not edit .docs/exec/duration-metadata-performance-rebuild.html as part of this work. Preserve concurrent autoplay for every visibly presented animated or video card.

Context And Orientation

Preview means the shared card media rendered by SearchResultCard across Search, For You, Creator Profile, Recents, and Codex browsing. Viewer means the full-screen nested post/media pager. A media delivery candidate is one local path or remote URL that can represent the current image. A candidate may be a quality upgrade that should load after a lower-resolution image succeeds, or a failure fallback that should be tried only when the current candidate fails. Prefetch means warming bytes for media near the current Viewer item before the user swipes to it. Single-flight means concurrent requests for the same resource share one job rather than downloading or refreshing twice.

Provider boundaries that must remain

  • Pixiv: retain source-scoped authorization and Referer headers. Static search results already contain medium/large/original image information; do not add a detail request merely to open a static illustration.
  • Gelbooru: preserve normalizeGelbooruMediaUrl and certificate verification. Search already returns preview, sample, and full URLs; use them before resolving the post again.
  • NHentai: preserve the primary API plus bounded mirror recovery. Alternate webp/jpg/png/gif locations are equivalent-format fallbacks, not progressively better images.
  • Hitomi: preserve Nozomi pagination, bounded hydration concurrency, live gg.js configuration, alternate shards/formats, and 404-driven configuration refresh.

Phase 5: Bound Pixiv Ugoira and unify token refresh

Status: Proposed.

GoalUgoira loading is cancellation-safe, retryable, single-flight, disk-backed, and bounded by compressed bytes, expanded bytes, dimensions, frame count, and decoded-memory weight.
Primary filesapp/src/main/java/com/theoriacodex/app/viewer/PixivUgoiraPlayer.kt, app/src/main/java/com/theoriacodex/app/di/TheoriaAppContainer.kt, core-sources/src/main/kotlin/com/theoriacodex/sources/RealAdapterRegistry.kt, core-sources/src/main/kotlin/com/theoriacodex/sources/pixiv/PixivSourceAdapter.kt, Pixiv auth classes under core-sources/src/main/kotlin/com/theoriacodex/sources/pixiv/, and their matching tests.
Commitperf(pixiv): bound ugoira loading and share auth refresh
AcceptanceConcurrent loads for one post perform one metadata request, one ZIP request, and at most one token refresh. Archive limits reject malformed/oversized input safely. Preview uses card-sized frames, Viewer can request a larger bucket, export reuses compressed data, and decoded cache weight never exceeds its configured bound.
  1. Create a core-sources PixivTokenCoordinator owned by TheoriaAppContainer and passed to both RealAdapterRegistry/PixivSourceAdapter and PixivUgoiraClient. Under one mutex, re-read durable credentials before refreshing so a concurrent winner is reused.
  2. Keep Ugoira binary transport app-owned but make every connection cancellation-aware, disconnected in finally, and retried for I/O plus existing retryable statuses under a bounded attempt policy.
  3. Stream the ZIP to an atomic temporary cache file with a hard compressed-byte limit. Validate frame count, entry names, duplicate names, per-entry expanded bytes, total expanded bytes, image dimensions/pixels, and metadata-to-entry correspondence before publishing the cache record.
  4. Decode from the disk-backed archive for an explicit size bucket. Preview/card requests must not decode full-resolution frames when the display target is much smaller. Viewer and MP4 export may request full data without keeping both compressed and every decoded representation live unnecessarily.
  5. Replace the eight-entry cache with a weighted LRU that accounts for bitmap allocation bytes. Active playback leases cannot be recycled underneath a visible consumer; inactive entries are evictable. Record the chosen byte budget and its relationship to Android memory class in Decision Log.
  6. Use a per-post-and-size single-flight map with consumer-isolated cancellation. Cancel the underlying job only after the last consumer leaves; never let one offscreen card cancel a visible Viewer load.

Work Plan

  1. Respect the active performance owner. Do not start behavior work until duration/scroll acceptance is stable. Rebase this inventory onto the accepted HEAD and update only this plan's stale facts.
  2. Characterize before repairing. Preserve deterministic failing tests for F01-F08 and a comparable device baseline. Tests that currently pass because they encode false-ready or first-six behavior must be changed only in the phase that changes the contract.
  3. Repair correctness before optimization. Make Retry and candidate fallback truthful before making launch or prefetch faster. A faster path that cannot recover is not accepted.
  4. Keep state ownership explicit. Reducers own media generation/error/prefetch status; ViewModel owns jobs and bounded queues; composables render immutable state and emit typed events; provider adapters own provider parsing and refresh.
  5. Unify caches without cross-contaminating identities. Image requests continue through Coil. Video preload/playback share Media3 cache identity including request headers. Ugoira owns a separate compressed-archive/decoded-frame cache because it is not ordinary video playback.
  6. Optimize provider calls last. Once shared retry/candidate/prefetch behavior is stable, add Pixiv token/Ugoira single-flight and Hitomi manifest reuse. Keep Gelbooru/NHentai changes limited to consuming already-known media and normal resolution recovery.
  7. Validate once at system level. Run the complete host/device matrix after the last relevant patch, compare against the frozen baseline, update this living plan, and stop when acceptance is sufficient.

Quantitative acceptance gates

  • Retry: deterministic first-failure/second-success coverage passes for every media renderer; device Retry visibly starts one new attempt without leaving duplicate jobs.
  • Prefetch selection: zero requested keys fall outside the configured adjacent window; at most two prefetch jobs run concurrently; superseded session jobs publish no state.

  • Requests: Gelbooru opening does not add a detail request when search media is viable; NHentai does not request a second extension after successful display; Hitomi Search-to-Viewer uses one manifest request within TTL; concurrent Pixiv requests perform at most one token refresh.

Surprises And Discoveries

  • Observation: the accepted long-scroll repair expanded the shared Media3 cache to 256 MiB and moved Preview player lifetime into an application-owned reusable pool. Consequence: Viewer preloading must reuse that cache/data-source identity without entering the feed lease or preparation owners.
  • Observation: no Android device was connected at Phase 0. Consequence: deterministic behavior can proceed, but final device timing, request, cache, and heap gates remain unproven until hardware is available.
  • Observation: the visible image Retry control is not a generic reload. It only requests optional provider recovery, and only Hitomi implements that interface. Evidence: ViewerRoute.recoverAndApplyMedia returns when recoverRemoteMedia returns null.
  • Observation: the current prefetch window contains six items but is unrelated to the current flattened position after the beginning of a session. Evidence: ViewerScreen filters the current key and then calls take(left + right) from the start.
  • Observation: video prefetch treats unsupported work as success. Evidence: ViewerVideoPrefetchAction.SKIP returns true, after which reducer state adds the key to ready.
  • Observation: NHentai mirror extension fallbacks share the same progressiveUrls field used for Pixiv/Gelbooru quality ladders. Evidence: imageUrlCandidates appends WebP/JPG/PNG/GIF alternatives while Viewer proactively prepares the next candidate after success.
  • Observation: Hitomi's CDN resolver is already bounded, mutex-protected, version-aware, and refreshes once per failed configuration. The repeated work is gallery-manifest acquisition, not CDN derivation.
  • Observation: the shared DefaultSourceHttpClient already retries I/O and retryable statuses with cancellation-safe connection teardown. Pixiv Ugoira bypasses that behavior for binary work and must reproduce equivalent bounded guarantees if it remains app-owned.

Idempotence And Recovery

  • All JVM, build, static-analysis, HTML, and host dry-run commands are safe to rerun. Generated evidence belongs under ignored build/reports/preview-viewer-media-delivery/ paths with unique baseline/final SHA names.
  • Each implementation phase has a focused Conventional Commit. If interrupted, inspect git status, the phase progress item, and the cached diff before continuing. Never discard unrelated work or use git reset --hard.
  • Candidate/retry/prefetch migrations are code-only and require no user-data rewrite. Old posts remain readable because ImageRef persistence is unchanged.
  • The video cache migration must not delete production data. Obsolete files live under app cache and may age out through bounded eviction; a cleanup action is optional and must target only the exact legacy cache directory.
  • Ugoira cache publication must be atomic: write a uniquely named temporary file, validate and sync it, then rename. On cancellation/failure, remove only that verified temporary file. A prior valid cache entry remains usable.
  • Hitomi and Pixiv single-flight maps remove terminal jobs in finally. A failed job must not remain as a poisoned reusable entry.
  • If the Media3 preload prototype cannot share the existing cache/header identity, document the failure and use the planned CacheWriter fallback. Do not land both architectures.
  • If device identity/signing proof is incomplete, stop before any connected command. Never uninstall, clear, downgrade, or replace com.theoriacodex.
