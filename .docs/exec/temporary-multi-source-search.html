Temporary multi-source Search

Let a user start from one Search source, long-press other source chips to build a temporary explicit source set, and run that set through the existing Unified search engine while keeping each chosen source visibly highlighted.

Purpose / Big Picture

Today Search has two mutually exclusive choices: one source, or global Unified using the sources enabled in Settings. After this change, a user in a single-source mode can long-press another source to create a temporary multi-source scope. The source chips themselves remain selected, the Unified chip remains unselected, and Apply searches exactly those sources through the existing UnifiedSearchOrchestrator.

The feature does not edit Settings and does not introduce a third permanent Search mode. It is a short-lived way to compare or combine a deliberate subset of sources. A normal tap on any source collapses back to that one source; a normal tap on Unified returns to the existing global Unified behavior.

Observable outcome: select Pixiv, long-press Gelbooru, and both logos become highlighted. Applying a query returns only Pixiv and Gelbooru results. Loading another page and retrying retain that exact pair.

Context And Orientation

Single-source mode means QueryMode.Source(source); the coordinator calls that source adapter directly and ignores the source’s global Unified toggle. Global Unified means QueryMode.Unified; the coordinator asks UnifiedSearchOrchestrator to search the currently enabled and available Settings sources. Temporary multi-source scope will mean an explicit set of two or more available sources that borrows the global Unified execution path without changing the global enabled-source set.

SearchViewModel is the navigation-scoped owner. It receives typed actions, schedules search jobs, publishes immutable SearchUiState, and survives ordinary Activity recreation. SearchCoordinator owns query rules and provider execution. This plan keeps the temporary selection in that route/coordinator boundary; it does not put UI-only selection logic in Compose and does not change AppSettings.

Persistence boundary

Temporary multi-source runs must not be written as a normal global Unified applied query or Recent Search because the current durable Query format cannot encode the explicit subset. Recording it as Unified would later replay against every globally enabled source, which is false history. The first pass therefore keeps the temporary query, its scope-aware execution key, and scroll/results ownership inside the active Search route. Durable subset history is explicitly out of scope and would require a separate versioned persistence design.

Execution identity

Create one helper that derives an execution key from the sanitized query hash plus a canonical, presentation-independent ordering of the explicit source names. Use it for temporary result override caches, scroll ownership, and Viewer launch context. This prevents a Pixiv+Gelbooru run from colliding with a global Unified run containing the same terms. Normal single-source and global Unified hashes remain backward compatible.

Work Plan

  1. In SearchContract.kt, add an immutable route-level selection type with constructors/invariants for global Unified, single source, and temporary explicit sources. Keep source sets canonical and require at least two entries for the temporary case.
  2. Add draft and applied selection fields to SearchQueryUiState. Change SearchUiState.hasPendingChanges to compare both query and selection. Add a typed action such as ToggleTemporarySource(source); do not pass raw gesture callbacks beyond the UI boundary.
  3. In SearchCoordinator, own draft and applied selection alongside the corresponding queries. Normal setMode calls clear temporary scope. A new toggle method creates, grows, shrinks, or collapses the temporary set and returns whether state changed.
  4. On temporary activation, sanitize the current draft through the existing Unified portability rule, reset unsupported facets, clear autocomplete state, and reuse the existing source-term removal message. Preserve portable sort/date/min-score values.
  5. Centralize effective source calculation: draft suggestions use the explicit draft set when present; a temporary root request uses the applied explicit set; global Unified uses Settings-enabled available sources; single-source mode continues to call its adapter directly.
  6. Extend RootSearchRequest with an explicit execution-scope marker and scope-aware execution key. Store exactly the selected sources in the request so root results, retry, page tokens, query overrides, resolved-post overrides, scroll state, and Viewer binding share one identity.
  7. Keep temporary runs out of QueryRepository and RecentsRepository. They cannot truthfully encode the subset today. Continue normal persistence unchanged for single-source and global Unified runs.
  8. Reconcile adapter availability against both draft and applied explicit sets. Invalidate active generations before changing the set. Collapse two-to-one without leaving a fake multi-source state.
  9. In SearchViewModel, handle the typed toggle action through the coordinator, cancel stale autocomplete, publish state, and refresh suggestions. Applying, resetting, retrying, and paging continue through existing scheduled request paths.
  10. In SearchCoordinatorStateMapper.kt, copy selection values defensively into immutable state. Do not derive applied execution from current Settings in the mapper.
  11. Refactor ModeRow in SearchScreen.kt to accept draft selection and separate tap/long-press callbacks. Use one accessible combined-click surface, retain logos and the Unified source-count badge, and highlight every explicitly selected source.
  12. Change multi-source-only UI conditions—source badges and status rows—to use the applied execution scope rather than only applied.mode == QueryMode.Unified.
  13. Add focused tests before the final batch. Prefer deterministic fake adapters and repositories; do not add live-provider dependence to this feature’s acceptance lane.
  14. Run the bounded validation batch once, perform the manual device pass once, update this plan’s living log/outcome, and stop when the stated evidence is sufficient.
Out of scope: changing Settings UI, saving named source groups, durable multi-source Recent Search replay, provider ranking changes, a new domain QueryMode, or redesigning the Search filter sheet.

Behavior-based acceptance criteria

  • A temporary selection begins only from non-Unified mode and always contains at least two available sources.
  • Every selected source is visibly highlighted; the Unified chip is not highlighted during temporary scope.
  • Apply, retry, paging, autocomplete, status, result badges, and Viewer continuation never widen beyond the correct draft/applied set.
  • Selected sources can participate without changing or being blocked by their global Unified Settings toggle.
  • Source-owned facets are removed before cross-source execution with honest user feedback.
  • Normal single-source and global Unified search behavior and persistence remain unchanged.
  • Temporary subset state is not persisted or misrepresented as a replayable global Unified Recent Search.

Surprises And Discoveries

  • Observation: RootSearchRequest already freezes enabled sources, weights, previous results, and statuses, so the temporary subset can reuse the existing cancellation-safe Unified execution instead of adding another orchestrator. Evidence: SearchCoordinator.beginRootSearch, executeSearch, and loadNextPage.
  • Observation: the current durable Query, query codec, and Recent Search entry cannot represent an explicit source subset. Evidence: QueryMode has only Unified and one Source; RecentSearchEntry stores only Query plus its hash.
  • Observation: source-specific terms are deliberately blocked or removed when entering Unified mode. A temporary cross-source search must reuse that rule or another provider could receive a facet it cannot interpret. Evidence: Query.forMode call sites and existing validation messages in SearchCoordinator.
  • Observation: the baseline plan at commit 8540503 already failed the repository HTML validator on ten documentation-only findings: lowercase doctype, two self-closing meta tags, two invalid aria-label uses, and five self-closing br tags. The closeout normalized those tags and reran html-validate successfully; no production file was changed for this finding.
  • Observation: a live one-tag Hitomi global search can return the same gallery ID more than once. Compose rejected the repeated keyed identity with IllegalArgumentException: Key "HITOMI:4076681" was already used. The owning repair is to preserve first-seen order while deduplicating the decoded provider record before gallery hydration.

Decision Log

  • Decision: keep temporary multi-source selection in the Search route/coordinator, not Settings or QueryMode. Rationale: the request describes temporary execution and separate chip highlighting; Settings and durable query semantics should remain truthful. Date/Author: 2026-07-26 / Codex.
  • Decision: maintain separate draft and applied source scopes. Rationale: Search already uses Apply/Reset semantics; result paging must follow the applied set while the user may edit the next draft set. Date/Author: 2026-07-26 / Codex.
  • Decision: explicit selected sources bypass global Unified enablement but never adapter availability. Rationale: a directly selected source already works outside Unified toggles, and the temporary set must behave like several deliberate direct selections without mutating Settings. Date/Author: 2026-07-26 / Codex.
  • Decision: do not persist or record temporary subset searches in the first pass. Rationale: existing persistence would replay them inaccurately as all-source Unified or one source. A later durable feature needs a versioned source-scope contract. Date/Author: 2026-07-26 / Codex.
  • Decision: use normal taps as deterministic exits and long press as add/remove. Rationale: this preserves existing mode selection, makes the feature discoverable through visible highlighting, and prevents users becoming trapped in a pseudo mode. Date/Author: 2026-07-26 / Codex.
  • Decision: normalize pre-existing ExecPlan HTML findings during closeout. Rationale: the ten validator findings were unchanged from baseline and belonged to the explicitly permitted docs-only scope; production code remained untouched. Date/Author: 2026-07-26 / Codex.
  • Decision: retain Material FilterChip as the visual component and place the combined gesture owner in a transparent sibling overlay. Rationale: this keeps the original styling exact and prevents either the Material click handler or the long-press handler from double-firing. Date/Author: 2026-07-26 / Codex.

Idempotence And Recovery

All planned Gradle and Git checks are safe to rerun. No database migration, Settings rewrite, tag, release, or destructive command is required. Implement phases in order because later UI work depends on the source-scope contract.

  • If Phase 1 is interrupted, inspect git diff, finish the immutable state/action/mapping contract, and rerun only the two focused test classes before continuing.
  • If a root search widens unexpectedly, inspect the source set captured in RootSearchRequest; do not patch individual adapters or filter results after execution.
  • If paging differs from the root results, repair the common applied-scope/request identity used by both paths rather than adding a paging-only selection.
  • If source chips double-fire, remove competing nested click surfaces and keep one combined click/long-click semantic owner.
  • If a selected source disappears at runtime, invalidate the active generation before collapsing the explicit set so a stale completion cannot republish removed-source results.
  • To abandon the feature before merge, revert only the files named in this plan. There are no generated data files or migrations to clean.
