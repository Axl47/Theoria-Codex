Harden code quality and clarify UI ownership

This plan turns the July 10 code-quality audit into a staged implementation program. It first protects cancellation, persistence, request ordering, and releases; then bounds runtime work; then moves long-lived dependencies out of Compose and gives each route one explicit state owner; finally it consolidates repeated policy, modernizes storage and tooling, and closes the work with measurable quality gates.

Purpose / Big Picture

Theoria Codex already has meaningful module separation and a substantial test suite. The problem is not a lack of architecture; it is that rapid feature growth has accumulated coordination work at a few junctions. The app shell constructs long-lived services, owns route and workflow state, and launches asynchronous work. Search, Viewer, and For You coordinators combine protocol orchestration with mutable Compose state. Several persistence and HTTP paths are unbounded or have inconsistent durability. The release workflow can publish a tag without first proving that the tagged commit passed the deterministic quality gate.

When this plan is complete, the user should see the same product behavior with fewer stale-result races, fewer restart-only data regressions, smoother startup and scrolling, safer long search sessions, and more reliable updates. A developer should be able to change Search, Viewer, For You, Creator Profile, storage, or a source adapter without reopening the entire application shell. A tagged prerelease must be unable to publish until the exact commit passes verification.

Scope decision: this is an incremental ownership migration, not a rewrite and not a mandatory Hilt conversion. Existing provider-specific protocols and separate file-backed/in-memory repository implementations remain explicit. Shared policy moves; protocol and storage mechanics do not get hidden behind generic base classes.

Context And Orientation

A composition root is the boundary that constructs long-lived dependencies. Today rememberTheoriaAppGraph() performs that work from Compose. A route state owner is a lifecycle-aware object—normally a ViewModel or narrowly scoped state holder—that owns one screen's asynchronous work and immutable UI state. A single-flight request allows one current request for a logical operation and cancels or supersedes older work. A repository contract suite runs the same behavior tests against both in-memory and file-backed implementations.

Subagent Orchestration Contract

The primary integrator owns this ExecPlan, working_list.md, cross-lane decisions, central-file integration, final validation, and commits. Subagents do not edit the plan or working list. Every lane starts from the same commit, reports the exact files changed, runs its focused tests, and stops if it needs a file owned by another lane.

RuleExecution contract
Agent choiceUse Luna Medium for contained implementation and tests, Luna Low for inventories/validation, and Terra High for UI ownership, persistence migration, or build-system decisions. Reserve the primary/Sol context for integration and final validation.
Parallel editsOnly lanes marked parallel may run together. Their file sets must remain disjoint. Tests may be shared; production files may not.
Central filesTheoriaApp.kt, TheoriaAppGraph.kt, TheoriaApplication.kt, app/build.gradle.kts, gradle/libs.versions.toml, and workflows are integrated by one serialized owner per phase.
Handoff evidenceEach agent returns: summary, changed files, tests and output, unresolved risks, and the next integration action. No “done” report without evidence.
Commit shapeOne integrated Conventional Commit per phase by default. If a phase has a risky migration, use one commit per independently revertible wave and record both in the living log.
Stop conditionStop and report if behavior requires a new product decision, persisted schema cannot be migrated losslessly, a live-provider contract changes, or unrelated dirty files overlap.

Surprises And Discoveries

  • Production copy-paste is already low at 1.02%. The important duplication is policy and ownership drift, so a mechanical DRY rewrite would create more risk than value.
  • The first connected run passed three tests but the only general Compose app-shell smoke failed reproducibly with no hierarchy. The deterministic unit/build baseline is green while the device UI signal is not.
  • The Compose smoke host did render its first frame, but the connected device was securely locked and dozing; Android moved MainActivity from RESUMED to CREATED and removed the semantics hierarchy. The test now reports that lifecycle cause directly and targets the navigation icons' actual content descriptions. A fake application container and render-only TheoriaAppContent seam are still required in Phase 3 for hermetic route-flow tests.
  • The previous quality plan successfully extracted the graph and shared media/download policy, but dependency creation still lives inside composition and feature growth moved orchestration pressure into the graph and route coordinators.
  • Hitomi's global index records can individually approach the configured multi-megabyte bound, making entry-count-only caching insufficient; the cache budget must be byte-weighted.
  • Some providers can ignore coroutine cancellation while finishing a request. Search therefore needs both job cancellation and generation-gated publication; cancellation alone cannot protect visible state or persisted query order.
  • Independent green lanes were not sufficient by themselves: integration review found repository memory could get ahead of failed disk writes, Hitomi page tokens could cross an index-version rotation, Search could lose a pending scroll write on disposal, and updater choices spanned multiple file commits. Phase 2 closed each cross-lane gap before commit.
  • File-backed constructors now dispatch bytes to IO but still synchronously await readiness. Phase 3 must move their construction out of Compose and give the container application lifetime; Phase 6's asynchronous-store decision remains responsible for eliminating the remaining startup wait.

Decision Log

  • 2026-07-10 / Codex: Fix correctness and observability before UI movement. Rationale: cancellation, request ordering, durability, and CI make subsequent ownership changes diagnosable.
  • 2026-07-10 / Codex: Use an application container without requiring Hilt. Rationale: stable lifetime and testable factories solve the current problem; introducing a DI framework is optional and does not itself clarify ownership.
  • 2026-07-10 / Codex: Route owners expose immutable state and typed actions. Rationale: this makes async ownership visible and allows screens to become renderers without losing feature-specific behavior.
  • 2026-07-10 / Codex: Keep provider protocols and storage implementations explicit. Rationale: common policy should be centralized, but a generic base adapter or repository inheritance would hide meaningful differences.
  • 2026-07-10 / Codex: Prototype DataStore/Room before migration. Rationale: the right store depends on measured write patterns and migration safety; modernization alone is not sufficient justification.
  • 2026-07-10 / Codex: Upgrade libraries, Kotlin/Compose, AGP/Gradle, and R8 in separate waves. Rationale: each layer changes failure modes and must remain independently revertible.
  • 2026-07-10 / Codex: Keep provider-live Android checks behind explicit instrumentation arguments. Rationale: protocol reachability is valuable evidence but must not make deterministic PR verification depend on external provider availability.
  • 2026-07-10 / Codex: Make UiRestoreRepository the sole final tab owner and retain the Settings field only as migration input. Rationale: one-time compatibility does not justify ongoing dual writes.
  • 2026-07-10 / Codex: Never delete unreadable encrypted credentials automatically. Rationale: a restore/key mismatch must be visible and user-confirmed because all source accounts share the encrypted store.
  • 2026-07-10 / Codex: Treat an atomic file commit and its observable repository state as one operation. Rationale: failure or cancellation must restore the previous in-memory snapshot so restart behavior cannot contradict what the UI just observed.
  • 2026-07-10 / Codex: Bind Hitomi global pagination to the galleries-index version. Rationale: an offset is meaningful only for the exact ordered ID snapshot that produced it; legacy global tokens therefore fail closed while pure Nozomi v2 tokens remain compatible.
  • 2026-07-10 / Codex: Make transient persistence lifecycle-owned. Rationale: Search flushes its final observed scroll position on disposal, updater decisions use one transform, and one application-owned tag store removes cross-Activity writer overlap while retaining explicit flush/close operations for tests and the future container.

Idempotence And Recovery

  • All Gradle test, lint, compile, assemble, and reporting commands are safe to rerun. Generated build/ outputs are disposable; do not delete user data or unrelated worktree changes.
  • At every phase start, run git status --short and record the baseline. Agents must not use destructive reset/checkout commands. If file ownership overlaps, stop and let the primary integrator reconcile.
  • For route migrations, keep one authoritative owner. If integration fails, revert the route wiring commit or restore the legacy owner as a whole; do not leave both owners mutating state.
  • For persistence migrations, copy legacy fixture files before first migration, use version markers, and make migration retry-safe. Never delete the legacy source until the new store commits and verifies its imported record count/checksum. A failed migration must leave the old data readable.
  • For credential migration, retain the old encrypted entry until the new Keystore value is written and read back. Do not log secret values. Backup exclusions may land before the storage replacement and are safe to keep if the replacement is delayed.
  • For toolchain waves, preserve one green commit before each version change. If a wave fails, revert only that wave; do not compensate with broad lint suppressions, disabled tests, or weakened release checks.
  • For R8, keep shrinking disabled until release-like device acceptance is green. If reflection/serialization breaks, add the narrowest keep rule with a regression test and record it in this plan.
  • To resume after interruption, open this file, read Current Status and the Living Log, inspect working_list.md, then continue from the first unchecked lane whose prerequisites are satisfied.
