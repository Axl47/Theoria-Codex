Purpose / Big Picture

A user can express tag1 AND tag2 AND (tag3 OR tag4) without learning query syntax. Search treats groups as Boolean eligibility and preserves the selected sort. In the Codex overflow, each source can own an Automatic recipe such as landscape AND (night OR sunset); a newly liked post is added only when it satisfies every required group for its source.

The grammar is intentionally shallow: AND between positive groups, OR inside a group, and the existing flat exclusions. No arbitrary nesting or grouped negative expressions are introduced.

Context And Orientation

A tag group is one or more equivalent alternatives. Every positive group is required; any term inside that group may satisfy it. A source recipe is the complete list of groups used for one provider in a Codex Automatic rule. Providers retain ownership of syntax and transport, while platform-free code owns the expression model and deterministic matching.

Phases

Phase 1: Provider OR Research

Use repository HTTP clients and local environment credentials to compare known single-tag result sets with candidate natural-OR forms for Pixiv and Gelbooru. Record only syntax, result identities/counts, and whether the response is exact; never print tokens, user IDs, API keys, or signed request URLs.

Phase 2: Shared Expression And Compatibility

Add ordered positive groups. Existing Search include terms decode as singleton groups, preserving current AND behavior. Existing Automatic tags migrate into one OR group per source, preserving current match-any behavior. Query hashes, applied queries, saved state, Recents payloads, JSON stores, Room records, and tests move together.

Phase 3: Grouped Search Execution

Prefer verified native OR. Otherwise branch on the smallest OR group, include all singleton requirements in each request, verify remaining groups against authoritative post taxonomy, deduplicate after hydration, and retain one continuation token per branch. Group matching never boosts rank.

Phase 4: Search Interaction

Normal Add creates a singleton required group. The compact editable row uses spacing between required groups and shows OR within multi-term groups, avoiding repetitive AND labels. Tapping a group opens an editor that reuses current autocomplete and favorites for Add alternative, removal, and splitting a term into a separate required group. Applied collapsed context remains one-line and never shows draft state.

Phase 5: Codex Automatic Recipes

The shared overflow becomes Automatic rules. Each represented source owns an independent recipe. Existing represented-tag counts feed Add requirement and Add alternative pickers. Like transitions evaluate the post only against its source recipe in the existing Room transaction; editing rules never removes saved memberships.

Phase 6: Bounded Validation

Run one focused host batch covering model compatibility, reducer behavior, query execution, provider compilation, Room migration/transaction matching, and UI presentation. No connected, installation, or production-package command is required.

Work Plan

  1. Build a credential-safe, test-only OR probe at the provider boundary and record Pixiv/Gelbooru findings.
  2. Add SearchTermGroup and canonical normalization/evaluation helpers in platform-free modules. Restrict one group to one facet/namespace; Unified accepts portable general-tag groups only.
  3. Version all Search encodings and hashes. Legacy flat includes become ordered singleton groups; exclusions stay flat.
  4. Add grouped continuation state and exact provider execution without deriving exhaustion from filtered visible results.
  5. Implement Search reducer actions and one reusable group editor UI. Preserve existing Add, Exclude, Apply, Reset, restoration, and scroll ownership.
  6. Replace CodexAutomaticTag storage with ordered source recipes/groups, retaining compatibility migration from flat OR rules.
  7. Update Room and atomic like matching, then replace the flat Automatic list with per-source recipe cards and represented-tag group editing.
  8. Run focused validation once, repair root causes in grouped patches, update this plan/checklist, and add only genuinely non-obvious durable findings to AGENTS.md.
The fallback planner must have a small branch and scan bound and an explicit unsupported result when authoritative taxonomy cannot prove remaining groups. It must never silently approximate a Boolean expression.

Surprises And Discoveries

  • The current production Room schema is version 6; grouped Automatic storage must advance from that system of record rather than the older completed Automatic-rule plan's version 4 snapshot.
  • Gelbooru's current exact OR syntax is a brace group with tilde-separated tags, for example {landscape ~ cat}; the older bare-tilde form returns no posts.
  • The supplied Pixiv access token returns OAuth invalid_grant for ordinary search, autocomplete, and trending calls. Native OR therefore remains unproven and must not be assumed.
  • Search and Codex already converge at shared owners, so no route-specific duplicate logic is needed.

Decision Log

  • Decision: AND between positive groups and OR within a group only. Rationale: this covers the requested behavior while keeping entry and editing comprehensible. Date/Author: 2026-08-11 / Codex.
  • Decision: groups are Boolean eligibility, never a ranking boost. Rationale: Newest, Popular, Top, Random, and Unified source weights remain meaningful. Date/Author: 2026-08-11 / Codex.
  • Decision: Automatic recipes are independent per source. Rationale: canonical tag identity is provider-owned and a post belongs to one source. Date/Author: 2026-08-11 / Codex.
  • Decision: legacy Search terms become singleton groups while legacy Automatic tags become one OR group per source. Rationale: both current behaviors survive migration exactly. Date/Author: 2026-08-11 / Codex.

Outcomes And Retrospective

The feature is implemented end to end. Search preserves shallow Boolean groups through draft/application, execution, paging, hashing, Saved State, Recents, and replay. Gelbooru compiles native brace groups; Pixiv and unverified providers use bounded exact fallback branches without changing sort ownership. Codex Automatic rules now evaluate AND across groups and OR within a group in the existing like transaction, while migration keeps every legacy source recipe as one OR group. All focused host checks pass. Device interaction and visual-density acceptance remain explicitly unrun; no APK was installed and no device data was touched.

Appendix: Expression And Runtime Notes

Canonical example
groups = [[tag1], [tag2], [tag3, tag4]]; match(post) = every group contains at least one matching post term; visible(post) = match(post) and no flat exclusion matches.
Fallback execution invariant
Branch on one bounded OR group. Retain raw provider continuation per branch. Hydrate before canonical identity and remaining-group verification. Deduplicate canonical Post.id after hydration. Never infer exhaustion from filtered or malformed visible records.
