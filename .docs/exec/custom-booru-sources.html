Purpose / Big Picture

Today every source is a constant of the Kotlin enum SourceKey. That enum is the identity of a source everywhere: posts, likes, Codex items, Recents, source weights, settings, backups, credentials and the presentation catalog. A site the user types in at runtime cannot be an enum constant, so before anything else can happen, source identity has to open up.

Step 2 (this thread) turns SourceKey into an open identity type. It keeps all eleven built-in ids byte-identical (PIXIV, GELBOORU, ...) and adds a stable form for user-added sites (custom_safebooru_org). Nothing user-visible changes in step 2. The observable proof is that existing likes, Codex items, Recents, settings, offline saves and backups load exactly as before, and that data keyed by a custom id survives every store round trip even when its site is not configured.

How identity flows today

SourceKey is declared in core-domain/src/main/kotlin/com/theoriacodex/domain/model/Post.kt. Module graph: core-domain ← core-data, core-sources, core-stubs; app-logic (domain + data); core-data-android (Room); app sees everything. Every persisted form is a string, converted in Kotlin:

  • Room: entities are Java classes with String source columns (PostEntity, LikedPostEntity, CodexItemEntity, CodexAutomaticTagEntity, RecentWatchedEntity, MediaDurationEntity, …). There are no type converters, no CHECK constraints, and no SQL literals naming a source. Kotlin writes source.name and reads with SourceKey.valueOf(...). Schema version 9 on main; PR #48 makes it 10.

Identity Design

The type

// core-domain/src/main/kotlin/com/theoriacodex/domain/model/SourceKey.kt (same package, so imports are unchanged)
/**
 * Stable identity of a content source. [id] is the persisted form everywhere (Room `source` columns,
 * JSON stores, backups, credentials) and never changes for a source. Built-ins keep their historical
 * enum names; user-added sites use [CustomSourceIds] (`custom_safebooru_org`).
 */
@JvmInline
value class SourceKey private constructor(val id: String) : Comparable<SourceKey> {
    val isCustom: Boolean get() = id.startsWith(CustomSourceIds.PREFIX)

    /** Built-ins first in their historical declaration order (the old `ordinal`), then custom ids alphabetically. */
    override fun compareTo(other: SourceKey): Int = ...

    override fun toString(): String = id   // enum toString() returned the name; keep interpolations identical

    companion object {
        val PIXIV = SourceKey("PIXIV")
        val GELBOORU = SourceKey("GELBOORU")
        val AIBOORU = SourceKey("AIBOORU")
        val DANBOORU = SourceKey("DANBOORU")
        val NHENTAI = SourceKey("NHENTAI")
        val HITOMI = SourceKey("HITOMI")
        val IWARA = SourceKey("IWARA")
        val RULE34XXX = SourceKey("RULE34XXX")
        val RULE34PAHEAL = SourceKey("RULE34PAHEAL")
        val RULE34VIDEO = SourceKey("RULE34VIDEO")
        val RULE34GEN = SourceKey("RULE34GEN")

        /** Shipped sources in historical enum order. Replaces `entries` where it meant "every shipped source". */
        val builtIns: List<SourceKey> = listOf(PIXIV, GELBOORU, AIBOORU, DANBOORU, NHENTAI, HITOMI, IWARA,
            RULE34XXX, RULE34PAHEAL, RULE34VIDEO, RULE34GEN)

        /**
         * Parses a persisted id. Built-in ids match exactly (as `valueOf` did). A well-formed custom id
         * parses whether or not a profile exists, so data from a removed site is never dropped. Input
         * is trimmed, and custom ids are lowercased. Returns null for anything else.
         */
        fun parse(raw: String): SourceKey?

        /** Identity for a stored site profile; the profile's stored id is authoritative. */
        fun of(profile: SiteProfile): SourceKey
    }
}

Why a value class rather than a sealed interface (built-in enum plus custom data class):

  • Persisted bytes stay identical without new code. A non-null value-class property compiles to a JVM field of the underlying String. Gson's reflective offline manifests therefore keep writing "source":"PIXIV", and old manifests still read. A sealed interface field cannot be deserialized by Gson at all (it has no constructor), which would break offline saves.
  • Least churn. SourceKey.PIXIV keeps compiling in all 288 places and in step 1's and PR #48's new code. Implementing Comparable in the old ordinal order keeps every sorted() and compareBy { it.source } identical for built-ins.
  • Cost: a when over sources loses compiler-checked exhaustiveness. This matters less than it looks. Behavior that custom sites should share moves to explicit traits (tag dialect, family), and the remaining built-in quirks already default with else. A catalog test still forces every built-in to have a presentation.

Why id and not name: the rename makes the compiler visit every use. That surfaces the half-dozen places that show source.name to users (for example ViewerRouteWorkflow.kt:95, "${postId.source.name} is unavailable", and CreatorProfileCoordinator.kt:28), which would show custom_safebooru_org. Those switch to displayName().

Custom id derivation

// core-domain/src/main/kotlin/com/theoriacodex/domain/source/CustomSites.kt (B0)
object CustomSourceIds {
    const val PREFIX = "custom_"
    const val MAX_LENGTH = 96          // keeps "custom_<id>_<postId>.webp" cache names far below 255 bytes
    /**
     * [host] is SiteAddress.host: lowercase ASCII (IDNA), validated DNS labels. [port] is null for 443.
     * [path] is the normalized install path without a trailing '/', or "" for a root install.
     */
    fun fromAddress(host: String, port: Int?, path: String): String =
        PREFIX + host.removePrefix("www.").replace('.', '_') +
            (port?.let { "__p$it" } ?: "") +
            (if (path.isEmpty()) "" else "__h" + sha256Hex(path).take(8))
    /** `custom_` + DNS labels ([a-z0-9-], no leading/trailing '-') joined by '_', then optional `__p<digits>` and `__h<8 hex>`; at most [MAX_LENGTH]. */
    fun isValid(id: String): Boolean
    /** "custom_safebooru_org" → "safebooru.org", ignoring any `__` suffix; exact for the host since labels never contain '_'. */
    fun hostLabel(id: String): String
}

The host mapping is injective because validated host labels contain only [a-z0-9-], so _ can only come from a dot, and __ can only start a port or path suffix (labels are never empty). The 32-bit path hash is unique enough for a handful of sites per host. Built-in ids are uppercase [A-Z0-9] and custom ids are lowercase with the custom_ prefix, so the two namespaces cannot collide, even with a future built-in named CUSTOM….

Data From A Site That No Longer Exists

A custom id with no profile can come from three places: the user removed the site, a backup restored rows whose profile was removed before the backup was made, or an imported Codex share file holds posts from a site this device never added. The behavior matches today's unavailable built-ins (credential-gated Rule34.xxx):

  • Parsing never drops it. SourceKey.parse accepts any well-formed custom id. Room rows, JSON entries and backup rows load.
  • Presentation falls back. SourcePresentationCatalog.presentation(key) returns the installed profile's entry. When there is none, it returns a fallback: label CustomSourceIds.hostLabel(id) ("safebooru.org"), Referer https://<host>/, the browser User-Agent, group CUSTOM, a text logo, and a mark from the first letter of the host. It never throws for a custom id.
  • Registry says unavailable. No adapter means it is absent from availableSources(), so it is hidden from the Search source picker. It is removed from Unified and For You by their existing enabledSources ∩ availableSources intersection.
  • Library keeps showing it. Likes, Codex, Recents and statistics render from stored post snapshots, as they do for credential-less R34X. Evidence rules (step 3): a Match must rest on protocol evidence that also exists on an empty or restricted site. For example, Danbooru answers /counts/posts.json with {"counts":{"posts":N}}, and Gelbooru 0.2 answers the DAPI without json=1 with a <posts count="N" …> XML envelope. A readable post is then a second, optional check. Requiring a parsed post is wrong: the Danbooru parser returns null for restricted posts that lack file_url (DanbooruSourceAdapter.kt:163). Before freezing fingerprints, step 3 captures JSON and XML fixtures from danbooru.donmai.us, aibooru.online, safebooru.org, gelbooru.com, rule34.xxx and sakugabooru.com (Moebooru), plus one ordinary HTML site, using host curl on metadata endpoints only, and commits them under core-sources/src/test/resources/custom-sites/.

Probe algorithm (SiteProber, step 3):

  1. Parse the address. Built-in hosts come from the family presets (DanbooruSite.DANBOORU, DanbooruSite.AIBOORU and step 1's Gelbooru presets) and give AlreadyBuiltIn.
  2. Try each supported family in registry order, Danbooru then Gelbooru 0.2, using that family's evidence requests from the rules above. The first Match wins. Requests go out anonymously first; if a family answers NeedsCredentials and the caller supplied credentials, it is retried once with them, and a match then yields Supported(credentialsRequired = true). Without credentials, NeedsCredentials is remembered as the fallback answer.
  3. Otherwise check unsupported signatures and return UnsupportedFamily. Otherwise return CredentialsRequired if remembered. Return NotABooru only when every attempt got a well-formed HTTP answer that matched nothing; if any attempt failed at the transport level, the probe was inconclusive, so return Unreachable with that failure.
  4. Bounds: 10 s per request and a 30 s total deadline, at most 6 requests, no retries, no writes, nothing persisted. This needs the custom-site transport in C7. A probe never changes a stored profile. Re-test keeps the stored family and reports a mismatch without switching; to switch, remove and re-add the site, which reuses the same id.
  5. Outcome table: protocol envelope or readable post → Supported. Recognized protocol refusing access (401/403 with the family's auth wording) → CredentialsRequired (rejected = true when supplied keys failed). Unsupported signature → UnsupportedFamily. HTML challenge or interstitial (403/503 with an HTML body) → Unreachable(BLOCKED). Well-formed answers matching nothing → NotABooru. Any transport failure and no match → Unreachable(reason). Step 3 confirms each row against the captured fixtures before the B0 enum values are considered final; adding a ProbeFailure value is a plan update.
  6. Term limit: the family default unless the probe measures one (Danbooru-family guests: 2, with ranked sorts using a term, as for DanbooruSite.DANBOORU; Gelbooru 0.2: none).

Before B1 merges, step 3 can build and test the probe on fixtures alone. After B1, when the site has a readable post, the probe also runs the family adapter's parser with the would-be SourceKey, so "locked in" means the real adapter can read the site.

C7. HTTPS-only policy (step 3)

  • Input must be HTTPS. A schemeless input becomes HTTPS, and http:// is rejected before any request.
  • API redirects may only go HTTPS→HTTPS on the same host. Anything else is INSECURE_REDIRECT or CROSS_HOST_REDIRECT on a probe, and a request failure in the adapter. This keeps query-string API keys from leaking to another host.
  • Enforcement needs its own transport. DefaultSourceHttpClient sets instanceFollowRedirects = true (DefaultSourceHttpClient.kt:159), retries, uses a 20 s read timeout, and SourceHttpResponse exposes no final URL. So a wrapper cannot stop a redirect that has already been followed. Step 3 adds a custom-site client in core-sources/.../custom/ that implements SourceHttpClient with redirects off, follows at most 3 hops only when they pass the rule above, never retries probes, and honors the probe deadline. Both the probe and custom-site adapters use it. Tests run against local controlled endpoints and prove that a rejected redirect is never requested.
  • Media URLs that are protocol-relative (//cdn…) or http:// are rewritten to https://. No cleartext fallback.
  • Only User-Agent and Referer can be customized. Arbitrary headers are out of scope.

Surprises And Discoveries

  • Room already stores the source as plain TEXT, converted in Kotlin. There are no type converters, CHECK constraints or SQL literals, so opening identity needs no schema change. Evidence: the *Entity.java files and DAO queries in core-data-android/src/main/java/com/theoriacodex/data/android/room/.
  • Offline manifests serialize the domain Post reflectively with Gson (OfflineMediaStore.kt:258 and :235). A value class keeps "source":"PIXIV"; a sealed type could not be deserialized. Related, unverified and out of scope: app/proguard-rules.pro has no keep rule for com.theoriacodex.domain.model.Post, so in minified builds those manifests may use obfuscated field names that change between releases. Recommended as a separate follow-up after checking a release mapping file.
  • The Viewer restoration format "$source:$postId" is decoded with split(':', limit = 2) (ViewerRestoration.kt:24-31). Named covers are matched by the prefix "${name}_${source}." (CodexCover.kt:58-70), and thumbnails are files named "${source}_${postId}" (FileBackedCacheRepository.kt:134). These shaped the custom id alphabet (D2).
  • RepositoryPolicies.normalizeSourceWeights orders by SourceKey.entries and falls back to a raw weight of 1.0. Left as is, a custom source would be dropped silently, or, once fixed, would take about half the mix.
  • Two strict readers, RoomRecentsRepository.kt:65 (observeWatchedPostIds) and RoomProfileBackupStore.kt, call bare valueOf. Older builds would throw on custom rows (D8).
  • TagCountCoordinator and SearchTermCountCoordinator prebuild per-source mutex maps, and getValue would throw for a custom key.
  • One runtime.enabledSources set drives both Unified (UnifiedSourceSettings.kt) and For You (ForYouCoordinator.availableSources), which gives D4.
  • AvailabilityAwareSourceAdapterRegistry intersects with the account store's built-in set, so custom adapters must be composed outside it (C4).
  • (Review round 1) SourceDependencies.availableSources is a second availability channel. SettingsViewModel.kt:270 intersects every Unified-selection save with it, so a built-in-only flow would erase custom opt-ins (C4).
  • (Review round 1) DefaultSourceHttpClient follows redirects internally (DefaultSourceHttpClient.kt:159), and responses carry no final URL, so the HTTPS/same-host policy needs its own transport (C7).
  • (Review round 1) presentation() lives in app. app-logic and core-data cannot read it, so family behavior had to move to adapter capabilities (category 3).
  • (Review round 1) Local main moved to 1ac37a9d with PR #48 merged (Room schema 10). Step 1 has commits that already satisfy D10.
  • (Review round 2) Ignoring path and port in ids made a real corruption path. SharedPostPayloadWriter.kt:17-32 upserts the shared post payload by (source, post id), so a different booru under a reused id would overwrite stored snapshots of old likes. This led to endpoint-derived ids and explicit reconnection (D2).
  • (B0) GsonWireContractTest was already failing on main. Idempotence And Recovery

  • Commands: every validation command is read-only against data and safe to rerun. Gradle outputs land in build/. Prune build/reports/ after B5.
  • Partial B1: the swap is atomic. If interrupted, the tree will not compile. Resume by working through the compiler errors with the migration rules, or discard uncommitted work (git restore -SW . inside this worktree only) and restart B1 from B0's commit. Never use bare git stash (the stash is shared across worktrees).
  • Reverting step 2: safe before step 3 ships custom sites to any device, because no custom-keyed data can exist yet. After that, revert is unsupported (D8). Fix forward.
  • Destructive actions: none planned. No data is migrated, rewritten or deleted. Removing a site (step 3/4) deletes only its profile, its credentials and its opt-in; library rows stay. Clearing data on any device needs explicit authorization for that exact action.
  • Backups: the v2 body is the v1 body plus an optional field, and readers accept both versions. A restore is journaled, capacity is checked before the journal is written, and profile merging is idempotent by sourceId, so repeating or recovering a restore adds nothing twice.
