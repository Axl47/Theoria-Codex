Clean a Codex using other Codices

Remove from one collection the posts also saved in any selected comparison collection. Sources retain every membership. Likes is a valid target and cleaning it also unlikes the matches.

Context and purpose

A membership is a saved canonical PostId (provider plus provider ID) in a Codex. The union of comparison memberships is subtracted from the target. The existing collection sheet in app/src/main/java/com/theoriacodex/app/codex/CodexListScreen.kt supplies the target. CodexListRoute.kt and CodexListUiState.kt connect selection to the shell. CodexCommandViewModel.kt retains mutations and acknowledged Retry/Undo. Room owns memberships and Likes together through core-data/src/main/kotlin/com/theoriacodex/data/repository/Repositories.kt and core-data-android/src/main/kotlin/com/theoriacodex/data/android/room/RoomCodexLikesRepository.kt.

Decisions

User explicitly requested Likes as a valid cleaning target, including unliking matches. Use the existing target collection action sheet to avoid adding another Library toolbar action. Provide exact Undo using the existing retained command owner. Perform no remote Like mutation.

Discoveries

Ordinary membership removal does not change Likes; cleaning must use CodexLikesTransactions so both commit atomically. Existing restoreItems retains original timestamps and skips newer memberships; cleaning Undo must preserve that behavior for Likes as well.

Idempotence and recovery

Repeated cleaning has no additional effect once overlap is removed. Cancellation before transaction commit rolls back. Retry retains captured target/profile/source IDs. Undo restores only removed rows and must fail safely if the target was deleted. Do not recreate a deleted target or profile. Keep the unrelated modified production-to-debug-copy plan untouched. No schema migration is required.
