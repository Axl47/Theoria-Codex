ExecPlan: Keyed Custom Site Access

Purpose / Big Picture

A friend added a Danbooru fork that challenges anonymous requests but lets accounts through. The site looked fine, then answered "Access denied" after a little browsing. Removing it and adding it again with the correct key did not help. After this work:

  • Adding, re-testing or browser-checking a site with a key uses that key first, so the key gets its chance even when anonymous access is closed.
  • A wrong key is reported at the moment it is entered.
  • A site that only let the app in after a browser check shows the API key fields before it is saved.
  • An account refusal in search, in a re-test or from a shared post offers a button that opens that site's page with its API key section open.
  • Saving a key clears any "site is down" mark and re-tests with the key.
  • A site with a saved key is not marked down by an anonymous launch request, and its images and videos can use the key when the site refuses them.

Context And Orientation

Terms. A probe is the bounded set of read-only requests that identifies which booru API a site speaks. A family is one such API, Danbooru or Gelbooru 0.2. An outage is an in-memory, 10-minute "this host is down" mark that makes requests fail without touching the network. A browser check is the in-app WebView page where a person passes a site's challenge; its cookies then reach the app's requests through the cookie bridge.

Phases

Phase 1: Key-first probe

With keys, SiteProber probes families with the keys first. A saved site names its family, which is tried first, and no anonymous request is made. Only adding a site makes one extra anonymous probe after a keyed match, to learn whether the site can work without keys. Acceptance: anonymous HTML refusal with a working key is Supported; a refused key on an open site is CredentialsRequired(rejected = true).

Phase 2: Stale marks and anonymous background traffic

Adding a site and changing its keys clear its outage. Sites with saved keys skip the anonymous launch check. Connection warm-up skips hosts that share browser identity, because it used a hard-coded agent with those cookies. Acceptance: controller and client tests.

Phase 3: Key entry where it is needed

New SitesRequest.EnterKey opens a site's page with the API key section open. Re-test failures, the Confirm step after a browser check, search failures, source chips and shared-link failures all lead there. Editing keys on the Confirm step sends the form back to Check site, so what is saved was tested. Acceptance: ViewModel, copy and failure tests.

Phase 4: Shared posts and media

A Danbooru post hidden from this identity becomes an account failure rather than "not found". Image, video and download requests refused on a Danbooru site's own host retry once with the key in an HTTP Basic header, and later requests to that host send it at once. Acceptance: client tests prove same-site only, HTTPS only, one retry.

Surprises And Discoveries

  • Observation: the anonymous-first probe saved keys it had never tested. Evidence: the old probeFamilies returned on the first anonymous match.
  • Observation: an HTML refusal never triggered a keyed attempt. Evidence: ProbeEvidenceTest pins an "Access denied" page as BLOCKED, and only NeedsCredentials led to keys.
  • Observation: Chrome denied the friend logged out on Wi-Fi and mobile data, so the refusal does not come from app state or one IP.

Decision Log

  • Decision: keep one anonymous probe, only when adding a keyed site. Rationale: credentialsRequired must stay accurate, or an open site would become unusable once its key is removed or absent after a restore. Date/Author: 2026-11-10 / Claude.
  • Decision: media gets the key only after a refusal, by HTTP Basic, on the site's own HTTPS hosts. Rationale: no evidence yet that media needs it, so working sites keep exactly their current requests, and an added header can stop CDNs caching. Date/Author: 2026-11-10 / Claude.
  • Decision: one message for rejected keys that also names account access. Rationale: a 401 bad key and a 403 not-permitted key need the same action from the person. Date/Author: 2026-11-10 / Claude.
