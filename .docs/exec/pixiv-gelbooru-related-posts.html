ExecPlan: Surface Related Posts After Likes

After a successful local Like on a Pixiv or Gelbooru card in Search or For You, Theoria Codex will reveal one contextual, dismissible “More like this” shelf without mixing provider-related posts into the canonical feed. The shelf will preserve provider ordering, Search scroll restoration, FYP pagination, Viewer ownership, duration enrichment, and the rule that provider requests never become remote bookmarks or durable FYP searches.

Purpose / Big Picture

A person browsing Search or For You can already Like a post, which records that choice locally for the active recommendation profile and synchronizes the system Likes Codex. This change makes that moment immediately useful: liking an eligible Pixiv or Gelbooru post reveals a small provider-native discovery shelf next to the post instead of waiting for a later global recommendation refresh.

The completed behavior is visible without opening a post. Tap the heart on a Pixiv or Gelbooru feed card, keep the current feed and scroll position, and observe a loading shelf become an ordered row of related cards. The row supports ordinary card actions and a static Viewer stream. Liking a card in the shelf continues discovery in the same location. Dismissing, unliking the current seed, replacing the root feed, changing profile, or restarting the process removes the transient shelf without changing the Like that already committed.

Product decision: a non-empty FYP feed no longer reruns its root generation solely because the active profile’s Like count changed. The new shelf is the immediate reaction. Newly recorded Likes train the next explicit refresh, shuffle, source/sort change, replay, or other legitimate root generation.
Non-goal: this feature does not bookmark or favorite anything on Pixiv or Gelbooru. The only provider mutations remain none; related retrieval is read-only and the existing Like remains local.

Context And Orientation

Terms

Canonical feed
The authoritative ordered List<Post> produced by Search or FYP root/pagination work. Provider-related posts never enter this list.
Seed
The Pixiv or Gelbooru post whose successful transition to Liked started the related request.
Related shelf
One transient full-line grid section containing loading, loaded, empty, or retry presentation for the active seed.
Presentation projection
A platform-free mapping from canonical visible posts plus one shelf into lazy-grid entries. It retains each post’s canonical index so UI-only insertion cannot corrupt paging, Viewer order, or Search scroll persistence.
Latest-wins request
A request identified by a monotonically increasing generation. A later seed, unlike, dismissal, root replacement, or owner teardown cancels or invalidates older responses.

Required Behavior

Successful Like

  1. The app shell completes the existing atomic local Like and Likes-Codex synchronization.
  2. If the committed outcome is LIKED and the post’s available adapter implements RelatedPostsSourceAdapter, the exact route owner receives RelatedLikeCommitted.
  3. The route replaces any older shelf with Loading(seed, anchorCanonicalIndex, generation) and starts one request.
  4. The adapter returns at most six fully usable, same-source posts in provider order.
  5. The route removes the seed, duplicate IDs, and IDs already present in the canonical feed without reordering survivors.
  6. The shelf becomes Loaded. If no new posts survive, show a compact “No new related posts” state with Dismiss; do not fabricate tag-based results.

Shelf placement and continued discovery

  • If the seed is visible, insert one full-line shelf immediately after it.
  • If Search’s Hide liked filter removes the seed, insert after the nearest still-visible post whose canonical index precedes the seed. If none exists, insert before the first visible post.
  • Liking a supported card inside the shelf reuses the shelf’s original canonical anchor and replaces its contents; shelves never nest.
  • Liking an unsupported-source canonical card does not start a request and does not relabel or move an existing supported shelf.
  • Only the latest supported seed is active. Dismissal hides the shelf but does not Unlike anything.

Clear and retention rules

Page appendRetain if its seed/generation is still current.Append normally; related IDs remain outside pagination.

Unlike active seedCancel/clear immediately after committed UNLIKED.Unchanged except ordinary Like visibility.
New Search root, Retry replacement, historical query, or applied tag searchClear before root work.Replace through existing Search state flow.
FYP refresh, shuffle, source/sort/profile change, replay, or seed blacklistClear before root work.Replace through existing FYP flow.
FYP Like count changes while results are non-emptyOutcome action may update the shelf.Do not start a count-only root refresh.
FYP Like count reaches zeroClear.Preserve current behavior: cancel work and clear the feed.
Route owner survives tab switch/re-entryRetain in memory.Unchanged.
Owner clear or process restartDiscard; do not restore.Existing durable Search/FYP restoration remains authoritative.

Failures

  • A failed Like commit emits no related request and leaves observer-backed Like state authoritative.
  • A provider authentication, rate-limit, network, parse, or all-hydration failure produces an inline retry state. It never rolls back a committed Like and never replaces the route’s primary error.
  • Partial Gelbooru hydration keeps successful posts in original order. If all candidates fail, treat the request as failed rather than as a truthful empty recommendation set.
  • Cancellation must propagate. A stale provider response cannot reopen a dismissed shelf, replace a newer seed, cross a profile/query boundary, or mutate canonical results.

Provider capability

Add this bounded operational interface to SourceAdapter.kt:

interface RelatedPostsSourceAdapter {
    suspend fun relatedPosts(seed: PostId, limit: Int): List<Post>
}

The loader checks the runtime adapter type through the availability-aware registry. Do not add supportsRelatedPosts to SourceCapabilities and do not hard-code Pixiv/Gelbooru in Search or FYP UI. Clamp the requested limit to 1..6, reject cross-source output, preserve adapter order, and let cancellation escape.

Pixiv implementation

  • Issue an authorized GET to https://app-api.pixiv.net/v2/illust/related with illust_id and the same Android filter convention as existing calls.
  • Use the adapter’s existing throttle, token refresh, HTTP failure mapping, and parseIllust.
  • Read only the first response and take the bounded prefix after parsing. Do not parse or persist next_url; Pixiv continuation carries repeated viewed/seed parameters that a Map<String, String> cannot represent faithfully and the UX does not require pagination.

Gelbooru implementation

  1. Fetch https://gelbooru.com/index.php?page=post&s=view&id=<seed> as a read-only text request.
  2. Parse with a new pure GelbooruRelatedPostsParser. Locate the exact “More Like This” heading, scope to its containing block, extract only post-view links, normalize ordered numeric IDs, remove duplicates/seed, and apply the limit.
  3. Hydrate those IDs through GelbooruSourceAdapter.resolvePost with at most two requests in flight. Use a supervisor boundary so one malformed/deleted post does not discard healthy peers, while preserving cancellation and original order.
  4. Publish only hydrated posts so cards have authoritative animation/media identity and participate correctly in autoplay, duration enrichment, Viewer, Likes training tags, and post actions.
Gelbooru fragility: the HTML block is an undocumented beta surface. Keep all selectors and URL parsing in the source-owned pure parser, cover image/video/deleted/missing-block fragments, add a live health step, and never let app-layer code know Gelbooru markup.

Shared route state

Create platform-free state and reduction helpers in app-logic/src/main/kotlin/com/theoriacodex/app/related/. Use one discriminated state with seed Post, original anchor, generation, and loaded posts:

Idle
Loading(request)
Loaded(request, posts)
Failed(request, userMessage)
Empty(request)

Both Search and FYP embed this state. Their ViewModels own a single related request Job and monotonically increasing generation. The application-scoped RelatedPostsLoader owns registry routing and output validation but no UI state, durable storage, or unbounded cache. A small in-memory LRU may be added only if live measurement shows repeated relikes cause unnecessary requests; it is not part of the first pass.

Typed Like outcome and owner handoff

Replace Boolean interpretation at the app-shell boundary with LikeToggleOutcome.LIKED and LikeToggleOutcome.UNLIKED. Keep LikesCodexSyncService as the atomic transaction owner. For each Search/FYP grid callback, capture that route’s current weak owner handle before launching the shell coroutine. After a successful commit, dispatch the outcome to that captured handle. If the owner was cleared, the lease rejects delivery and the Like remains valid without creating orphan UI work.

Viewer, Creator, Recents, and Codex Like callbacks may ignore the returned outcome because this feature is intentionally limited to Search and FYP grids.

Grid projection and canonical indices

Create RelatedFeedProjection in app-logic with PostEntry(post, canonicalIndex) and ShelfEntry(state, anchorCanonicalIndex). Search/FYP screens build it after ordinary visibility filtering. Add a projected entry point in PostStaggeredGrid.kt backed by the same private two-column implementation; leave the existing post-only function and the other three feed call sites intact.

  • Grid keys are post:<source>:<id> and related:<source>:<seed-id>.
  • The shelf uses StaggeredGridItemSpan.FullLine and a horizontal row of bounded cards with an explicit heading, source label, Dismiss, and Retry where applicable.
  • Main-card Viewer launches use PostEntry.canonicalIndex, never the lazy-grid index.
  • Paging uses the greatest visible PostEntry.canonicalIndex; a visible shelf alone cannot trigger a page.
  • Search persists/restores canonical post indices. When the first visible entry is the shelf, persist the nearest preceding post index with offset zero; if none exists, persist index zero. Restore by translating the stored canonical index into the current projected grid index.

Media and Viewer integration

  • Render loaded recommendations with SearchResultCard so visible video/animated cards retain stable-visibility gating, pooled playback, action behavior, and duration publication.
  • Pass the distinct canonical-plus-related post union to each rememberMediaDurationRouteBinding without changing the root query/seed content identity. Related additions are content reconciliation, not a new route identity.
  • Add ViewerStreamSource.RELATED. It has no live route snapshot, no load-more owner, no durable source-list restoration, and maps to ordinary Watched Recents through the existing default section policy.
  • Open a shelf card with queryHash = "related:<source>:<seed-id>", only the shelf’s visible ordered posts, and liveSearchBinding = false. A process-death restoration attempt for this transient stream returns unavailable rather than substituting current Search/FYP results.
  • A related request is not a Search execution or accepted FYP root generation. It must not write applied queries, Search scroll records beyond canonical position, recent searches, FYP search history, or FYP source statuses.

Surprises And Discoveries

  • Observation: Gelbooru’s visible “Similar” link is a SauceNAO reverse-image lookup, while the desired recommendations are a separate server-rendered “More Like This” block. Evidence: live post-page DOM inspected 2026-09-02.
  • Observation: Gelbooru’s public post API documentation has no related operation, so the feature needs one HTML discovery request plus bounded post hydration. Evidence: howto:api and current GelbooruSourceAdapter.
  • Observation: Pixiv related continuation includes repeated seed/viewed parameters, but the app HTTP abstraction accepts a string map. Consequence: first bounded response only; no lossy token encoding.
  • Observation: Search persists raw lazy-grid indices and FYP/Search compare lazy-grid indices to post counts. Consequence: inserting a shelf without canonical translation would cause restoration drift and premature paging.
  • Observation: FYP currently refreshes whenever activeProfileLikesCount changes. Consequence: preserving an inline seed shelf requires the approved count-only refresh behavior change.
  • Observation: the first complete diff exceeded frozen Search screen/ViewModel budgets because request and presentation logic existed in both routes. Consequence: one shared RelatedPostsRouteController and one shared related-feed presentation owner now keep both routes under the hotspot gate.
  • Observation: repository-wide core Detekt is red on pre-existing oversized owners unrelated to this feature. Evidence: app/app-logic Detekt passes and no new related file appears in core findings; the hotspot debt-exact gate passes.
  • Observation: keying scroll collection on the related projection caused Loading/Loaded changes to emit without user scrolling; a shelf-first viewport then mapped to the liked seed at offset zero and overwrote Saved State before Viewer return. Consequence: shelf rows now produce no persistable position and projection updates flow through rememberUpdatedState without restarting the collector.
  • Observation: provider connect/read timeouts and retries could hold the shelf in Loading far longer than the interaction allows. Consequence: the shared route controller owns one 15-second overall deadline and publishes the existing retryable failure message.

Decision Log

  • Decision: Keep related posts outside canonical Search/FYP results. Rationale: protects provider ordering, continuation, Viewer indices, Search restoration, and FYP history. Date/Author: 2026-09-02 / Developer and Codex.
  • Decision: Show one full-line shelf anchored to the latest supported Like; related Likes replace it in place. Rationale: immediate context without recursive feeds or multiple network-heavy shelves. Date/Author: 2026-09-02 / Developer and Codex.
  • Decision: Do not regenerate a non-empty FYP feed for count-only Like changes. Rationale: keeps the user’s position stable while the shelf provides immediate discovery; next legitimate root generation still trains from all Likes. Date/Author: 2026-09-02 / Developer and Codex.
  • Decision: Use an optional adapter interface instead of source flags/UI checks. Rationale: matches existing operational-capability patterns and keeps provider details source-owned. Date/Author: 2026-09-02 / Codex.
  • Decision: Parse Gelbooru’s native HTML block and never relabel tag overlap as native similarity. Rationale: preserves truthful product language and provider ordering despite the documented fragility. Date/Author: 2026-09-02 / Codex.
  • Decision: Add a static RELATED Viewer source. Rationale: prevents process restoration or live binding from substituting canonical Search/FYP results for an ephemeral shelf stream. Date/Author: 2026-09-02 / Codex.
