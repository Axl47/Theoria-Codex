Purpose / Big Picture

Duration badges and duration filtering should become progressively useful without making scrolling, preview startup, or simultaneous autoplay feel slower. A Hitomi post with directly available authoritative video must not need a Viewer round trip before its duration appears. Static posts and unresolved animated posts must not leak into a narrowed duration range. Opening and closing Viewer must not make duration metadata disappear and then reappear.

When this plan is complete, duration information comes from the cheapest authoritative source available: provider metadata, a player that is already decoding the full media, a bounded persistent cache, or a low-priority bounded container parser. Unsupported media settles once instead of repeatedly triggering full provider hydration. Routes request metadata; they do not own independent resolution loops or rewrite their complete post lists whenever one badge changes.

Scope: rebuild the duration metadata subsystem, not the feed, navigation, source registry, or autoplay policy. Existing shared cards, stable player ownership, viewport/lifecycle activation, protected request headers, and concurrent visible-card autoplay remain.

Context And Orientation

An authoritative media reference points at the complete post media whose duration is being described; a looping preview clip is not authoritative. A duration decision is one of Pending, Known, Unsupported, or Retryable Failure. A media fingerprint is a stable non-secret identity derived from the post ID plus normalized authoritative media identity; it prevents an old duration from being reused when a provider changes the media. A demand ticket says which route wants a duration, why, and at what priority. A single-flight job lets multiple routes share one acquisition for the same fingerprint.

unknown animated results
  -> composable requests enrichment
  -> route scans the complete feed
  -> up to 8 child jobs / 3 application workers
  -> each worker resolves full provider detail first
  -> separate remote MediaMetadataRetriever work
  -> route copies/publishes posts with durations
  -> result-list effect requests enrichment again
  -> active filter hides unresolved rows
  -> small visible result count loads another page
  -> more unknown results enter the same loop

Product and safety constraints

  • Every visibly presented animated or video card continues autoplaying simultaneously. Do not introduce a single-active-card policy.
  • Never measure a preview-only clip and call it the post duration.
  • Do not rewrite durable Codex post snapshots with acquired duration metadata. Duration storage is independent.
  • Preserve source-specific headers and URL normalization at the Android/application boundary.
  • Provider metadata and raw provider pagination remain authoritative; duration visibility never decides whether a provider page is exhausted.
  • app-logic remains platform-free and owns pure classification, acquisition planning, demand scheduling, and filter-readiness policy.
  • Physical benchmark work targets only com.theoriacodex.benchmark. Debug acceptance targets only com.theoriacodex.debug. The production package com.theoriacodex is never installed over, cleared, downgraded, uninstalled, or benchmarked.
  • The Macrobenchmark runner must not configure SideEffectRunListener or mutate unrelated packages.

State contract

Add platform-free types under app-logic/src/main/kotlin/com/theoriacodex/app/media/:

  • MediaDurationKey(postId, mediaFingerprint).
  • MediaDurationState.Pending, Known(durationMs, provenance), Unsupported(reason), and RetryableFailure(retryAtEpochMs, reason).
  • MediaDurationProvenance.PROVIDER, ACTIVE_PLAYER, and CONTAINER_PROBE.
  • DurationDemand(identity, key, priority, reason), where priorities are Active Filter, Visible, Near Viewport, and Background Idle.
  • DurationAcquisitionPlan.AlreadyKnown, UsePersisted, AskProvider, ProbeAuthoritativeMedia, or Unsupported.

Pending is process state, not a durable record. Known and Unsupported decisions persist by fingerprint. Retryable failures may persist only until their bounded retry time. A fingerprint change makes the old row irrelevant without destructive migration.

Acquisition order

  1. Use valid Post.durationMs and record provider provenance.
  2. Use a matching durable Known or Unsupported record.
  3. Accept an authoritative duration already reported by the visible feed player, Viewer, Ugoira player, GIF decoder, or animated-WebP decoder.
  4. If the sparse post already contains authoritative full video, probe it directly; never call full resolvePost first.
  5. Ask a source that implements the optional DurationMetadataSourceAdapter for Known, Authoritative Media, Unsupported, or Retryable Failure. The generic coordinator must not hydrate an entire post as a duration fallback.
  6. Probe only authoritative full media using the bounded container parser. Unknown or preview-only media settles Unsupported rather than invoking a broad resolver.

Background setting semantics

resolveUnknownAnimatedDurations becomes the permission to perform speculative background provider/probe work while browsing. Provider durations already present on posts, durable hits, and authoritative active-player events are always accepted because they add no extra fetch. An explicitly narrowed duration filter is direct user demand and may resolve the currently loaded page even when speculative background resolution is disabled.

New or missing settings records default speculative background resolution to false; explicit stored true or false values remain authoritative. When enabled, routes enqueue unknowns as soon as they arrive, but Background Idle work yields to visible playback, active filtering, lifecycle stop, and active scrolling.

Durable cache contract

Add an independent Room table rather than a foreign key to posts, because ordinary Search results may never become Codex or Recents rows. Use a composite primary key of source, source post ID, and media fingerprint. Store status, positive duration when Known, provenance, observed time, and optional retry time. Cap the table at 4,096 records and prune least-recently-observed rows in the same serialized repository write path. Never store credential-bearing URLs or request headers.

Probe contract

Retire remote MediaMetadataRetriever.setDataSource(url, headers). Add pure parsers with fixture tests for MP4/ISO-BMFF and WebM metadata, and use SourceHttpClient.getBytes with request-scoped headers. Read at most 256 KiB from the head and, only when required and supported by Content-Range metadata, 256 KiB from the tail. One probe worker may run at a time. Wrap the complete operation in a 12-second timeout; the HTTP client retains its lower-level cancellation/disconnect behavior. Do not create a hidden ExoPlayer solely to obtain duration.

GIF and animated-WebP duration may be published from an already completed authoritative full-media decode. Do not add a second full download solely for an image duration in this plan. A source whose only animated reference is a preview or gallery cover settles Unsupported.

Metric comparison contract

Use the same device and OS whenever possible. If either changes, report the run but do not claim a direct speed comparison. For each run compute:

CPU penalty p90 = duration-on Search frameDurationCpuMs p90
                  - autoplay-control Search frameDurationCpuMs p90

Overrun penalty p90 = duration-on Search frameOverrunMs p90
                      - autoplay-control Search frameOverrunMs p90

The final run is accepted when all correctness invariants pass and:

  • If the baseline CPU penalty exceeds 1.0 ms, the final penalty is at least 30% smaller. If the baseline penalty is 1.0 ms or less, the final penalty does not regress by more than 0.5 ms.
  • Final duration-on p90 frame CPU and p90 frame overrun are both no worse than their baseline duration-on values.
  • Preview prepare and media-load counts do not increase due to duration publication; first-frame counts do not decrease.
  • Every iteration settles all 24 duration decisions and keeps at least two simultaneously visible previews playing.
  • Provider resolve/probe counts are no higher than baseline, and Unsupported decisions do not perform provider hydration or probe work.
  • If a threshold misses, inspect the preserved traces, identify the common cause, patch once, and rerun the affected host checks. A second physical run requires recording why the first final run was invalid or insufficient; do not silently cherry-pick a favorable sample.

Surprises And Discoveries

  • Observation: the existing Macrobenchmark cannot see this regression because every fixture post starts with a known duration. Evidence: BenchmarkFixtureActivity.benchmarkPosts assigns BENCHMARK_MEDIA_DURATION_MS.
  • Observation: player instances are remembered by media location/source, so duration-only Post replacement does not directly recreate ExoPlayer. Evidence: rememberFeedPreviewPlayerState uses remember(location, sourceKey). Contention and feed-state churn are the primary suspects.
  • Observation: the current lane collects the full unknown candidate set with Int.MAX_VALUE, launches batches of eight, and the application service permits three concurrent workers.
  • Observation: AnimatedDurationEnrichmentService.compute resolves provider detail before inspecting directly available full media.
  • Observation: Hitomi non-anime full resolution can resolve every gallery file, while the current duration probe accepts video only. Animated WebP work may therefore end in a negative decision after substantial useless work.
  • Observation: Search, For You, and Creator duration filtering can load another provider page because unresolved posts are hidden and the visible result count looks too small.
  • Observation: Viewer already reads ExoPlayer duration, and Ugoira/GIF/WebP players have local timing knowledge, but none publishes authoritative duration to shared feed metadata.
  • Observation: Macrobenchmark reuses an interaction fixture activity across iterations unless the fixture intent explicitly clears its isolated task. The first attempt therefore saw a prior Settled 24/24 state during setup. Evidence: the failed attempt is preserved under failed-8ca9ecd-20260810T0950Z; commit 6bd7536 freezes FLAG_ACTIVITY_NEW_TASK | FLAG_ACTIVITY_CLEAR_TASK and the subsequent full run passed.
  • Observation: the offline baseline shows no aggregate p90 frame penalty after within-run control normalization (-0.082 ms CPU, -0.037 ms overrun), while still proving the old system performs 24 resolves, 24 native probes, and three whole-list publications. Interpretation: the final gate uses the plan's low-penalty no-regression threshold plus workload/count/correctness evidence; it must not claim a 30% frame-penalty reduction from this baseline.
  • Observation: Hitomi's sparse anime result already carries its canonical MP4, while a sparse animated-WebP gallery carries only a cover and media count. The shared planner can therefore probe anime directly and settle galleries unsupported without any Hitomi-specific full-post hydration.
  • Observation: a single total acquisition permit is a safe strict bound for the transitional coordinator adapter: it implies at most one probe and one provider request while route migration is incomplete. Phase 3 will move provider/probe classification behind the durable acquisition engine without loosening the probe bound.
  • Observation: the repository module cannot import the application-owned duration state without creating a dependency cycle. The durable contract therefore owns a smaller Pending-free stored state and the app owns the exhaustive typed mapping at the coordinator boundary.
  • Observation: a range response is safe for metadata parsing only when its Content-Range, body length, and known total length agree with the requested window. Treating a server's silent full-body fallback as success would defeat the memory/network budget.
  • Observation: continuous Viewer timeline callbacks are not a safe duration-publication seam: GIF progress runs at frame cadence and would enqueue unchanged metadata repeatedly. Duration publication now occurs once when each authoritative player's total duration becomes known.
  • Observation: pagination effects must key the pending-decision count itself. A page that settles entirely Unsupported or outside the selected range does not change the visible result count, so keying only visible/base list sizes would leave refill permanently paused.
  • Observation: the final connected benchmark task graph can be inspected without touching a device. Its successful dry run schedules the isolated benchmark APK, :app:verifyBenchmarkReleaseInstallableApplicationId, the runner APK, and only then :macrobenchmark:connectedBenchmarkReleaseAndroidTest.
  • Observation: cached metadata prevented network reacquisition but did not make the presentation path cheap. onPostVisibilityChanged still launched main-thread synchronizeDemand(), which rebuilt candidates, recalculated SHA-256 keys, and reconciled every lane for every enter/exit event, even when background resolution and filtering were off. Reconstructed players could also publish an already-Known value and force route-map churn.

Phase 0 froze and preserved the physical benchmark. Phases 1 through 4 rebuilt bounded acquisition, scheduling, persistence, parsing, and route integration. Idempotence And Recovery

  • Host tests, compilation, static analysis, and packaged-artifact verification are safe to rerun.
  • Never delete a connected benchmark output directory before preserving and hashing it. Move it into a uniquely named build/reports/duration-metadata-performance/ directory.
  • If Phase 0 instrumentation fails before producing iterations, repair only benchmark code and rerun. If it produces partial artifacts, preserve them as failed-run evidence before retrying.
  • If any duration behavior changes before the baseline, capture a new baseline at the last pre-fix commit or revert only this task's uncommitted behavior changes with a reviewed patch. Do not use git reset --hard or discard unrelated user work.
  • Room migration is forward-only. Test 4-to-5 with exported schemas before any device install. Do not use destructive migration fallback, clear app data, or uninstall as a repair.
  • The coordinator rollout is reversible route by route while the old service still exists. Do not delete the old lane/service until every production consumer and architecture test has moved.
  • Parser failures return typed Unsupported or Retryable results and must never fail feed loading. A parser can be disabled independently while provider/cache/player acquisition continues.
  • If the same physical device or OS is unavailable for the final run, preserve the final artifacts but label the numeric comparison non-equivalent. Do not normalize across different devices and claim improvement.
  • No phase authorizes push, tag, release, production-package install, production data mutation, or unrelated device cleanup.
