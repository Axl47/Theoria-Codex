Purpose / Big Picture

Users keep their profiles and exact reading/search state; account changes remain authoritative; duration work settles even when its bounded queue fills; cancelled requests stop; downloads save complete galleries under distinct filenames. Large libraries avoid repeated full scans and unused JSON decoding. Imports, collection commands, updater operations, and feed requests have one explicit lifecycle owner and useful failure/retry behavior.

The user authorized implementing every audit finding and recommendation, divided into commits, on October 3, 2026. This work does not publish a release or change production services.

Context and Orientation

app contains Android routes, ViewModels (retained state/job owners), media integration and provider wiring. app-logic contains platform-free state/policies. core-domain defines canonical Post identity, provider interfaces and Unified search. core-data defines repositories and portable persistence; core-data-android supplies Room (transactional SQLite). core-sources owns provider adapters and cancellable HTTP. A continuation is the provider token identifying the next page. Demand is an owner’s request for duration metadata; admission means it is scheduled, not merely desired.

Retain canonical IDs, grouped query boundaries, exact FYP replay, section-specific Recents, one-shot statistics, atomic Codex/Likes, bounded shared caches, original offline-media provenance, and simultaneous autoplay for every visible animated card. Do not cap visible player leases. The synchronous final Search scroll flush is intentional. No schema migration is needed unless an implementation explicitly establishes one.

Audited behavior and required acceptance

F01 · Profile limits silently hide libraries and can break subsequent backups

The production settings normalizer keeps only 64 profiles, replacing the last retained profile with the active one when necessary. Profile creation activates the new profile; restore appends profiles without a capacity check. Restore commits the library before writing the truncated Settings result and then deletes its journal. The isolated reproduction used the real DataStoreSettingsRepository: creation dropped p63; restore reported one profile added but retained zero imported profiles. A subsequent export failed with “Collection has no unique profile.”

Change: Make profile capacity an explicit, shared admission rule for creation and restore. Reject overflow before any library mutation; keep normalization from silently deleting user-owned identities. Verify that every restored profile is present before declaring the journal complete. Apply the same preflight principle to bounded favorite and blacklist data.

Acceptance: At 64 profiles, creation and additive restore must fail with useful feedback and zero durable changes. A 63+1 restore must survive reopen, expose its collection, and export successfully. Use the production DataStore repository for this test; the in-memory fixture does not exercise the same cap.

F02 · A stale Pixiv refresh can undo Disconnect or overwrite a new account

PixivTokenCoordinator reads the old refresh token, awaits the provider, and saves the result unconditionally. Its mutex protects refresh callers, not account replacement or clearing. Settings also implements its own refresh-and-save path outside that coordinator. Controlled deferred responses reproduced both credential resurrection after clear and replacement of a newer account.

Change: Use one account-session owner for provider and Settings refresh. Commit refreshed tokens only if the credential revision/session that started the request is still current. Make compare-and-set atomic with disconnect and login persistence; a separate read-before-save check still has a race.

Acceptance: Suspend a refresh, then disconnect or save another account, then release the response. The old response must be rejected. Also test stale refresh failure against a new login so Settings cannot clear the newer credentials.

F03 · Duration filtering can remain unresolved after the bounded queue fills

The scheduler admits at most 512 queued keys. MediaDurationRouteViewModel discards submit’s admission result and returns the entire desired set as its tracked demand. Rejected keys are therefore treated as submitted; settlement only publishes metadata and does not retry them. With the default queue bound, 513 unknown videos, and a paused execution gate, the reproduction acquired 512 and left one permanently unsubmitted after resuming.

Change: Distinguish accepted, already-decided, and deferred demand. Keep bounded scheduling in the coordinator, replenish capacity from still-required demand, and avoid recording rejected work as admitted. Cover eviction and expired retry decisions as well as initial saturation.

Acceptance: Load 513+ unknown videos while paused, enable a filter, resume, and verify every item settles without another UI event. Repeat with two routes and cancellation. Preserve simultaneous autoplay for all visible cards.

F04 · Search scroll reset bypasses the cache used to suppress duplicate writes

persistAppliedSearch writes (0,0) directly to UiRestoreRepository. persistedScrollStateByQuery still remembers the old position, so persistSearchScrollState can incorrectly skip an equal position. The reproduction saved (12,24), reapplied/reset the query, saved (12,24) again, and read back durable (0,0). The reset and normal writes also use different mutexes.

Change: Route resets and ordinary position writes through one serialized persistence path with one cache authority. Update or invalidate the cached position on reset, and account for an older debounced write racing with a new root commit.

Acceptance: Cover save → reset → same-position save, and an older pending flush overlapping a root reset. Retain the documented final-flush guarantee during ViewModel teardown.

F05 · Download filenames collide for ordinary non-Latin titles

sanitizeFileName strips every non-ASCII character and substitutes “image.” Because that is nonblank, the canonical source/post-ID fallback is never used. Two different Pixiv IDs titled 猫 and 犬 both produced image.jpg. Identical or equivalently sanitized Latin titles also collide.

Change: Build a filesystem-safe, length-bounded name that retains a readable Unicode title when possible and always includes canonical source/post identity plus gallery page identity. Define an explicit policy for repeat downloads of the same item.

Acceptance: Test Japanese titles, equal titles across different sources/IDs, punctuation-only titles, long names, gallery pages, and a repeated download. Verify the final destination policy in the isolated Android lane when implemented.

F06 · Hitomi manifest requests outlive every consumer

HitomiGalleryManifestStore replaces its supplied parent Job with a detached SupervisorJob and has no consumer count. Cancelling the only waiter, and then cancelling the supplied parent scope, both left the controlled loader running. Cache admission occurs after a waiter’s await, so a completed abandoned load is not even necessarily retained for reuse.

Change: Give shared manifest loads reference-counted leases: one departing consumer must not cancel another, while the last departing consumer cancels the request. Retain a real parent lifetime and bounded transport deadline. Reuse the ownership approach already established for Ugoira where it fits.

Acceptance: Two waiters share one load; cancelling one preserves the other; cancelling the last aborts transport; closing the parent aborts all owned flights. Measure abandoned network work during rapid source changes and Viewer swipes.

F08 · Offline saves rebuild the entire catalog, and Viewer entry resolves every offline post

Every offline commit or retain calls publishSnapshot, which reparses all manifests, checks gallery media files, and recursively walks stored files for byte totals. Saving N previously absent posts therefore performs at least 1+2+…+N catalog-entry validations: 500,500 for 1,000 posts, before counting gallery files. This is an analytical work count, not a device timing. FileBackedCacheRepository also scans directories per thumbnail. preparePostsForLaunch sequentially calls find for every offline member of the entire launch list before entering Viewer.

Change: Maintain an incremental process catalog after a bounded startup/reconciliation scan, update counts and ownership per committed post, and batch thumbnail accounting. Resolve offline media for the selected post and the established small lookahead window while retaining exact feed order.

Acceptance: Compare 100- and 1,000-post imports using filesystem-operation counters; growth should track changed entries rather than the full catalog per save. Opening one post should read only the current/lookahead records. Keep manifest verification and canonical source-media restoration intact.

Acceptance: Retain cancellation, replay, source-availability, related-shelf, restoration, and concurrent autoplay contracts. Validate behavior through the real owners. Ratchet down large-file exceptions when responsibilities actually leave; do not add wrapper layers merely to meet a line budget.
