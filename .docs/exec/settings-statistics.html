Purpose / Big Picture

The Settings screen will expose one Stats card with App, Posts, Search, Tags, and Codex groups. It will answer how the app is used without sending analytics off-device. Counts and duration remain local, survive relaunch, and update from real feature outcomes rather than UI impressions.

A user can open Settings, expand Stats, and see total foreground time, route-category time, watched/search/share activity, source participation, top watched and saved tags, current saved-post composition, and the most/least entered Codex for the active recommendation profile.

Lifetime event counters begin when this feature is installed. Current saved-post, source, and tag composition is derived from the active profile's live Codices and therefore includes data saved before this version.

Context And Orientation

Lifetime statistics are cumulative local counters. They do not decrease when Recents is cleared or a Codex is deleted. Current library statistics are recalculated from canonical posts currently saved in the active profile's visible Codices. Source participation means one Unified or Multi-Search may increment several source rows while incrementing the overall search count once.

States

  • Before the statistics store is ready, Settings keeps the safe zero/empty projection.
  • Empty rankings render a short “No … yet” message rather than fake source or tag rows.
  • Percentages use zero-safe denominators and whole-number rounding.
  • All durable counters are non-negative Long values; additions saturate at Long.MAX_VALUE.

Error paths

  • Statistics writes are best-effort side effects and must never turn a successful search, save, share, or Viewer transition into a feature failure.
  • Cancellation still propagates from coordinator work; ordinary statistics storage failures are isolated.
  • The typed store rejects unsupported newer schemas. Corrupt bytes use the existing DataStore preservation/reset behavior.
  • Foreground duration is flushed before changing category or entering background. A later failed persistence attempt does not duplicate already captured time in the same process.

Phases

Phase 1: Durable aggregate and projection

Add a schema-versioned statistics_store_v1.json, atomic mutation methods, normalization, and platform-free projection tests. The new store has no legacy input: counters default to zero while current Codex projections can immediately show existing saved data.

Phase 2: Authoritative event wiring

Add process lifecycle/category timing, accepted search recording, watched-page recording, successful URL-copy callbacks, successful For You save attribution, and Codex-entry recording. Analytics calls remain outcome-adjacent and failure-isolated.

Phase 3: Settings presentation

Add SettingsSectionKey.STATS, feed its live state from the Settings owner, and render five compact groups with nested source/tag rows and explicit empty states.

Phase 4: Bounded verification and durable guidance

Run one focused host batch. Update this plan, working_list.md, and AGENTS.md with only findings that future developers cannot cheaply rediscover.

  4. Add AppUsageTracker using elapsed realtime. Register it against process lifecycle and map the current navigation destination/top-level tab to Browsing, Watching, Codex, or uncategorized total-only time.
  5. Inject the statistics repository into Search and For You coordinators. Record only after accepted root persistence/publication, separately from Recents error handling.
  6. Extend ViewerRouteWorkflow.recordVisiblePost to record watched source/tags. Route successful URL-copy callbacks from the shared action sheet and Viewer to the same repository mutation.
  7. Carry a pending save origin beside the pending post. Record a For You save only after CodexRepository.addItem returns. Record Codex entry from the destination back-stack entry, not from a tile press.
  8. Extend the Settings owner with live statistics/current Codex collection, add the Stats expansion key, and render the requested hierarchy.
  9. Add focused repository, projection, timing, coordinator, presentation, and architecture tests; update R8/Gson wire manifests for durable record fields.

Surprises And Discoveries

  • Saved composition cannot be inferred from Likes alone because ordinary Codices and the system Likes Codex share canonical posts. The projection must union all visible Codex posts by Post.id.
  • Android 13+ suppresses the app-owned successful clipboard Toast, so a non-null confirmation message is not a reliable URL-copy success signal. Tracking must occur directly beside the boolean clipboard result.
  • The existing Viewer visible-post effect is keyed by canonical post ID and page index, providing the correct one-shot watched event without adding a second observation loop.
  • The broader Gson contract exposed a pre-existing manifest omission for CodexAutomaticTagRecord; the keep rules and wire manifest now match the already-durable Codex record fields.

Decision Log

  • Decision: keep analytics entirely on-device. Rationale: no remote analytics requirement exists and the data describes private viewing behavior. Date/Author: 2026-08-10 / Codex.
  • Decision: use a separate typed DataStore rather than AppSettings, UI restore, or Recents. Rationale: statistics are durable app data, not preferences, UI restoration, or clearable history. Date/Author: 2026-08-10 / Codex.
  • Decision: derive current saved composition and persist only irreversible lifetime event aggregates. Rationale: this avoids duplicated Codex truth and stale results after removal/profile changes. Date/Author: 2026-08-10 / Codex.
  • Decision: use process lifecycle and elapsed realtime. Rationale: Activity recreation must not create opens, and wall-clock changes must not alter duration. Date/Author: 2026-08-10 / Codex.
