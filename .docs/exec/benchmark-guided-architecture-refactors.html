Purpose / Big Picture

The current app is behaviorally strong: the developer accepted every outstanding user-facing interaction group on 2026-08-12, and all five physical Macrobenchmarks passed with the simultaneous-autoplay contract intact. The remaining opportunity is architectural. Production source sets still carry test repositories, Viewer has a second state model beside its authoritative reducer, app-shell and provider files combine too many policies, startup profiles predate major architecture changes, and one duration metric no longer means what its label suggests.

When complete, the production graph will require explicit durable dependencies, media zoom will reset with the selected media rather than leak between pages, benchmark output will distinguish per-item work from batch latency, the app shell and large providers will have clearer component boundaries, and startup profiles will describe the final code layout. Users should see the same workflows, with lower maintenance risk and startup performance that is measured against fresh compiler guidance.

Scope guard: this is a behavior-preserving refactor. No new store, navigation framework, single-active-player rule, schema, provider feature, or UI redesign is authorized.

Work Plan

  1. Instrument the benchmark batch before touching runtime architecture so the final run has honest semantics.
  2. Remove duplicate Viewer route fields and key only transform state by selected media identity.
  3. Make repository dependencies explicit, move reusable fakes to test fixtures, and keep only active file-backed owners in production.
  4. Extract shell UI/platform seams through parameterized components; leave state/effect orchestration in TheoriaAppContent.
  5. Extract provider policies one adapter at a time, running its focused test suite after each cohesive patch.
  6. Run one host validation batch. Repair common causes in grouped patches.
  7. Generate profiles through the isolated collection package, rebuild exact final artifacts, then run the physical benchmark once and compare it with both frozen and pre-refactor v0.10.0 results.

Do not touch the route-wide media-duration viewport design, repository schemas, playback pool policy, provider feature behavior, or navigation model. Those areas lack benchmark justification or requirements in this request.

Surprises And Discoveries

  • The first benchmark shell setup emitted a nonfatal appops warning because androidx.test.services had no UID before installation; instrumentation continued and all five tests passed. Treat as harness noise unless it becomes fatal or skips evidence.
  • The duration-workload “regression” is a measurement-definition change: one legacy batch span became 24 concurrent spans.
  • D8 reported 736 additional missing startup classes/methods while the checked-in profiles predate the latest application architecture.
  • The first profile-generation attempt found that the Android test module namespace collided with its isolated target package. Android installed the target first, then rejected the version-code-0 test APK as a downgrade. Giving the test APK its own .test identity and guarding both packaged IDs repaired the lane without touching production data.
  • Profile regeneration completed on SM-S926U with 38,889 baseline rules and 36,436 startup rules; the structural refactors changed enough ownership paths to add 9,308 and 9,024 rules respectively.
  • The duplication gate exposed that retaining already-retired file-backed repositories as test fixtures preserved needless parallel implementations. Removing those dead implementations restored the 0.58% fail-closed result while keeping active query/cache migration owners.
  • The current feed system delivered all expected first frames with stable frame CPU, so a route-wide viewport controller would add risk without an evidence-backed payoff.
  • The final duration RSS median rose 19.49% from the pre-refactor run, but its five samples shifted from 115788, 130056, 156784, 157376, 194404 KiB to 117612, 127696, 187340, 189028, 187376 KiB. Ordinary Search RSS improved 2.24% and Viewer remained within 0.80%, so this is a bimodal process-state watch item rather than evidence of a duration-owner leak.

Idempotence And Recovery

Source and documentation edits are ordinary version-controlled changes and safe to reapply after inspecting the diff. Gradle host tasks are safe to rerun. Profile generation intentionally rewrites checked-in generated profile files; inspect their diff before acceptance. Connected profile and benchmark tasks install only isolated application IDs after their guards pass. Preserve the current benchmark output before rerunning because Gradle may replace variant output directories.

If a refactor fails validation, keep already passing independent phases, revert only the incomplete owned patch, update this plan, and resume from its focused test. Do not use destructive Git cleanup, clear packages, uninstall production, or delete the preserved trace directory.
