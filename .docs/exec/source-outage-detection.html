ExecPlan: Detect source outages and fail fast

Branch spike/webview-verification (PR #49). Started 2026-11-07.

Purpose / Big Picture

When a provider is down (Danbooru's "Downbooru" maintenance page, a Cloudflare origin error, a browser challenge on a custom site, or a domain that no longer resolves), the app should notice quickly, stop hammering it for the rest of the session, show a small red dot on that source in every source dropdown, and say what to do: wait for maintenance, verify in the browser, or re-add a moved site. Nothing about this may slow app startup.

Current Status

Implemented on spike/webview-verification; host tests and a live check against Danbooru's maintenance page pass. On-device look and feel awaits the developer.

Context And Orientation

  • Observed failure. During maintenance Danbooru answers every URL with HTTP 503, an HTML body titled "Downbooru", and Retry-After: 30. DefaultSourceHttpClient (core-sources/.../http/DefaultSourceHttpClient.kt) retries 5xx twice and honors Retry-After (capped at 30 s), so each request waits about 60 s before failing. Search, For You, autocomplete and tag counts each issue several requests, which is the "retrying constantly" symptom.
  • Transports. Built-in sources share one DefaultSourceHttpClient created in app/.../di/TheoriaAppContainer.kt (sourceHttpClient). User-added sites use CustomSiteHttpClient (core-sources/.../custom/CustomSiteHttpClient.kt); the runtime instance is created in the same container (the prober keeps its own, untracked instance so it always sees raw answers).
  • Failure reporting. Adapters turn IOException into SourceAdapterException(NETWORK) via sourceNetworkFailure (core-sources/.../common/SourceAdapterCommon.kt). The search status UI (app/.../search/SourceFailureUiText.kt) shows the raw message for NETWORK failures.
  • Source dropdowns. Every picker renders through SourceIconMenu / SourceMenuChoices in app/.../ui/components/SourceSelector.kt.
  • Terms. Outage: a remembered "this host is down" record with a kind and an expiry. Circuit breaker: once an outage is recorded, further requests to that host fail immediately without touching the network until the outage expires or is cleared.

Phases

  1. Transport: HostOutageTracker + HostUnavailableException in core-sources/.../http/HostOutageTracker.kt. Both HTTP clients consult it before sending and record outages from answers. Long Retry-After no longer causes waits.
  2. App state: map tracked hosts to SourceKeys (by each source's presentation referer host), expose sourceIssues, and run a non-blocking background check after startup.
  3. UI: red dot in dropdowns; selecting a down source clears its outage (the search is the check); a challenged custom site opens its browser verification instead; messages per kind.

Work Plan

  • Outage kinds: MAINTENANCE (502/503/504, 520–530), CHALLENGE (403 with cf-mitigated: challenge, or a custom site's API answering with the verification page), UNRESOLVED (UnknownHostException, recorded only while the device is online).
  • Expiry: 10 minutes, or until clear(host). 500 is not an outage (often query-specific).
  • Retry rule: 5xx is retried only when Retry-After is absent or at most 3 s.
  • Messages come from the exception: "Down for maintenance. Try again later.", "Needs browser verification. Open Settings → Sites.", "Couldn't find this site. If it moved, remove it and add its new address."
  • Background check: after the container is ready, wait a few seconds, then GET each enabled source's site root sequentially through the tracked clients with a small body limit. Only outage answers matter; everything else counts as up. Never awaited by startup.

Surprises And Discoveries

  • The slowness was mostly self-inflicted: honoring a maintenance page's Retry-After for every request.
  • Built-in home pages can be challenged while their APIs work, so the background check counts challenges only for custom sites.

Decision Log

  • Track by host in the transport, not by wrapping adapters: adapters implement optional capability interfaces (faceted search, related posts) that a decorator would hide, and every request already passes the two clients.
  • The startup check runs in the background and only feeds the tracker; real requests also trip the breaker, so a skipped or slow check costs nothing (developer request: never block startup).
  • Tapping a down source clears its outage and lets the real search act as the check, instead of a separate probe UI.

Outcomes And Retrospective

The minute-long waits were the client obeying a maintenance page's Retry-After on every request; refusing long waits plus a per-host breaker turns an outage into instant, explained failures. The startup check runs only in the background and is redundant by design: the first real request trips the breaker too.

Idempotence And Recovery

All changes are code-only; no stored data or schema changes. Outages live in memory and vanish on restart. Reverting the branch commits restores previous behavior.
