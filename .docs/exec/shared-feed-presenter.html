ExecPlan: One retained presenter per feed

Each feed screen decides what to show (sort, hide by filters, wait for video lengths, build the related shelf) in its own chain of steps inside the screen code. This plan would give every paged feed one owner for that decision: it computes off the main thread, survives opening and closing the Viewer, and hands the screen one consistent result. Audit fix A3 already moved the heavy steps off the main thread and shared part of the wiring, so whether to build this is decided by a measurement of what A3 left.

Purpose / Big Picture

A feed is a scrolling list of posts: Search results, a For You result grid, a creator's posts, a Codex. Before a post is drawn the app applies, in order: the chosen sort; the visibility filters (hide viewed, hide liked, media type and others); the length filter, which needs video durations that arrive over time and reveals posts in a stable order as they become known; and the related-posts shelf.

Each screen wires those steps together itself, in composition (the code that builds the screen, on the main thread). Audit fix A3 changed how the two heaviest steps run, through one shared helper (rememberComputedOffMain):

  • A new list is still computed on the main thread, in the same frame. That covers a new search, an appended page (only the new page is filtered) and the first frame after returning from the Viewer. A3 tried delivering list changes a frame late and it moved where the grid lands on return, so this is deliberate.
  • Any other change is computed in the background while the previous result stays on screen: a filter toggle, a like, a resolved video length, a sort change.

A3's emulator numbers: re-sorting a 480-post Codex by length while lengths resolve went from about 0.9 s of main-thread work per 20 s to none, and a Search page arrival filters about 2 ms on the main thread instead of 11 ms. What remains after A3:

  • Returning from the Viewer redoes the whole list on the main thread. The helper's result lives in composition, which the feed leaves whenever a post opens, so the first frame back filters or sorts every loaded post again. A length sort of 480 posts cost about 23 ms per pass on the emulator before A3 (894 ms over about 38 passes); that pass still happens once per return.
  • Stages finish at different times. After a filter toggle the screen holds the new filter settings and the previous list for a moment. Paging, scroll restoration, saved scroll position and the tap that opens the Viewer each read whichever pieces are current. A length sort is two background steps in a row (known lengths, then the sort).
  • The wiring is still per screen. A3 shared the filter step for Search, For You and Creator (rememberFilteredFeed) and routed three Codex sorts through the helper. The length filter, the related shelf, and how each screen feeds paging and restoration are still wired separately, and Codex detail still filters in composition on the main thread.

The first draft claimed more than that: that every stage costs a frame of delay and that unfinished work is thrown away on each change. Review showed both claims were overstated, and that the first design would have broken returning from the Viewer. So this plan now starts with a measurement and a go or no-go, and the design below is what would be built on a go.

Requirements the design must meet

  1. Warm return shows the full list on the first frame. The presenter, its last result and its running work live in the retained holder, keyed per feed. "No result" happens only on a feed's first visit and after the process was killed. No composition renders an empty grid on return from the Viewer.
  2. A result is shown only for the context it was computed for. Every input carries a context key (applied query, creator feed, Codex id). A held result from another context is never shown. A held result from the same context that lags behind its input counts as "preparing": it stays on screen and paging is blocked, as today for an appended page.
  3. One snapshot for everything. The posts drawn, the filters reported, tap payloads that open the Viewer, the related shelf, index mapping, counts, scroll restoration, saved scroll position and page demand all come from one result. Restoration, saving and paging act only when that result is current: same context, and computed from the very list the screen state holds now.
  4. Surface rules stay expressible without flags. Search-style and Codex-style filtering are two typed cases. Known lengths are computed once and feed both the length sort and the length filter. The related shelf's projection stays separate and non-retained.
  5. Reveal history is explicit. The presenter is a state transition, not a pure function. Skipping an intermediate snapshot may change the order among posts whose lengths arrived late; membership and the order of everything else may not change. This is an accepted, tested difference.
  6. Cheap change detection. A new input is skipped when every field is the same object as last time; nothing compares lists deeply. Inputs are sent after composition, not during it.
  7. No extra work per change. A like or a related-shelf update must not re-sort; marks are narrowed to the enabled hide rules as today.

Owner and lifetime

FeedRetainedState gains one FeedPresenter per feed key. The presenter owns the retained length projection, the last FeedPresentation, and a worker on Dispatchers.Default in the holder's scope, so it outlives the screen. The screen still gathers inputs (they come from several state holders) and submits them from a side effect; it reads the presenter's current result as state. The worker runs each accepted input to completion and keeps only the latest waiting one. Results are published only for the presenter's current context; changing context drops the held result.

Hosting compared: in composition (first draft) loses the result whenever the Viewer opens; in each screen's ViewModel would move ownership of inputs that today live in several places; in the retained holder keeps input ownership where it is and gives the lifetime needed. The retained holder is chosen.

Per surface

  • Search, For You result grid, Creator: build their existing feed object entirely from one result and add the "current" condition to restoration, persistence and page demand.
  • Codex detail: the presenter is hosted in CodexDetailScreen, keyed by Codex id. The route boundary passes unsorted posts, the sort and usage; header, selection, source options and the Viewer list read canonical. "Loading" means no result for this Codex yet.
  • Followed and saved-search Codexes: the controller keeps calling the same pure sort for its anchor; a test asserts its order equals the presenter's canonical.

Smaller alternative, kept on the table

Keep A3's helper and close its gaps one by one, with no new owner:

  1. Keep the helper's last result in the retained holder, keyed per feed, so the first frame after the Viewer reuses it when the list and inputs are the same objects. This removes the return-time pass. The same key rule as requirement 2 applies: a result from another context is never reused.
  2. Route the Codex detail filter through the helper.
  3. Add the "current" condition to paging, restoration, persistence and tap payloads only where Phase 0 reproduces a mismatch.

This is the fallback on a no-go, and the expected outcome if Phase 0 finds only the return-time cost.

Appendix: Evidence And Notes

Review round 1: what changed

The plan gained a go or no-go after A3 and a smaller fallback. The presenter moved from composition into the retained holder, keeps its last result, and publishes per context. Paging, restoration and persistence require a current result. The input type gained a context key, a sort, a typed filter and a length setting; the output gained the canonical list. The Viewer, Recents, Library Saved shelves and For You home shelves left scope. Codex hosting moved into the detail screen. Behaviour is pinned with timed Compose tests instead of function comparisons. The claims about one frame per stage and discarded work were withdrawn.

Refresh after A3: what changed

A3 did more than the first two drafts assumed: one helper, a shared filter step for Search, For You and Creator, and in-place computation for new lists. The "ten copies of the wiring" claim was narrowed to what is still separate (length filter, related shelf, paging and restoration inputs, the Codex detail filter). A new, measured leftover was added: the whole-list pass on the first frame after the Viewer. The smaller alternative became concrete (retain the helper's result, route the Codex detail filter through it, add the "current" condition where a mismatch is reproduced), and Phase 0 now ends in one of three outcomes.
