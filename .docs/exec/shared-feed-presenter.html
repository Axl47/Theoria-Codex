ExecPlan: Feed presentation after A3

Each feed screen decides what to show (sort, hide by filters, wait for video lengths, build the related shelf) in its own chain of steps inside the screen code. Audit fix A3 moved the heaviest steps off the main thread. This plan finishes that job in place: it keeps results alive while the Viewer is open, stops the length filter from undoing A3's gain, and removes an empty frame on return. The original idea, one retained presenter that owns the whole decision per feed, stays in the plan as an option that is built only if a problem remains that the in-place work cannot fix.

Purpose / Big Picture

A feed is a scrolling list of posts: Search results, a For You result grid, a creator's posts, a Codex. Before a post is drawn the app applies, in order: the chosen sort; the visibility filters (hide viewed, hide liked, media type and others); the length filter, which needs video durations that arrive over time and reveals posts in a stable order as they become known; and the related-posts shelf.

Each screen wires those steps together itself, in composition (the code that builds the screen, on the main thread). Audit fix A3 changed how the two heaviest steps run, through one shared helper (rememberComputedOffMain):

  • A new list is still computed on the main thread, in the same frame. That covers a new search, an appended page (only the new page is filtered) and the first frame after returning from the Viewer. A3 tried delivering list changes a frame late and it moved where the grid lands on return, so this is deliberate.
  • Any other change is computed in the background while the previous result stays on screen: a filter toggle, a like, a resolved video length, a sort change.

A3's emulator numbers: re-sorting a 480-post Codex by length while lengths resolve went from about 0.9 s of main-thread work per 20 s to none, and a Search page arrival filters about 2 ms on the main thread instead of 11 ms. What A3 left, sorted by how sure we are:

The first draft claimed that every stage costs a frame of delay and that unfinished work is thrown away on each change. Review round 1 showed both were overstated and that a presenter in composition would break returning from the Viewer. Review round 2 showed that a presenter fed from a side effect delivers new lists late, and that the in-place fixes cover everything demonstrated so far.

Requirements

Requirement 0 applies to everything in this plan. Requirements 1 to 7 apply to the presenter option.

  1. A new list and its result reach the same frame. When the posts list is not the same object as last time (a new query, a replaced list, an appended page), the result is computed in place during composition, as A3 does. Background work is only for changes to the other inputs. A kept result is checked against the current context and inputs when it is read in composition, not when a later submission arrives.
  2. Warm return shows the full list on the first frame. The presenter, its last result and its running work live in the retained holder, keyed per feed. "No result" happens only on a feed's first visit and after the process was killed. No composition renders an empty grid on return from the Viewer.
  3. A result is shown only for the context it was computed for. Every input carries a context key (applied query, creator feed, Codex id). A held result from another context is never shown. A held result from the same context that lags behind its input counts as "preparing": it stays on screen and paging is blocked, as today for an appended page.
  4. One snapshot for everything. The posts drawn, the filters reported, tap payloads that open the Viewer, the related shelf, index mapping, counts, scroll restoration, saved scroll position and page demand all come from one result. Restoration, saving and paging act only when that result is current: computed from the very list the screen state holds now and from inputs equal to the current ones, filters, marks and lengths included.
  5. Surface rules stay expressible without flags. Search-style and Codex-style filtering are two typed cases. Known lengths are computed once and feed both the length sort and the length filter. The related shelf's projection stays separate and non-retained.
  6. Reveal history is explicit. The presenter is a state transition, not a pure function. Skipping an intermediate snapshot may change the order among posts whose lengths arrived late; membership and the order of everything else may not change. This is an accepted, tested difference.
  7. Cheap change detection that actually hits. The posts list is compared by identity and every other field by equals, as A3's helper does (OffMainComputation.kt :60-62). Screens rebuild their filter and mark objects on every composition (SearchFeed.kt :61-69, :81; SearchVisibilityFilters.kt :55-65), so an identity check on those would never match.
  8. No extra work per change. A like or a related-shelf update must not re-sort; marks are narrowed to the enabled hide rules as today.

Owner and lifetime

FeedRetainedState gains one FeedPresenter per feed key. The presenter owns the retained length projection, the last FeedPresentation, and a worker on Dispatchers.Default in the holder's scope, so it outlives the screen. The screen still gathers inputs (they come from several state holders). Per requirement 0, a new list is presented in place during composition through the presenter; only changes to the other inputs go to the worker, which runs each accepted input to completion and keeps only the latest waiting one. Results are read with a context check in composition, so a result from another context is never drawn, even for one frame.

Hosting compared: in composition (first draft) loses the result whenever the Viewer opens; in each screen's ViewModel would move ownership of inputs that today live in several places; in the retained holder keeps input ownership where it is and gives the lifetime needed. The retained holder is chosen.

Per surface

  • Search, For You result grid, Creator: build their existing feed object entirely from one result and add the "current" condition to restoration, persistence and page demand.
  • Codex detail: the presenter is hosted in CodexDetailScreen, keyed by Codex id. The route boundary passes unsorted posts, the sort and usage; header, selection, source options and the Viewer list read canonical. "Loading" means no result for this Codex yet.
  • Followed and saved-search Codexes: the controller keeps calling the same pure sort for its anchor; a test asserts its order equals the presenter's canonical.

Appendix: Evidence And Notes

Review round 1: what changed

The plan gained a go or no-go after A3 and a smaller fallback. The presenter moved from composition into the retained holder, keeps its last result, and publishes per context. Paging, restoration and persistence require a current result. The input type gained a context key, a sort, a typed filter and a length setting; the output gained the canonical list. The Viewer, Recents, Library Saved shelves and For You home shelves left scope. Codex hosting moved into the detail screen. Behaviour is pinned with timed Compose tests instead of function comparisons. The claims about one frame per stage and discarded work were withdrawn.

Refresh after A3: what changed

A3 did more than the first two drafts assumed: one helper, a shared filter step for Search, For You and Creator, and in-place computation for new lists. The "ten copies of the wiring" claim was narrowed to what is still separate (length filter, related shelf, paging and restoration inputs, the Codex detail filter). A new, measured leftover was added: the whole-list pass on the first frame after the Viewer. The smaller alternative became concrete (retain the helper's result, route the Codex detail filter through it, add the "current" condition where a mismatch is reproduced), and Phase 0 now ends in one of three outcomes.

Review round 2: what changed

Both reviewers found the presenter's side-effect submission would deliver new lists a frame late (requirement 0 added, design changed). Opus found two facts the refresh had wrong or missed: with the length filter on, each arriving length still filters the whole list on the main thread, and the first frame after the Viewer is handed an empty list. Sol found that identity checks on rebuilt filter and mark objects never match (requirement 6 changed to value equality), that "current" ignored filters, marks and lengths (requirement 3 changed), and that the input type lacked Codex usage. Both found the decision rule broken: the 2 ms line could not be met, one outcome was unreachable, and the user's preference was mixed into a measurement. The in-place work became Step 1 with per-item triggers; the presenter became Step 2, built only for a reproduced problem that remains. Sol's verdict was to do the smaller alternative. Not adopted: a statistics protocol beyond five runs and a median, which is enough for a direction check on the emulator.
