ExecPlan: One background presenter for every feed

After this plan, every list of posts the app shows (Search, For You, Creator profiles, saved and live Codexes, related shelves, and the Viewer's lists) is sorted, filtered and projected by one shared piece of code that runs on a background thread and hands the screen a finished list. Screens stop computing lists while they are being drawn, the copies of that logic in each screen are deleted, and a filter or sort behaves the same everywhere.

Purpose / Big Picture

Compose builds a screen by running its functions on the main thread. Anything those functions compute delays the frame. Every feed screen in this app turns raw posts into the list it shows in several steps, and runs most of them inside the screen function itself: put the posts in the chosen order, attach known video lengths, apply the visibility filters (animated only, hide liked, hide saved, hide watched, date range, length range), and work out which related posts to show. Each step walks the whole loaded list, and each reruns whenever any input changes: a page arrives, a like is toggled, one more video length becomes known.

Audit finding A3 moved the heaviest of those steps to a background thread, one step at a time and screen by screen. That removes the frame cost but leaves three problems. The logic still exists in a slightly different form per screen, which the repository's maintainability rule treats as a defect. Each step that moves to the background adds a frame of delay, so a chain of three shows two intermediate states built from a mix of old and new inputs. And the logic cannot be tested without a screen.

When this plan is complete there is one feed presenter: a plain function from "everything this feed depends on" to "what this feed shows", run on a background thread, one result per input snapshot. A screen passes its inputs in and renders what comes out. A developer can see it working in three ways: the presenter's tests cover each screen's rules without Android; the main-thread check from the observability plan stays silent while feeds update; and slow-frame counts for feed screens do not rise when filters are toggled or pages arrive.

Context And Orientation

  • Feed: any scrolling list or shelf of posts.
  • Visibility filters: SearchVisibilityFilters and filterSearchResults in app-logic/src/main/kotlin/com/theoriacodex/app/search/SearchVisibilityFilters.kt. Pure functions.
  • Duration projection: DurationFilterProjection in app/src/main/java/com/theoriacodex/app/media/DurationFilterProjection.kt. It matches posts to video lengths that are resolved in the background, and keeps a reveal order so posts do not jump as lengths arrive. It is the one step that already ran off the main thread before the audit, through produceState with withContext(Dispatchers.Default), and it keeps state between runs.
  • Related projection: buildRelatedFeedProjection, used by rememberRelatedFeedPresentation in app/.../ui/components/RelatedFeedPresentation.kt, decides where related posts appear among the main results.
  • Codex sorting: sortCodexPosts, sortLiveCodexPosts and rememberCodexPostDurations in app/.../codex/CodexPostSorting.kt. ShownPosts keeps the previous order on screen until a new sort has an answer.
  • Marks: the sets of liked, saved and watched post ids, plus posts "retained" so a card does not vanish the moment it is liked while the Viewer is open.

Design

One input, one output

data class FeedInput(
    val posts: List<Post>,
    val order: FeedOrder?,                 // Codex sort with its usage; null keeps the given order
    val filters: SearchVisibilityFilters,
    val marks: FeedMarks,                  // liked, saved, watched, retained ids
    val durations: FeedDurationInput,      // resolved states, whether the length filter is on, unknown-length policy, reveal exemption
    val related: RelatedPostsUiState?,     // null for feeds without related posts
)

data class FeedPresentation(
    val input: FeedInput,                  // the snapshot this was computed from
    val visiblePosts: List<Post>,
    val durationMetadata: DurationFilterMetadata,
    val related: RelatedFeedProjection?,
)

FeedPresenter.present(input) runs the steps in a fixed order (sort, duration projection, filter, related projection) by calling the functions that exist today. This plan moves and joins logic; it does not rewrite the rules. One presenter instance belongs to one feed, because the duration step remembers its reveal order; instances for a feed's main list are kept across a visit to the Viewer the same way rememberRetainedDurationProjection keeps the projection today. The presenter calls OffMainWork.note("feed-present") first, so running it on the main thread is reported.

Running it: latest input wins, nothing is cancelled half-way

A single composable, rememberFeedPresentation(presenter, input), feeds inputs into a conflated stream (only the newest waiting input is kept) and computes them one at a time on Dispatchers.Default. A computation in progress always finishes and publishes before the next starts. This matters because video lengths resolve in bursts: restarting the computation on every change, which is what keying a produceState on its inputs does, can keep the list from updating until the burst ends.

Until the first result exists the composable returns nothing and the screen shows what it shows today while its first page loads. After that the previous result stays on screen until the next is ready, which generalises what ShownPosts does for Codex sorting. Because each result carries the input it came from, code that needs an exact match can check it: paging asks for the next page only when the shown result reflects the current posts, and scroll restoration waits for a result computed from the restored posts.

Cost of the work itself

The presenter is the place to stop redoing work, but only where a measurement asks for it. Two changes are in scope because the audit identified them: the animated-only filter lowercases every tag of every post on each pass (SearchVisibilityFilters.kt :102-103), which becomes a per-post value computed once; and under a length sort the whole Codex is re-sorted each time one length resolves, which the conflated runner already reduces to one sort per burst. Incremental filtering of appended pages is not planned unless the slow-frame data shows a need.

Alternatives considered

AlternativeWhy not
Keep A3's per-step background helper and stop.Leaves the per-screen copies, chained one-frame delays with mixed snapshots, and untestable rules.
Move the whole pipeline into each screen's ViewModel as a StateFlow.The inputs have different owners: filter toggles are saved UI state, marks and video lengths are app-wide flows collected in composition. Each ViewModel would first have to take ownership of all of them, a larger change with no extra benefit for frames. The presenter is written so a ViewModel can host it later.
Do the work in the data layer (queries that filter and sort).Most feeds are provider pages held in memory, not database rows.

Surprises And Discoveries

  • Observation: keying a background computation on its inputs restarts it on every change and discards the unfinished result. Evidence: produceState(null, posts, states, active) in media/DurationFilterProjection.kt. Consequence: the runner is a conflated stream that lets each computation finish.
  • Observation: there are eight call sites of the filter and five of the related presentation, more than the five screens the audit named. Evidence: the surface table above. Consequence: the Viewer route and Recents are in scope.

Decision Log

  • Decision: The presenter composes the existing rule functions and does not rewrite them. Rationale: the goal is one place and one thread, not new behaviour. Date/Author: 2026-11-15 / Claude.
  • Decision: Host the presenter in composition, not in ViewModels. Rationale: its inputs are owned in several places today; see Alternatives. Date/Author: 2026-11-15 / Claude.
  • Decision: Results carry their input. Rationale: paging and scroll restoration need to know whether the shown list reflects the current posts. Date/Author: 2026-11-15 / Claude.

Idempotence And Recovery

No stored data or settings change. Each surface converts in its own commit and can be reverted alone; converted and unconverted screens coexist because both call the same rule functions. Nothing is deleted until Phase 5, so until then a revert restores the previous chain exactly. If a converted screen shows a behaviour difference that the Phase 0 tests did not cover, add the missing case to the tests first, then fix or revert.
