ExecPlan: Make source calls safe from any thread

After this plan, every call the app makes into a content source (search, resolve a post, comments, tag counts, sign-in, site probing) does its response handling and parsing on a background thread no matter which thread calls it. Today that is true only where the calling code remembered to switch threads, and review of this plan found several callers that did not.

Purpose / Big Picture

The app's main thread draws the screen. A source adapter is the class that talks to one provider: it sends HTTP requests and parses the answers into posts, tags and comments. The network wait itself never blocks a thread, but everything after the response arrives (decoding up to 8 MB of text, parsing JSON or HTML, building objects) runs on whichever thread called the adapter. If that is the main thread, frames are late.

Kotlin's convention for this is main-safety: a suspending function should be safe to call from the main thread, and should move its own heavy work elsewhere. The adapters do not follow it. Protection lives in callers, each with its own thread switch, and audit finding A1 fixed three callers that had none (Search, Followed Codex, Creator).

Review of this plan found more callers on the main thread with no switch, none of them covered by A1:

Fixing those one by one leaves the next caller free to make the same mistake. This plan moves the responsibility into the sources: each function in the boundary defined below switches to a background dispatcher itself, and tests fail when one does not.

What this plan does not do: remove the thread switches callers already have. Review showed almost all of them also protect the caller's own work, so they stay.

Context And Orientation

  • Dispatcher: the object that decides which thread a coroutine runs on. Dispatchers.Default is the shared background pool. withContext(dispatcher) { … } runs a block on that dispatcher and returns to the caller's; when the caller is already on that dispatcher it does not hop.
  • Capability interfaces: core-domain/src/main/kotlin/com/theoriacodex/domain/adapter/SourceAdapter.kt declares SourceAdapter (5 suspending functions) and ten optional interfaces (13 more), 18 function names in all. App code finds the optional ones with as? checks on the adapter (24 checks in 13 files), which is why wrapping adapters in a decorator is not practical.
  • Adapters: under core-sources/src/main/kotlin/com/theoriacodex/sources/: Danbooru, Gelbooru, Pixiv, Nhentai, Hitomi, Iwara, and the Rule34 family (AbstractRule34KvsVideoSourceAdapter, Rule34VideoSourceAdapter, Rule34PahealSourceAdapter, Rule34GenSourceAdapter). Together they override 75 interface functions. Custom Sites have no adapter classes of their own: custom/Families.kt builds Danbooru and Gelbooru adapters (:54, :99).
  • HTTP: http/DefaultSourceHttpClient.kt. Bytes are read on OkHttp's thread; the text decode happens on the thread that resumes the caller (:50, :239).
  • A1's precedent: UnifiedSearchOrchestrator takes providerContext: CoroutineContext = Dispatchers.Default; tests pass EmptyCoroutineContext to stay on their own dispatcher. This plan uses the same pattern.
  • The marker: OffMainWork.note(label) from main-thread-observability.html, placed at parse sites. An installed checker sees every call and the thread it ran on.

Design

1. The boundary this plan guarantees

The guarantee covers the suspending functions that code outside core-sources calls and that handle a provider response:

  • The 18 function names declared in SourceAdapter.kt, in every class that overrides them.
  • The public suspending functions of the non-adapter classes the app imports: PixivAuthApi, PixivTokenCoordinator (called directly from SettingsViewModel.kt :109 and PixivUgoiraPlayer.kt :53), SiteProber, SiteHealthCheck, and the new fetchGelbooruProfileOwner (below). Phase 0 rebuilds this list independently of the list above, by reading every import of com.theoriacodex.sources in app and app-logic and every suspending function called on those types, and adds whatever it finds.

Outside the guarantee, by decision:

  • The raw HTTP client. App code that calls SourceHttpClient itself (BoundedMediaDurationProbe, PixivUgoiraPlayer) receives bytes or text and owns what it does with them.
  • Functions reached only through the boundary. For example HitomiMediaUrlResolver.refresh and the family probes in Families.kt (reached only through SiteProber, SiteProber.kt :65, :86, :88). They run on the background thread because their caller put them there.
  • A future non-adapter class. The scan cannot know that a new class is called from the app. The backstop is the parse marker from the sibling plan, which reports any marked parse on the main thread in real use.

2. One helper, used by every function in the boundary

// core-sources/.../common/SourceAdapterCommon.kt
/** Runs a source entry point on a background dispatcher so it is safe to call from any thread. */
internal suspend fun <T> sourceCall(
    context: CoroutineContext = Dispatchers.Default,
    block: suspend () -> T,
): T = withContext(context) { block() }

Every function in the boundary becomes override suspend fun search(…) = sourceCall { … }. The switch is unconditional. The first draft switched only when the caller's dispatcher was a "main" dispatcher type; review showed that misses Compose's own dispatcher (the one behind rememberCoroutineScope and LaunchedEffect, which is not that type) and unconfined coroutines, which are exactly the callers in the table above.

Consequences, all intended:

  • A caller already on Dispatchers.Default pays nothing. Nested calls (one adapter function calling another) pay nothing for the same reason.
  • Tests that rely on virtual time inside an adapter. Pixiv, Nhentai and Hitomi take a constructor parameter callContext: CoroutineContext = Dispatchers.Default and write = sourceCall(callContext) { … }; their tests pass EmptyCoroutineContext. Review identified the tests that need it: PixivRequestPacingTest.kt :28, :47 (virtual clock, 10 s interval), NhentaiCreatorSourceAdapterTest.kt :24-31 (a real delay racing a virtual timeout), HitomiPaginationSourceAdapterTest.kt :349-358 (ordering through runCurrent()). No other adapter gets the parameter.
  • Nhentai tests that keep the default 350 ms request interval (NhentaiSourceAdapter.kt :60, :604-612) will really wait. They get slower, not wrong; pass EmptyCoroutineContext where the wait is noticeable.
  • Early return statements inside a converted body become return@sourceCall.
  • A result that completes after its caller was cancelled is dropped (withContext checks cancellation on return). The caller is already cancelled, so nothing observes the difference.
  • Shared in-flight work keeps its semantics. SharedFlights runs each fetch under its own job (SharedFlights.kt :39-40), and the Hitomi stores use their own scope or NonCancellable, so the wrapper changes nothing there. No new cancellation behaviour is added; the existing tests, including HitomiGlobalIndexCacheTest :98 (an owner's cancellation reaches the other waiters), must pass unchanged.
  • The count callback. onCounts in fetchTagCountsIncrementally runs on the caller's thread for adapters that use the interface's default body (SourceAdapter.kt :181, which only delegates) and on a background thread for Nhentai. Its documentation will say "may be called on any thread", and Phase 0 confirms its single consumer (TagCountCoordinator into the locked tag store) is safe for that.
  • Adapter state is safe with the switch: review found no ThreadLocal or limitedParallelism; the Pixiv and Nhentai mutexes sit inside the function bodies; the Gelbooru flags are already read from several threads.

3. The Gelbooru profile lookup moves into the module

The lookup in CreatorOpeningWorkflow.kt :43 becomes a top-level suspend fun fetchGelbooruProfileOwner(http, creatorId, headers): String? in the Gelbooru package of core-sources, written as = sourceCall and using GelbooruSite.GELBOORU.baseUrl. The app keeps its timeout, passes the headers it already builds (SourceKey.requestHeaders(), SourceMetadata.kt :291), and builds the CreatorProfile. It does not become an adapter method: that would need a cast to the concrete class or one more interface.

4. Proof

Completeness test (host). SourceEntryPointCompletenessTest reads the module's main source files and fails unless:

  • every override suspend fun whose name is one of the 18 declared in SourceAdapter.kt, and every public suspending function of the listed non-adapter classes, is written as exactly = sourceCall { or = sourceCall(callContext) { (with or without a declared return type), and the function ends where that block ends, so nothing can be appended after it;
  • no file under any module's src/main passes a callContext argument. Production code cannot choose the dispatcher; only tests can.

Matching by function name avoids resolving inheritance from source text and leaves protected hooks alone (Rule34GenSourceAdapter.latestPage, :25, overrides a hook of its base class, not an interface function). This test is what carries the guarantee across all 75 overrides, including mapping done after a nested call returns (HitomiSourceAdapter.autocompleteTags, :354).

Contract test (host). SourceMainSafetyContractTest shows the wrapper does what the scan assumes. It calls from a stand-in "main" thread: a plain single-thread dispatcher, deliberately not a main-dispatcher type. It installs an OffMainWork checker. Rows:

  • one search per adapter the real registry builds, reusing the ten payloads in RealProviderPageContractTest.kt :56-84 and Hitomi's URL-routing fake (HitomiSourceAdapterTestFixture.kt :209);
  • PixivAuthApi.refresh, PixivTokenCoordinator.activeTokens, SiteProber.probe;
  • one search made through an unconfined coroutine started on the stand-in thread.

Each row asserts: the call returned its expected result (for search, the payload's post count); at least one marked parse ran; no marked parse, HTTP call or credential read ran on the stand-in thread. The confined rows also assert the call resumed on the stand-in thread. The unconfined row does not, because an unconfined coroutine has no thread to return to.

The first revision planned a row for every capability of every adapter, about 75. Review showed the existing fake client returns one canned response for every request, so that would mean a new fixture set per provider, and those rows would add little once the scan guarantees the form of every function.

Device proof. One journey test, SourceCallThreadJourneyTest, on the fixture from main-thread-observability.html Phase 2: open a post's menu by long press, choose "Open original post" (PostMenuActions.kt :45), and land in the Viewer on the resolved post. This is the path at TheoriaShell.kt :656, which runs on Compose's real dispatcher and has no switch of its own. Fixture requirements:

  • the link's source must be one the fixture makes available (TheoriaShell.kt :648 sends the link to the browser otherwise); the journey fixture's sources are PIXIV and GELBOORU (AppJourneyFixture.kt :48), and the Gelbooru adapter already parses links;
  • the in-memory client answers that adapter's single-post endpoint as well as its search;
  • the test post carries an originUrl, set through customizePost, or the menu entry does not appear.

It asserts the single-post request was made, the Viewer shows the resolved post, at least one parse ran, and none ran on the main thread. It fails without this plan even with A1 in place.

5. Alternatives considered

AlternativeWhy not
Switch only for main-type dispatchers (first draft)Misses Compose scopes and unconfined coroutines; moves viewModelScope tests onto real threads anyway.
Fix each unprotected callerNine more local switches, and the tenth caller is unprotected again.
Decorate adapters in the registryCallers discover capabilities with 24 type checks; a decorator would have to implement every combination of eleven interfaces.
Parse inside the HTTP layerParsing is per adapter and per endpoint; the HTTP layer cannot own it.
One injected dispatcher for every adapterConstructor plumbing through every adapter and the registry for something three adapters' tests need.
Scan every public suspending function in the moduleKotlin members are public by default, so the scan would need a long list of exceptions for helpers that are only reached through the boundary.
A request-start marker in the HTTP layerNothing would read it, and the app's direct HTTP users would fill it with noise. Deferred.

  • Decision: The source scan carries the guarantee; the contract test is one search per adapter plus the non-adapter classes. Rationale: per-capability rows cost a new fixture set and prove nothing the scan does not. Date/Author: 2026-11-16 / Claude.
  • Decision: The scan accepts only sourceCall { and sourceCall(callContext) {, and forbids callContext arguments in production code. Rationale: closes the bypass through the injected dispatcher. Date/Author: 2026-11-16 / Claude.

Outcomes And Retrospective

Phases 0 and 1: every function on the boundary runs its body on Dispatchers.Default, so each caller in the Purpose table, and the start-up token refresh found in Phase 0, no longer parses on the main thread. The caller's own work after the call still runs where the caller runs; that was never in scope. The completeness test fails for each of the four planned negative controls plus appended work and a positional dispatcher. Not proven: anything on a device (Phase 2), live Pixiv sign-in and refresh, and live site probing.

Phase 2: on the emulator, opening an original-post link from a post's menu parses the resolved post off the main thread, and the journey fails when sourceCall stops switching (one parse on the main thread, at TheoriaShell.kt :656) or when the provider answers nothing (no parse). The Search journey passed in both controls, so A1's caller switch alone does not cover this path. Still open: its first run in the Main workflow on Android 16 and 17.

Lesson: a dispatcher switch inside a callee turns every virtual-time deadline around it in tests into an immediate timeout, so a main-safety change should search the tests for withTimeout around the converted calls before the first run.

Idempotence And Recovery

No data changes. Each group commit can be reverted on its own; a reverted group makes the completeness test fail, which is the intended signal that the guarantee no longer holds. A flaky row in the contract test is fixed or the plan is reopened; adapters are not excluded. Negative controls are single-line edits: undo them and confirm with git status --short.
