ExecPlan: Make source calls safe from any thread

After this plan, every call into a content source (search, resolve a post, comments, tag counts, sign-in, site probing) does its network handling and parsing on a background thread no matter which thread calls it. Today that is true only where the calling code remembered to switch threads, and review of this plan found several callers that did not.

Purpose / Big Picture

The app's main thread draws the screen. A source adapter is the class that talks to one provider: it sends HTTP requests and parses the answers into posts, tags and comments. The network wait itself never blocks a thread, but everything after the response arrives (decoding up to 8 MB of text, parsing JSON or HTML, building objects) runs on whichever thread called the adapter. If that is the main thread, frames are late.

Kotlin's convention for this is main-safety: a suspending function should be safe to call from the main thread, and should move its own heavy work elsewhere. The adapters do not follow it. Protection lives in callers, each with its own thread switch, and audit finding A1 fixed three callers that had none (Search, Followed Codex, Creator).

Review of this plan found more callers on the main thread with no switch, none of them covered by A1:

CallerWhat reaches a source on the main thread
ui/TheoriaShell.kt :656, :710 (scope from rememberCoroutineScope, :873)Opening an original-post link calls adapter.resolvePost.
search/SearchResultCard.kt :338 into recommend/ForYouCoordinator.kt :129Resolving a card's preview calls adapter.resolvePost.
creator/CreatorFollowsViewModel.kt :73Checking followed creators calls searchCreatorPosts.
creator/CreatorOpeningWorkflow.kt :43A creator link fetches a Gelbooru profile page and runs a regular expression over the HTML, in app code.
Custom Sites controller (:131, :181, :195) and Pixiv sign-in (PixivPkceController.kt :67)Site probing and token exchange parse JSON. Reported by review; confirmed in Phase 0.

Fixing those one by one leaves the next caller free to make the same mistake. This plan moves the responsibility into the sources: every suspending entry point of the core-sources module switches to a background dispatcher itself, and tests fail when one does not. Callers then cannot get it wrong.

What this plan no longer aims to do: remove the thread switches callers already have. Review showed almost all of them also protect the caller's own work, so they stay.

Context And Orientation

  • Dispatcher: the object that decides which thread a coroutine runs on. Dispatchers.Default is the shared background pool. withContext(dispatcher) { … } runs a block on that dispatcher and returns to the caller's; when the caller is already on that dispatcher it does not hop.
  • Capability interfaces: core-domain/src/main/kotlin/com/theoriacodex/domain/adapter/SourceAdapter.kt declares SourceAdapter (5 suspending functions) and ten optional interfaces (13 more), such as comments, related posts, creator posts and tag counts. App code finds them with as? checks on the adapter (24 checks in 13 files), which is why wrapping adapters in a decorator is not practical.
  • Adapters: under core-sources/src/main/kotlin/com/theoriacodex/sources/: Danbooru, Gelbooru, Pixiv, Nhentai, Hitomi, Iwara, and the Rule34 family (AbstractRule34KvsVideoSourceAdapter, Rule34VideoSourceAdapter, Rule34PahealSourceAdapter, Rule34GenSourceAdapter). Together they override 76 suspending functions. Custom Sites have no adapter classes of their own: custom/Families.kt builds Danbooru and Gelbooru adapters (:54, :99) and contains the probing functions (:34, :83, :121).
  • Other suspending entry points in the module: PixivAuthApi, PixivTokenCoordinator, custom/SiteProber.kt, custom/SiteHealthCheck.kt.
  • HTTP: http/DefaultSourceHttpClient.kt. All transports, including the Custom Sites client (custom/CustomSiteHttpClient.kt :57), go through executeHttpRequest (:193). Bytes are read on OkHttp's thread; the text decode happens on the thread that resumes the caller (:50, :239).
  • A1's precedent: UnifiedSearchOrchestrator now takes providerContext: CoroutineContext = Dispatchers.Default; tests pass EmptyCoroutineContext to stay on their own dispatcher. This plan uses the same pattern.
  • The marker: OffMainWork.note(label) from main-thread-observability.html, placed at parse sites. An installed checker sees every call and the thread it ran on.

Design

1. One helper, used by every entry point

// core-sources/.../common/SourceAdapterCommon.kt
/** Runs a source entry point on a background dispatcher so it is safe to call from any thread. */
internal suspend fun <T> sourceCall(
    context: CoroutineContext = Dispatchers.Default,
    block: suspend () -> T,
): T = withContext(context) { block() }

Every suspending entry point becomes override suspend fun search(…) = sourceCall { … }. The switch is unconditional. The first draft switched only when the caller's dispatcher was a "main" dispatcher type; review showed that misses Compose's own dispatcher (the one behind rememberCoroutineScope and LaunchedEffect, which is not that type) and unconfined coroutines, which are exactly the callers in the table above.

Consequences, all intended:

  • A caller already on Dispatchers.Default pays nothing. Nested entry points (one adapter function calling another) pay nothing for the same reason.
  • An adapter whose tests rely on virtual time inside the adapter takes a constructor parameter callContext: CoroutineContext = Dispatchers.Default and passes it to sourceCall; those tests pass EmptyCoroutineContext. Phase 0 finds which adapters need it (candidates: Pixiv pacing, Nhentai, Gelbooru, Hitomi, the shared tag-count helper).
  • Early return statements inside a converted body become return@sourceCall.
  • A result that completes after its caller was cancelled is dropped (withContext checks cancellation on return). The caller is already cancelled, so nothing observes the difference; shared in-flight requests (Hitomi, Viewer resolution) get a test that a cancelled waiter does not cancel the others.
  • Callbacks passed into a source run on the background thread. The only one is onCounts in fetchTagCountsIncrementally. Its interface documentation will say "may be called on any thread", and Phase 0 confirms its single consumer (TagCountCoordinator into the locked tag store) is safe for that.

2. What gets wrapped

  • All 76 adapter overrides.
  • The public suspending functions of PixivAuthApi, PixivTokenCoordinator, SiteProber, the family probe functions in Families.kt, and SiteHealthCheck.
  • The Gelbooru profile lookup in CreatorOpeningWorkflow moves into the Gelbooru package of core-sources as a wrapped function; the app keeps only the call.

Non-suspending adapter members (accountFeeds, supportedSearchScopes and similar) must stay free of network access and parsing; the completeness test lists them so a new one is looked at.

3. Proof

Contract test (host). SourceMainSafetyContractTest in core-sources calls sources from a stand-in "main" thread: a plain single-thread dispatcher, deliberately not a main-dispatcher type. It installs an OffMainWork checker and uses the fake HTTP client and credentials provider from RealProviderPageContractTest, extended to record the calling thread. The fake client returns valid synthetic responses, so parsing really happens. For every adapter the real registry builds with all sources enabled, plus the adapters built by each Custom Sites family, and for each capability the adapter implements, the test makes one call with arguments valid for that adapter and asserts:

  • the fake client was reached (rows that legitimately return before any request are declared as such in the test, with the reason);
  • no HTTP call, credential read or marked parse ran on the stand-in thread;
  • the call completed back on the stand-in thread.

It adds rows for the non-adapter entry points, for a second call that hits a cache (Hitomi caches, Pixiv ugoira metadata), and for one call made through an unconfined coroutine started on the stand-in thread.

Completeness test (host). A test reads the module's source files and fails if any override suspend fun in a class implementing an adapter interface, or any public suspending function of the listed non-adapter classes, is not written as = sourceCall. This is what catches work the contract test cannot see, such as mapping done after a nested call returns (HitomiSourceAdapter.autocompleteTags, :354), and new adapters or interface functions added later. There is no exclusion list.

Device proof. Two journey tests on the fixture from main-thread-observability.html (a real Danbooru adapter fed by an in-memory client): one calls adapter.search directly from the Android main thread; one opens an original-post link through the app shell, the path at TheoriaShell.kt :656. Each asserts at least one parse and none on the main thread. These prove the result with the real main looper and Compose's real dispatcher, and they fail without this plan even with A1 in place.

Request-start report. OffMainWork.note(SOURCE_HTTP) at the top of executeHttpRequest. This is a separate, weaker signal than the parse marker: after this plan, a source request that starts on the main thread means some code reached the HTTP layer without going through an entry point. It is logged, not gated. App code that uses the HTTP client directly (BoundedMediaDurationProbe) will show up here if it runs on main; that is recorded as a finding.

4. Alternatives considered

AlternativeWhy not
Switch only for main-type dispatchers (first draft)Misses Compose scopes and unconfined coroutines; moves viewModelScope tests onto real threads anyway.
Fix each unprotected callerSix more local switches, and the seventh caller is unprotected again.
Decorate adapters in the registryCallers discover capabilities with 24 type checks; a decorator would have to implement every combination of eleven interfaces.
Parse inside the HTTP layerParsing is per adapter and per endpoint; the HTTP layer cannot own it.
One injected dispatcher for every adapterConstructor plumbing through every adapter and the registry for something only a few tests need; the optional parameter covers those.

Both reviews read every candidate the first draft proposed to remove. Where they disagreed, the switch stays.

Surprises And Discoveries

  • Observation: Compose's coroutine dispatcher is not a main-dispatcher type, so a type check cannot recognise the most common main-thread callers. Evidence: review disassembled AndroidUiDispatcher in ui-android 1.11.4.
  • Observation: several main-thread callers reach sources with no switch and are outside A1. Evidence: the table in Purpose.
  • Observation: nearly every existing caller switch also protects the caller's own work. Evidence: the table in Caller switches.
  • Observation: Custom Sites and the health check bypass DefaultSourceHttpClient but share executeHttpRequest. Evidence: custom/CustomSiteHttpClient.kt :57.
  • Observation: a test that makes the fake client throw proves only where requests start; adapters also swallow failures and fall back. Evidence: AbstractRule34KvsVideoSourceAdapter.kt :65.

Decision Log

  • Decision: Switch unconditionally to a background dispatcher. Rationale: the guarantee must hold for any calling thread, and the conditional form missed real callers. Date/Author: 2026-11-16 / Claude.
  • Decision: Keep every caller switch. Rationale: they protect caller work; removing them was the first draft's weakest claim. Date/Author: 2026-11-16 / Claude.
  • Decision: The contract covers every suspending entry point of core-sources, not only adapters. Rationale: sign-in and probing parse on the caller's thread too. Date/Author: 2026-11-16 / Claude.
  • Decision: Prove execution sites with valid responses and a source scan, not a throwing client and a hand-kept list. Rationale: the earlier test could pass with parsing on main and could miss new adapters. Date/Author: 2026-11-16 / Claude.
  • Decision: onCounts may run on any thread. Rationale: one consumer, already locked; forcing the caller's thread would add a hop per batch. Date/Author: 2026-11-16 / Claude.
  • Decision: The request-start note is a report, not a gate. Rationale: it does not show where parsing ran. Date/Author: 2026-11-16 / Claude.
  • Decision: Phase 0 can stop the plan. Rationale: after A1 the value is the unprotected callers plus prevention; if the first is empty the user decides on the second. Date/Author: 2026-11-16 / Claude.
