ExecPlan: Make every source call safe from the main thread

After this plan, any screen can call any provider source from the main thread and no parsing or other source work will run there. The guarantee lives in the source layer itself, so a new screen or a new source cannot reintroduce the problem, and the dispatcher switches that individual screens added over time to protect themselves are removed.

Purpose / Big Picture

The main thread builds and lays out the screen. Work that is not drawing, such as turning a provider's response into posts, delays frames when it runs there. In Kotlin, a suspend function is expected to be main-safe: callable from the main thread without blocking it, because the function itself moves its heavy work to a background thread.

The source adapters do not meet that expectation. They wait for the HTTP response without blocking, but then continue on whatever thread called them and parse there. Whether parsing happens off the main thread is therefore decided by each caller. For You, related posts, comments, tag counts and the Viewer wrap their calls in a background dispatcher. Search, Followed Codex and Creator profiles did not, which was audit finding A1.

A1 fixed those three callers. This plan removes the cause: adapters become main-safe at their entry points, a test proves it for every capability of every adapter, and a runtime check reports any source request that starts on the main thread. A developer can then write adapter.search(...) from a ViewModel and get the right behaviour without knowing any of this.

Context And Orientation

  • Source adapter: one class per provider in core-sources. Every adapter implements SourceAdapter and any of ten optional capability interfaces (creator posts, comments, related posts, tag counts and so on), all declared in core-domain/src/main/kotlin/com/theoriacodex/domain/adapter/SourceAdapter.kt. Together they declare about 25 suspend functions.
  • Registry: SourceAdapterRegistry.adapterFor(sourceKey) returns the adapter object. Callers find capabilities by type test, for example registry.adapterFor(source) as? CommentsSourceAdapter (24 such tests in 13 files under app/src/main).
  • Dispatcher: the coroutine setting that decides which thread pool runs a piece of code. Dispatchers.Default is the background pool for computation.
  • Custom Sites: user-added sources served by family adapters in core-sources/.../custom/Families.kt. The repository's cross-source parity rule requires them to get the same treatment.

Design

One wrapper at every adapter entry point

A single helper in SourceAdapterCommon.kt:

/** Runs source work off the main thread. Every public suspend entry point of an adapter starts with this. */
internal suspend fun <T> sourceCall(block: suspend CoroutineScope.() -> T): T =
    if (coroutineContext[ContinuationInterceptor] is MainCoroutineDispatcher) withContext(Dispatchers.Default, block)
    else coroutineScope(block)

Each override suspend fun in an adapter becomes = sourceCall { … }. Called from the main thread, the body moves to the background pool and the result is delivered back to the caller. Called from a background or test dispatcher, it runs in place, so existing callers pay nothing and adapter tests keep their virtual time. MainCoroutineDispatcher is part of the coroutines core library, so the plain Kotlin module can test for it without Android classes. Entry points that only build a value from their arguments (no request, no parsing) may stay unwrapped with a one-line comment saying so.

Phase 0 checks this choice against the conventional alternative, an unconditional withContext(dispatcher) with the dispatcher injected into each adapter. The conventional form is stricter but adds a constructor parameter to every adapter and makes delays inside adapters real in tests.

A contract test instead of a convention

A convention across 80 functions will be forgotten. A test in core-sources builds every adapter with a fake HTTP client and calls each capability function from a single-thread dispatcher that extends MainCoroutineDispatcher and so stands in for the main thread. The fake client fails the test if it is reached on that thread and otherwise throws a marker exception, which the test treats as success. No real responses are needed. The call table has one row per interface function (about 25) and applies to every adapter that implements the interface, so a new adapter is covered by adding it to the adapter list.

A runtime check at the one place all sources pass through

DefaultSourceHttpClient calls OffMainWork.note("source-http") where a request starts. After this plan, a source request that starts on the main thread means an entry point is missing its wrapper, or something outside the adapters (a sign-in flow, for example) is using the client from the main thread and will parse there too. Either is reported once with a stack and fails the benchmark gate on exercised paths.

Remove the per-caller switches that only protected adapter calls

For each candidate in the table above: if the block inside withContext(...) contains only adapter calls, remove the switch and the constructor parameter that fed it. If it also does the caller's own computation, leave it and write why in the Decision Log.

Alternatives considered and rejected

AlternativeWhy not
Parse inside the HTTP read callback, which already runs on OkHttp's thread.Every request site in every adapter would have to move its parsing and post-processing into a lambda, a larger rewrite than wrapping entry points, and it would run CPU work on OkHttp's dispatcher threads.
Have the registry return wrapping objects.Callers find capabilities with as?. A wrapper that does not implement the same interfaces makes those tests return null and features disappear silently. Avoiding that needs either one decorator per capability plus a new accessor at all 24 call sites, or a reflection proxy, which is fragile under R8 and with default interface methods.
Keep the rule in callers and add a lint check.This is the current state plus policing. It keeps the knowledge in the wrong layer.

Work Plan

  1. Add sourceCall to core-sources/.../common/SourceAdapterCommon.kt with the comment shown above.
  2. Add core-sources/src/test/kotlin/com/theoriacodex/sources/AdapterMainSafetyContractTest.kt: the stand-in main dispatcher, the fake SourceHttpClient, the adapter list, and the call table keyed by capability interface. Reuse the argument builders the existing adapter tests already have.
  3. Wrap entry points adapter by adapter, one commit per group: Danbooru and Gelbooru; the three Rule34 adapters and their abstract base; Pixiv; Nhentai; Hitomi; Iwara; Custom Sites families. In each, wrap the public override suspend fun only; private helpers stay as they are. Where one entry point calls another on the same adapter the inner wrapper runs in place, so nesting is harmless.
  4. Hitomi's caches use withContext(NonCancellable) and their own IO scope. Leave them; the wrapper goes around the adapter entry points that reach them.
  5. Add OffMainWork.note("source-http") at the start of the request path in core-sources/.../http/DefaultSourceHttpClient.kt. Keep the source-parse markers that the observability plan added to the parse helpers.
  6. For each caller in the Context table, read the withContext block. Remove the switch and its dispatcher parameter when the block is only adapter calls; update the caller's tests if they passed a test dispatcher for that parameter. Record each decision.
  7. Update the class comment on SourceAdapter in core-domain to state the contract: every suspend function is safe to call from the main thread.

Not touched: UnifiedSearchOrchestrator's own switch, ForYouCoordinator's ranking, the registries, the capability as? pattern, and the data layer (Room repositories already move their work off the main thread and Room's blocking calls assert against it).

Decision Log

  • Decision: Switch only when the caller is on a main dispatcher, pending Phase 0. Rationale: no cost for callers already in the background, no constructor changes, virtual time preserved in tests. Date/Author: 2026-11-15 / Claude.
  • Decision: Keep the orchestrator's own background switch. Rationale: it merges pages, which is its own work, and it is a shared layer rather than a per-screen workaround. Date/Author: 2026-11-15 / Claude.

Idempotence And Recovery

No data, schema or stored setting changes. Each adapter group is its own commit and can be reverted alone; a half-converted state is safe because unconverted adapters behave as they do today and callers keep their switches until Phase 3. Phase 3 is the only step that removes protection, so it lands last and in one commit that can be reverted without touching the adapters. If the contract test proves flaky on one adapter, exclude that adapter with a comment naming the reason rather than weakening the fake client.
