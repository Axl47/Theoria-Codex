ExecPlan: Catch main-thread work automatically

After this plan, work that has been declared "background only", starting with parsing provider responses, fails an automated emulator test the moment it runs on the main thread, and is logged with its call site in every build. Debug builds also report disk access on the main thread. A later, separately gated phase adds slow-frame counts per screen. Today none of this is checked: the same class of problem has been found by reading code and fixed screen by screen.

Purpose / Big Picture

An Android app draws on two threads. The main thread runs Compose (building and laying out the screen), input handling, and in this app every video player call. RenderThread turns what the main thread recorded into pixels. Other work that lands on the main thread, such as parsing a provider's JSON response, delays the next frame.

A threading audit on 2026-11-15 found such work in seven places (findings A1 to A7, fixed separately). Nothing would have caught them: the journey and benchmark fixtures hand back ready-made posts, so no test ever parses a response; there is no StrictMode (Android's detector for disk and network access on the main thread); and the diagnostics log records failures, not threading.

This plan has one required outcome and two smaller ones:

  • A gate. Shared code marks the work that must not run on the main thread. An emulator journey test drives a search through a real source adapter and fails unless that marked work ran, and ran off the main thread. The test runs automatically on every push to main. The two refactors that follow (B1 source boundary, B2 feed presenter) add their own markers and are held to the same test.
  • A log line in real use. In every build, the first time each distinct call site runs marked work on the main thread, the diagnostics log and logcat record it.
  • Debug detectors. Debug builds report disk reads and writes on the main thread.

Slow-frame counts per screen are designed here but ship only to non-production builds until their cost has been measured on the phone. A watchdog that samples the main thread during long stalls was considered and is not part of this plan; the reasons are in the Decision Log.

Design

1. The contract marker

A new object in core-domain, OffMainWork, with one call: OffMainWork.note(label). Labels come from a fixed set of constants on that object (SOURCE_PARSE first), never from data. The call goes where background-only work actually executes, for example the first line of a parse helper. It does not go at the start of a suspend function that callers may legitimately invoke from the main thread before it switches dispatcher.

With no checker installed the call is one volatile read. The app installs a checker when the process starts, in every process of the app, that:

  • emits a trace section OffMain:<label> on every call and, when the calling thread is the main thread, OffMainViolation:<label> as well, so a trace or benchmark can count both;
  • on a main-thread call, writes one logcat line (tag TheoriaThreads) and one Diagnostics report (area main-thread) per distinct call site, identified by the label plus the first stack frame outside the marked helper. At most twenty call sites are reported per process; after that one line says the limit was reached. The Diagnostics part only exists in the main process, where the sink is installed.

The checker never throws. In release builds the reported stack is obfuscated; the label and the first frame are enough to find the site with the release's mapping file, and debug and journey runs give readable stacks.

2. Call sites in this plan

The three shared JSON helpers, the two Hitomi JSON sites, and one new shared helper pair in SourceAdapterCommon.kt, parseHtml and parseXml, which call note and then Jsoup. The direct Jsoup calls listed in Context are routed through that pair. Later plans add their own: B1 keeps these and adds none at adapter entry points; B2 adds one inside the feed presenter; the A2 fix's GIF frame renderer can take one when it lands.

3. The gate: a journey test through a real parser

A new journey test serves one fixture source through a real adapter instead of the ready-made one. JourneySourceRegistry gains an optional parameter naming sources to serve that way; for those it constructs the real adapter (Danbooru, whose post JSON is flat, unless implementation finds a simpler one) with a small in-memory SourceHttpClient. That client answers the adapter's post-search request with JSON generated from the fixture posts, honouring the adapter's real limit and page parameters, and passes every other request to the client the container already uses. Media stays local: the adapter's URL handling passes non-HTTP locations through unchanged (SourceAdapterCommon.kt :299-305). No provider data is recorded or stored.

The test installs a recording checker, opens Search on that source, and scrolls until two further pages have loaded. It then asserts all of:

  • the in-memory client received three requests with three distinct page parameters;
  • the recording checker saw at least three SOURCE_PARSE calls;
  • none of them was on the main thread;
  • posts from the third page are displayed (by accessibility text).

A second, tiny test in the same class is a permanent control for the plumbing: it calls OffMainWork.note on the main thread and asserts the checker recorded a main-thread call.

A host test keeps the JSON generator honest: it runs generated JSON through the adapter and compares the resulting posts with the fixture posts, so a parser change that would empty the journey fails on the host first.

4. StrictMode in debug builds

Debug builds extend the main thread's existing policy rather than replacing it, so Android's default network-on-main protection stays: StrictMode.ThreadPolicy.Builder(StrictMode.getThreadPolicy()).detectDiskReads().detectDiskWrites().penaltyListener(executor, listener). The listener reports each distinct topmost app frame once (area strictmode, plus logcat), with the same cap of twenty. StrictMode sees disk access performed on the main thread. It does not see the main thread waiting for another thread's disk access, which is what finding A5 was.

5. Slow frames per screen (non-production until measured)

A recorder counts, per screen and per foreground session, frames observed, slow frames and the worst frame, and writes one line per screen when the activity stops, only for screens that had slow frames. The screen name is the navigation route pattern plus, on home, the active pager tab, from a fixed vocabulary; no query or post id reaches the log.

Frame data comes from AndroidX JankStats (androidx.metrics:metrics-performance) if a stable release exists when this phase starts, because it already handles what a hand-written listener gets wrong: callbacks the platform drops, the reused metrics object, the always-long first draw, unavailable values, and a jank rule that does not flag frames that still met their deadline. If no stable release exists, the phase uses Window.addOnFrameMetricsAvailableListener with those five rules written out and tested.

A build flag turns the recorder on in debug, releaseAcceptance and benchmarkRelease only. Turning it on for the production package is a separate decision that needs a same-APK comparison on the phone (frame percentiles and idle CPU with the recorder on and off) and a look at how many log lines a week of real use produces.

Limits. Frames drawn in separate windows (dialogs, popups, some bottom sheets) are not counted. Frame data arrives a little late, so frames during a transition can be credited to the neighbouring screen. Frame time includes rendering, but cannot say whether a slow frame was caused by the main thread or by RenderThread.

Decision Log

  • Decision: The required outcome is a threading gate for annotated work, not a production performance monitor. Rationale: both reviews showed the monitor's signals could not serve as acceptance for the other findings, and its cost on the production package was argued by analogy, not measured. Date/Author: 2026-11-15 / Claude.
  • Decision: The gate is an emulator journey test, not a macrobenchmark metric. Rationale: journeys run on every push to main; the macrobenchmark does not run automatically and its contract would break. Date/Author: 2026-11-15 / Claude.
  • Decision: Markers sit where background-only work executes, never at suspend entry points. Rationale: a main-safe suspend function is correctly called from the main thread; marking its entry would report correct code. Date/Author: 2026-11-15 / Claude.
  • Decision: The gate needs positive evidence (pages requested, parses counted) and two recorded negative controls. Rationale: a count of zero violations also describes a test that parsed nothing. Date/Author: 2026-11-15 / Claude.
  • Decision: Report per call site with a cap, not once per label. Rationale: one old offender would otherwise hide every new one. Date/Author: 2026-11-15 / Claude.
  • Decision: Drop the stall watchdog. Rationale: it measures delayed message delivery, not a cause; its detection window is loose; it wakes the main thread ten times a second on the production package; and its stacks would be obfuscated. ANR traces and Perfetto remain the tools for stalls. Revisit only with release mapping files retained and a measured wake-up budget. Date/Author: 2026-11-15 / Claude.
  • Decision: Frame recording is off in production builds until measured on the phone. Rationale: capping log lines does not cap monitoring cost, and frequent lines would push failures out of a 256 KB log. Date/Author: 2026-11-15 / Claude.
  • Decision: Prefer JankStats over a hand-written frame listener if a stable release exists. Rationale: review listed five platform pitfalls the library already handles. This reverses the first draft. Date/Author: 2026-11-15 / Claude.
  • Decision: StrictMode extends the existing thread policy. Rationale: a fresh policy would drop Android's network-on-main protection. Date/Author: 2026-11-15 / Claude.
  • Decision: Generate provider-shaped JSON from fixture posts instead of recording real responses. Rationale: no provider content in the repository; local media. Date/Author: 2026-11-15 / Claude.

Idempotence And Recovery

Nothing here migrates data or deletes anything. Every phase is additive and can be reverted by reverting its commit. The diagnostics log format is unchanged. The negative controls modify the working tree temporarily: undo exactly the recorded patch (git apply /tmp/a1.patch) or the single edited line, and confirm with git status --short that nothing else changed; do not use a blanket checkout. Instrumented-test reports that serve as acceptance evidence are kept until the phase's pull request has merged, then pruned as AGENTS.md describes.
