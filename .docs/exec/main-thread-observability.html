Purpose / Big Picture

An Android app draws on two threads. The main thread runs Compose (building and laying out the screen), input handling, and in this app every video player call. RenderThread turns what the main thread recorded into pixels. Other work that lands on the main thread, such as parsing a provider's JSON response, delays the next frame.

A threading audit on 2026-11-15 found such work in seven places (findings A1 to A7, fixed separately). Nothing would have caught them: the journey and benchmark fixtures hand back ready-made posts, so no test ever parses a response; there is no StrictMode (Android's detector for disk and network access on the main thread); and the diagnostics log records failures, not threading.

This plan delivers three things:

  • A marker and a gate. Shared code marks the work that must not run on the main thread. An emulator journey test drives a search through a real source adapter and fails unless that marked work ran, and ran off the main thread. The test runs automatically on every push to main.
  • A log line in real use. In every build, the first time each distinct call site runs marked work on the main thread, the diagnostics log and logcat record it.
  • A debug detector. Debug builds report disk reads and writes on the main thread.

The gate covers the Search path and nothing else. The two refactors that follow extend it for their own work: the source-boundary plan adds device tests that call sources directly from the main thread, and the feed-presenter plan must assert that its presenter ran and never on the main thread. Adding a marker without such an assertion gives logging, not a gate.

Two things from earlier drafts are not in this plan: slow-frame counts per screen, and a watchdog that samples the main thread during stalls. The reasons are in the Decision Log.

Design

1. The contract marker

A new object in core-domain, OffMainWork, with note(label) and install(checker). Labels are constants on the object (SOURCE_PARSE, and SELF_TEST for the control), never data. install returns the checker it replaced, so a test can wrap the app's checker and put it back. The call goes where background-only work executes, for example the first line of a parse helper, never at the start of a suspend function that callers may correctly invoke from the main thread before it switches.

With no checker installed, note is one volatile read. The app installs its checker next to startDiagnostics(), in the main process only (no other process calls an adapter). Off the main thread the checker does nothing. On the main thread it:

  • increments a per-label counter that is never capped;
  • for the first twenty distinct call sites in the process, captures a stack, writes one logcat line (tag TheoriaThreads) and one Diagnostics report (area main-thread). A call site is identified by the label and the stack's top frames below note. After twenty, it writes one line saying the limit was reached and stops capturing stacks, so a repeating violation costs a counter increment.

The checker never throws. In minified builds the frames are renamed and distinct callers can merge into one identity; there the report means "a violation exists under this label", to be reproduced in a debug build, where stacks are readable. That limitation is accepted and not tested.

2. Call sites in this plan

The three shared JSON helpers; three new helpers beside them, parseHtml, parseXml and parseHtmlFragment, which call note and then the matching Jsoup function; every site in the Context table routed through one of those six (the Hitomi sites and ProbeEvidence may call note directly if a helper does not fit); and one note in PixivUgoiraPlayer's parse.

3. The gate: a journey test through a real parser

Fixture. JourneySourceRegistry gains an optional parameter naming sources to serve through a real adapter. For those it constructs DanbooruSourceAdapter with a small in-memory SourceHttpClient that keeps a request log. AppJourneyFixture gains hooks for that parameter and for the post list. The gate's posts are provider-compatible: 100 posts with numeric ids and local image files as media, so three pages of 40 exist. The in-memory client answers /posts.json with JSON generated from those posts, honouring limit and both paging forms (page=N and the b<id> cursor), and passes other requests to the container's existing client. The adapter passes non-HTTP media locations through unchanged (SourceAdapterCommon.kt :299-305). No provider data is recorded or stored.

Test. It installs a recorder that counts calls and threads per label and forwards every call to the app's checker, and restores the app's checker afterwards. It opens Search on that source with the default newest-first order, and scrolls (using the scroll helper moved from SearchNavigationJourneyTest into AppJourneyFixture) until the request log shows three distinct page values. It then asserts:

  • at least three distinct page values among /posts.json requests;
  • at least as many SOURCE_PARSE calls as responses served;
  • no SOURCE_PARSE call on the main thread;
  • a card for a known third-page post exists, found by its test tag (searchCardTestTag(PostId(source, id))).

Permanent control. A second test calls OffMainWork.note(SELF_TEST) on the main thread and asserts that the app's checker counted it and that a main-thread report reached the diagnostics sink. This proves on a device that startup installs the real checker, its main-thread detection works and its reporting path is connected.

Generator check (host). A host test runs generated JSON through the adapter and compares what the parser can carry: ids, tags, media location and the next-page token. A parser change that would empty the journey fails on the host first.

4. StrictMode in debug builds

Debug builds extend the main thread's existing policy, so Android's network-on-main protection stays: StrictMode.ThreadPolicy.Builder(StrictMode.getThreadPolicy()).detectDiskReads().detectDiskWrites().penaltyListener(executor, listener). The listener counts every violation and reports each distinct topmost app frame once (area strictmode, plus logcat), up to twenty. StrictMode sees disk access performed on the main thread. It does not see the main thread waiting for another thread's disk access, which is what finding A5 was.

Outcomes And Retrospective

Phases 1 and 3 (2026-11-16): marked work on the main thread is counted and reported per call site in every build, every provider-response parse is marked, and debug builds report main-thread disk access. Both are proven on the emulator through the app's real startup: the control test's report reached the diagnostics log and logcat, and a test disk read was counted at the test's own frame while network on main still threw. The first real use already found one site (app lock).

Phase 2 (2026-11-16): a Search through the real Danbooru parser now fails an emulator test if any marked parse runs on the main thread, and fails if it pages fewer than three times, parses fewer bodies than it served, or never shows a third-page card. Both negative controls turned it red on the expected assertion: main-thread provider calls on the main-thread count, a provider that repeats its first page on the third-page card. The gate covers Search only. The journey runs in about 75 seconds on the emulator, most of it dragging to card 82. What remains is its first run in the Main workflow after merge.

Idempotence And Recovery

Nothing here migrates or deletes data. Every phase is additive and can be reverted by reverting its commit. The negative controls are one-line edits in fixture code: undo them and confirm with git status --short that nothing else changed. Instrumented-test reports that serve as acceptance evidence are kept until the phase's pull request has merged, then pruned as AGENTS.md describes.

Round 2: coverage stated as Search only; negative control uses A1's dispatcher parameter; fixture made compatible with the Danbooru adapter (numeric ids, 100 posts, id cursor) with hooks in AppJourneyFixture; cards found by test tag and pages by the client's request log; the recorder forwards to and restores the app's checker and the control exercises the real one; behaviour after the reporting limit defined and the mapping-file claim removed; fragment parsing preserved and missing parse sites added; checker installed in the main process only with no trace sections; frame counts dropped.

Parse sites that call note directly

Every Jsoup site in the Context table now calls parseHtml, parseXml or parseHtmlFragment (CommentText keeps fragment parsing), and the Danbooru error body goes through parseJsonObject inside its existing runCatching. Four sites call OffMainWork.note(SOURCE_PARSE) directly because a helper does not fit:

  • hitomi/HitomiProtocol.kt parseJson: uses JsonParser.parseString and its own HitomiProtocolException.
  • hitomi/HitomiPageTokenCodec.kt decode: deserializes a typed token class, not a JsonElement.
  • custom/ProbeEvidence.kt jsonBody: returns null on malformed input instead of throwing.
  • app/.../viewer/PixivUgoiraPlayer.kt parseMetadata: in the app module, outside core-sources' helpers.

Not marked: health/ProviderHealth.kt :196 (and its caller ProviderHealthCheckCli.kt :126) parses the health-check CLI's case file, not a provider response, and never runs in the app. After routing, grep -rn "Jsoup\.\|JsonParser\.\|fromJson" core-sources/src/main finds only the helpers, the direct sites above and that case-file parse.
