ExecPlan: Make main-thread work visible

After this plan, the app reports on its own when the main thread does work that is not drawing the screen. Work that has been declared "background only" is logged the first time it runs on the main thread and fails a benchmark gate. Every build records how many slow frames each screen produced and what the main thread was doing during long stalls, in the existing on-device diagnostics log. Debug builds also log disk access on the main thread. Today none of this is visible without attaching a profiler, which is why the same class of problem has been fixed screen by screen.

Purpose / Big Picture

An Android app draws on two threads. The main thread runs Compose (building and laying out the screen), input handling, and in this app every video player call. RenderThread turns what the main thread recorded into pixels. Any other work that lands on the main thread, such as parsing a provider's JSON response, delays the next frame.

A threading audit on 2026-11-15 found such work in seven places (findings A1 to A7, fixed separately). The common cause was that nothing detects it: the frame benchmarks use test sources that hand back ready-made posts, so they never parse anything; there is no StrictMode (Android's detector for disk and network access on the main thread); and the diagnostics log records failures, not slowness.

When this plan is complete:

  • A developer who accidentally calls a source or a feed computation from the main thread sees a main-thread line in logcat and in the diagnostics log, with the stack that did it, and the macrobenchmark gate fails.
  • The diagnostics report from any install, including the daily-driver phone, shows per screen how many frames were slow and the stack of any main-thread stall of roughly 150 ms or more.
  • The three larger refactors that follow (B1 source boundary, B2 feed presenter, B3 player thread) can be judged against these signals instead of ad hoc traces.

Context And Orientation

Terms used below:

  • Source adapter: one class per provider (Danbooru, Pixiv, and so on) in the core-sources module. It makes HTTP requests and parses the response into the app's Post model.
  • Diagnostics log: a private, bounded, redacted on-device log (DiagnosticLogStore). Code anywhere calls Diagnostics.report(area, message, error); the store writes on its own thread and collapses repeated lines. The user can export it from the app.
  • Fixture: test data built into the benchmark and debug builds (app/src/fixtures), so journeys run without a network or provider media.
  • Macrobenchmark: the macrobenchmark module drives the benchmark build on a device and records frame timings and named trace sections.
  • Build types: debug (com.theoriacodex.debug), release and personalRelease (com.theoriacodex, production, never used for tests), releaseAcceptance (com.theoriacodex.acceptance, a release-equivalent build for emulator checks), benchmarkRelease (com.theoriacodex.benchmark, includes fixtures).

Design

1. A contract marker for work that must not run on the main thread

A new object in core-domain, OffMainWork, with one call: OffMainWork.note("source-parse"). Shared code calls it at the start of work that is background-only by contract. With nothing installed it is a single volatile read. The app installs a checker at startup that asks Android whether the current thread is the main thread and, if so:

  • reports the first occurrence per label per process to Diagnostics (area main-thread) with a stack, and to logcat under the tag TheoriaThreads; later occurrences only increment a counter that is written with the frame summary;
  • emits a trace section named OffMainViolation:<label>, so the macrobenchmark can count it.

The checker is installed in every build type. It never throws: a contract breach should be reported, not crash a user's session. Unit tests can install a throwing checker where a test wants a hard failure.

First call sites are the JSON parse helpers listed in Context. Plan B1 later moves the marker to the adapter entry points, and B2 adds one to the feed presenter.

2. Slow frames per screen

Android reports timing for every frame an activity's window draws (Window.addOnFrameMetricsAvailableListener, delivered on a background handler). A small recorder counts, per visit to a screen: frames, slow frames (total duration above the frame's deadline), frozen frames (above 700 ms) and the worst duration. When the screen changes or the activity stops, a visit with at least one slow frame is written as one line, for example frames | Search: 5432 frames, 61 slow (1.1%), 0 frozen, worst 212 ms.

The platform API is used directly instead of the AndroidX JankStats library: the app's minimum is API 36, where the platform already supplies the deadline, so the library would add a dependency for a few dozen lines. The screen name is the navigation route pattern (such as viewer), never a filled-in route, so no query or post id reaches the log.

3. Stacks for long main-thread stalls

Frame counts say how often; they do not say why. A watchdog thread posts a marker to the main thread every 100 ms while an activity is started. If the marker has not run by the next tick, the main thread has been busy for at least that long, so the watchdog samples the main thread's stack once and, when the marker finally runs, reports main-stall | Main thread busy 340 ms on Search with that stack. Reports are capped at 20 per process and skipped while a debugger is attached. Short stalls of one or two frames are below this detector's reach; Perfetto traces remain the tool for those.

4. StrictMode in debug builds

Debug builds set a main-thread StrictMode policy that detects disk reads and writes, and report violations whose stack contains an app frame (com.theoriacodex) to Diagnostics (area strictmode) and logcat. Network access on the main thread already throws on Android, and Room already asserts, so disk access is the gap. Framework-only stacks are dropped because they cannot be fixed here.

5. A benchmark that parses

One fixture source is served by a real adapter instead of the ready-made one: DanbooruSourceAdapter constructed with a fixture SourceHttpClient that answers the post-search request from memory with Danbooru-shaped JSON generated from the existing fixture posts (same local media, realistic tag counts so the payload size is representative). No real provider data is recorded or stored. A new macrobenchmark scenario pages through that source's search results and records frame timing plus the count of OffMainViolation:% sections. scripts/benchmark_results.py fails the run when that count is above zero.

If the generated JSON ever drifts from what the parser accepts, the adapter returns no posts and the scenario's existing "all visible videos are playing" check fails, so the fixture cannot silently stop exercising the parser.

What this does not do. It does not measure RenderThread work (texture uploads, video surface composition) and it does not find unannotated work shorter than about 150 ms. Those still need a trace.

Surprises And Discoveries

  • Observation: personalRelease has no application-id suffix, so it is the production package. Evidence: app/build.gradle.kts build types. Consequence: frame and stall reporting had to be safe for the daily-driver install, which is why it is bounded and always on rather than a debug feature.

Decision Log

  • Decision: Reporting is on in every build type except StrictMode. Rationale: the diagnostics log is already designed to stay on permanently, a single code path is simpler than a build-type matrix, and the acceptance build can then prove the same code that ships. Date/Author: 2026-11-15 / Claude.
  • Decision: Use platform frame metrics, not JankStats. Rationale: minimum API 36 already provides the frame deadline. Date/Author: 2026-11-15 / Claude.
  • Decision: The contract check reports and never throws. Rationale: a threading breach must not crash a session. Date/Author: 2026-11-15 / Claude.
  • Decision: Generate provider-shaped JSON from fixture posts instead of recording real responses. Rationale: no provider content in the repository, and deterministic local media. Date/Author: 2026-11-15 / Claude.

Idempotence And Recovery

Nothing here migrates data or deletes anything. Every phase is additive and can be reverted by reverting its commit. The diagnostics log format is unchanged, so old and new builds read each other's logs. If the benchmark scenario is flaky on the emulator, it can be excluded from the gate without affecting the other phases. The local build with the A1 switch removed exists only to prove the detector; discard it with git checkout -- . and never commit it. Benchmark and trace output under build/reports/ is pruned once the evidence is recorded here.
