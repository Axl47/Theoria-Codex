Purpose / Big Picture

The app already has a stable application-owned container, route-scoped ViewModels, durable quality gates, and strong provider protocol tests. Recent Search, Settings, mixed-media, and Hitomi work has nevertheless concentrated responsibility back into several large boundaries. This increases the chance that a change to one surface triggers unrelated recomposition, duplicated persistence, stale state, memory pressure, or a regression that current CI cannot observe.

After this plan, browsing should remain visually familiar but feel steadier during media-heavy scrolling. Search will have one authoritative state owner. Each destination will observe only the state it needs. Recents and UI restore data will have clear durable owners. Hitomi random search will have a bounded memory model. CI will execute every instrumentation suite it compiles, and performance will be tracked with numbers rather than intuition.

No rewrite: retain the application container, explicit provider adapters, route ViewModels, existing navigation and persistence contracts, and the current autoplay product behavior. Repair ownership at the narrowest durable seam.

Context And Orientation

A route owner is the ViewModel that owns one destination's jobs and immutable render state. A single-flight operation lets only one request for the same logical item proceed and lets callers share its result. A Macrobenchmark drives the built app from another process and records startup or rendered-frame timing. A visible card is a card intersecting the active feed viewport; cards retained outside the viewport may be paused or released.

Non-Negotiable Product And Execution Constraints

  • Concurrent autoplay remains: every visible video or animated card in Search, For You, Creator Profile, Recents, and Codex must autoplay simultaneously. Do not implement one active preview, tap-to-play, or an autoplay-off default.
  • It is acceptable to pause/release cards only after they leave the visible viewport, the destination stops, or the app lifecycle stops. Returning cards must resume automatically without a tap.
  • Preserve route IDs, query hashes, page tokens, saved state, source headers, authentication, and fail-closed explicit-provider behavior.
  • Use authoritative provider metadata or raw record counts for pagination. Never infer exhaustion from hydrated/deduplicated visible counts.
  • Implement findings sequentially. Do not begin the next finding before focused verification and a commit for the current finding.
  • Update this ExecPlan and working_list.md in every finding commit. Record surprises and deviations immediately.
  • Do not push, tag, publish, or create a release unless separately authorized.
  • Do not report emulator, stub, compilation, or baseline-profile generation as physical-device performance proof.

Work Plan And Commit Protocol

  1. Before each finding, re-read its current files and tests because prior commits may have changed the recommended seam.
  2. Move only that finding to [~] in working_list.md; keep later findings pending.
  3. Implement the smallest complete behavior, including migrations and cleanup required to leave one owner. Do not leave a second production path “temporarily” writable.
  4. Run the focused test lane named in the finding/phase. Repair root causes in one coherent patch.
  5. Update this ledger status, Progress, Surprises, Decision Log, and the working-list evidence before committing.
  6. Review git diff --check, git status --short, and the exact staged diff. Do not stage generated reports or unrelated changes.
  7. Create one Conventional Commit for the finding using the suggested message or a more accurate user-facing equivalent. Include concise body bullets for multi-file findings.
  8. Record the commit SHA and verification evidence in this plan. Only then begin the next finding.
If a later finding exposes a defect in an earlier commit: create a separate focused fix(...) commit. Do not rewrite, squash, or silently amend the earlier finding history.

The owner now refreshes only after a successful write or a store failure, and focused tests hold both validation and recovery labels at the observable boundary.
  • Observation: production has a file-backed applied-query store and a DataStore-backed UI-restore store; there is no second DataStore query repository. The legacy offset format was the scrollOffsets member embedded in query_store.json, so the safe migration seam is a UI DataStore migration that retains the live queries object while atomically removing only that legacy member.
  • Observation: ViewModel teardown offers no suspending completion hook, and viewModelScope is cancelled during clear. A reliable last-position flush therefore needs an independently owned scheduler plus a synchronous close acknowledgement; a coroutine mutex is required so close joins a write that already entered its non-cancellable durable section instead of duplicating it.
  • Observation: a fixed first-eight duration batch can permanently starve later posts when early probes return unknown, and ignoring same-session requests while a batch runs can miss appended pages. F06 therefore keeps attempted IDs per route identity and drains the latest owner snapshot until no unattempted candidates remain.
  • Observation: a unique permutation of source positions is insufficient when a Nozomi file repeats raw gallery IDs. F07 canonicalizes a copied primitive snapshot with sort/dedupe before fingerprinting and permutation, so continuation pages cannot repeat the same raw ID and shared inline/global arrays are never mutated.
  • Observation: the release R8 verifier task currently declares the obsolete outputs/mapping/release/mapping.txt path. AGP 9.1.1 produced the text mapping under intermediates/mapping/release/minifyReleaseWithR8/ and a mapping.prt output; the verifier passed manually against the actual mapping and seeds, but the Gradle task wiring remains a separate build-tooling gap.
  • Observation: the live AtomicJsonFileStore owners are applied queries, Recents activity, updater state, and tag suggestions. Codex/Likes are Room-backed and Settings/UI restore are DataStore-backed; those newer-schema and migration contracts remain separate from legacy whole-file quarantine.

  • Decision: preserve simultaneous autoplay for every visible media card. Rationale: it is an intentional browsing affordance; optimization must reduce cost without reducing information available while scanning. Date/Author: 2026-07-31 / User and Codex.
  • Decision: execute findings serially with one focused commit each. Rationale: the changes cross state, persistence, media, Room, and CI boundaries; independent commits preserve reviewability, rollback, and regression attribution. Date/Author: 2026-07-31 / User and Codex.
  • Decision: measure playback before optimizing it. Rationale: multiple simultaneous decoders are inherently device-sensitive, so player-count intuition is not acceptance evidence. Date/Author: 2026-07-31 / Codex.
  • Decision: Coil 3 and configuration cache remain evidence-gated migrations. Rationale: modernization is valuable only if protected media behavior and build reliability stay intact. Date/Author: 2026-07-31 / Codex.
  • Decision: source API-key fields are replace-only. Rationale: Settings can communicate configured state and preserve existing credentials without ever restoring durable secrets into Compose state; only a nonblank replacement crosses from UI into the encrypted store. Date/Author: 2026-07-31 / Codex.
  • Decision: Search owner teardown waits synchronously for the final UI-restore write and then cancels its owned scheduler. Rationale: a timeout or a launch in cancelled viewModelScope would make final scroll persistence unprovable; the deliberate cost is a main-thread teardown wait bounded in practice by one storage operation, with repository failure surfaced rather than abandoned. Date/Author: 2026-07-31 / Codex.
  • Decision: animated-duration enrichment is one application service with route-owned identity lanes. Rationale: application ownership deduplicates the same post across routes and bounds network/retriever work, while route ownership alone can safely coalesce pagination and reject stale query/seed completions without changing autoplay behavior. Date/Author: 2026-07-31 / Codex.
  • Decision: Hitomi random continuation uses affine permutation algorithm v1 over one canonical primitive snapshot. Rationale: a coprime multiplier proves a bijection for every positive list size without retaining a shuffled copy per seed; mixed seed coefficients provide deterministic spread, and the v4 token fails closed if the query, snapshot, algorithm, or global-index version changes.
