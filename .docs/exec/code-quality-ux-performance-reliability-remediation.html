Purpose / Big Picture

The app already has a stable application-owned container, route-scoped ViewModels, durable quality gates, and strong provider protocol tests. Recent Search, Settings, mixed-media, and Hitomi work has nevertheless concentrated responsibility back into several large boundaries. This increases the chance that a change to one surface triggers unrelated recomposition, duplicated persistence, stale state, memory pressure, or a regression that current CI cannot observe.

After this plan, browsing should remain visually familiar but feel steadier during media-heavy scrolling. Search will have one authoritative state owner. Each destination will observe only the state it needs. Recents and UI restore data will have clear durable owners. Hitomi random search will have a bounded memory model. CI will execute every instrumentation suite it compiles, and performance will be tracked with numbers rather than intuition.

No rewrite: retain the application container, explicit provider adapters, route ViewModels, existing navigation and persistence contracts, and the current autoplay product behavior. Repair ownership at the narrowest durable seam.

Context And Orientation

A route owner is the ViewModel that owns one destination's jobs and immutable render state. A single-flight operation lets only one request for the same logical item proceed and lets callers share its result. A Macrobenchmark drives the built app from another process and records startup or rendered-frame timing. A visible card is a card intersecting the active feed viewport; cards retained outside the viewport may be paused or released.

Non-Negotiable Product And Execution Constraints

  • Concurrent autoplay remains: every visible video or animated card in Search, For You, Creator Profile, Recents, and Codex must autoplay simultaneously. Do not implement one active preview, tap-to-play, or an autoplay-off default.
  • It is acceptable to pause/release cards only after they leave the visible viewport, the destination stops, or the app lifecycle stops. Returning cards must resume automatically without a tap.
  • Preserve route IDs, query hashes, page tokens, saved state, source headers, authentication, and fail-closed explicit-provider behavior.
  • Use authoritative provider metadata or raw record counts for pagination. Never infer exhaustion from hydrated/deduplicated visible counts.
  • Implement findings sequentially. Do not begin the next finding before focused verification and a commit for the current finding.
  • Update this ExecPlan and working_list.md in every finding commit. Record surprises and deviations immediately.
  • Do not push, tag, publish, or create a release unless separately authorized.
  • Do not report emulator, stub, compilation, or baseline-profile generation as physical-device performance proof.

Work Plan And Commit Protocol

  1. Before each finding, re-read its current files and tests because prior commits may have changed the recommended seam.
  2. Move only that finding to [~] in working_list.md; keep later findings pending.
  3. Implement the smallest complete behavior, including migrations and cleanup required to leave one owner. Do not leave a second production path “temporarily” writable.
  4. Run the focused test lane named in the finding/phase. Repair root causes in one coherent patch.
  5. Update this ledger status, Progress, Surprises, Decision Log, and the working-list evidence before committing.
  6. Review git diff --check, git status --short, and the exact staged diff. Do not stage generated reports or unrelated changes.
  7. Create one Conventional Commit for the finding using the suggested message or a more accurate user-facing equivalent. Include concise body bullets for multi-file findings.
  8. Record the commit SHA and verification evidence in this plan. Only then begin the next finding.
If a later finding exposes a defect in an earlier commit: create a separate focused fix(...) commit. Do not rewrite, squash, or silently amend the earlier finding history.

Idempotence And Recovery

  • Gradle, lint, Detekt, Kover, jscpd, helper tests, and HTML validation are safe to rerun. Generated reports stay ignored and must not be committed.
  • Room and DataStore migrations require fixtures proving first import, repeated startup, partial legacy state, corrupt legacy state, and downgrade/unknown-version behavior before the old store path is removed.
  • Never use destructive Git resets. If a finding fails validation, keep its changes uncommitted, repair the common cause, or restore only the explicitly owned patch with apply_patch.
  • If a device or physical benchmark is unavailable, complete deterministic work but leave that acceptance item pending. Do not substitute compilation or emulator timing.
  • If provider protocol behavior blocks the Hitomi range/permutation design, retain the bounded primitive implementation, record exact evidence, and avoid weakening continuation uniqueness or snapshot validation.
  • To resume, read this plan, working_list.md, AGENTS.md, the latest finding commit, and git status --short. Continue from the first pending finding ID.
