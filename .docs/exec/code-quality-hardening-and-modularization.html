This plan turns the current quality audit into an implementation path: make lint green, make persisted user state resilient to partial writes and future enum changes, move duplicated media/download policy into shared services, reduce TheoriaApp.kt into a composition surface, and add the missing test lanes that make those changes safe.

Purpose / Big Picture

Theoria Codex is now large enough that the main risk is not one bad function. The risk is drift: duplicated download behavior, one huge app junction box, and persistence code that assumes every saved enum value will stay valid forever. This plan keeps the app's behavior stable while improving how the system is divided.

When complete, a developer should be able to make media, persistence, update, deep-link, or navigation changes without re-reading a 3,000-line composition file. Users should keep their saved state even if the app is killed during a write, and future source or sort renames should drop only the invalid persisted record instead of crashing startup. The app should also have a repeatable lint and test gate that catches these regressions before release.

System framing: treat this as a reliability refactor, not a redesign. The visible app should feel the same at the end of each phase; the internal flow becomes easier to reason about.

Context And Orientation

The project is a multi-module Android/Kotlin app. app owns Compose UI and Android integration. core-domain owns shared models and orchestration. core-data owns in-memory and file-backed repositories. core-sources owns live source adapters. core-stubs owns fixture-backed providers for deterministic tests.

A composition root is the place where dependencies and workflows are assembled. In this app that role is mostly app/src/main/java/com/theoriacodex/app/ui/TheoriaApp.kt. A file-backed repository stores app state as JSON files on disk. A media request policy is the set of rules that decide the URL, request headers, filename, MIME type, and Android DownloadManager request used for images, videos, and saved post downloads.

Phases

Phase 1: Restore a Green Lint Gate

Fix the known lint failures and low-risk warnings first. This creates a clean signal before deeper refactors.

Goal./gradlew lint passes on minSdk 26 without suppressing real compatibility problems.
Specific editsReplace API 33-only URL decoding in ExternalPostDeepLinks.kt; replace MediaMetadataRetriever().use in MediaDurationProbe.kt with explicit release; add Media3 @OptIn(UnstableApi::class) around player APIs in ExoVideoComponents.kt and any Search/Viewer usage lint names; migrate LocalLifecycleOwner imports after adding androidx.lifecycle:lifecycle-runtime-compose to the version catalog; remove ambiguous nested return@forEach in Rule34XxxSourceAdapter.kt.
Commands./gradlew lint, then ./gradlew :app:testDebugUnitTest :core-sources:test.
AcceptanceLint has zero errors. Any remaining warnings are either fixed, intentionally deferred with a plan note, or linked to platform deprecations that need a broader replacement.

Phase 2: Harden File-Backed Persistence

Make disk writes atomic and make decode paths tolerant of older or future enum values. The user-visible behavior is that one bad persisted record should not prevent the app from starting or loading the rest of the library.

GoalJSON state writes no longer leave truncated files on crash, and unknown persisted enum values are dropped or defaulted at the smallest safe boundary.
Specific editsAdd a shared atomic JSON writer in core-data that writes to a sibling temp file and moves it into place; keep parent directory creation centralized. Convert direct enum parsing in CodexItemRecord.toDomain(), PostRecord.toDomain(), and QueryRecord.toDomain() to tolerant parsing. Split persistence helper code only where it reduces risk, such as JsonFileStore, PersistenceCodecs, or per-store record files.
Commands./gradlew :core-data:test, then ./gradlew test after the phase settles.
AcceptanceTests prove atomic writes leave either the old valid file or the new valid file, unknown post/source/query values do not crash repository initialization, and valid legacy JSON still loads.

Phase 3: Consolidate Media Requests and Downloads

Search, Viewer, and app-level downloads currently repeat request-header, filename, MIME, and DownloadManager setup. This phase creates one app-owned policy so future provider header changes do not drift across screens.

GoalSearch image loading, Viewer image loading, Viewer downloads, and app-level post downloads use the same source-header and filename policy.
Specific editsAdd MediaRequestFactory for Coil ImageRequest creation and PostDownloadService or DownloadRequestFactory for Android downloads under app/src/main/java/com/theoriacodex/app/media/. Reuse existing PostMedia.kt candidate selection and SourceMetadata.kt request headers. Replace buildImageRequest() in Search, buildViewerImageRequest() and enqueueViewerDownload() in Viewer, and enqueuePostDownload() in TheoriaApp.
Commands./gradlew :app:testDebugUnitTest, then ./gradlew lint.
AcceptanceTests prove headers are attached for protected sources, file names are stable and sanitized, missing media returns a typed failure instead of a silent false where practical, and Search/Viewer behavior remains visually unchanged.

Phase 4: Split TheoriaApp.kt into Workflow Coordinators

After lint, persistence, and media policy are guarded, move workflow ownership out of the app shell. The app shell should connect state to screens; it should not implement every workflow.

GoalTheoriaApp.kt becomes a readable composition surface with named collaborators for update, deep link, app graph, Codex transfer, likes sync, and viewer launch/session work.
Specific editsCreate TheoriaAppGraph or rememberTheoriaAppGraph for dependency construction; extract startup update prompt and install orchestration to an update-facing coordinator; extract external URI classification/opening to a deep-link coordinator; extract Codex import/export/share/download orchestration to a transfer service; extract likes-Codex sync; keep navigation calls at the app shell boundary.
Commands./gradlew :app:testDebugUnitTest :app:assembleDebug after each workflow extraction; full ./gradlew test before moving to the next workflow group if behavior was touched.
AcceptanceEach coordinator has focused tests for policy decisions. Manual smoke checks prove startup, update prompt eligibility, external post deep links, Codex import/export, likes sync, Search navigation, and Viewer launch still work.

Phase 5: Modernize Test Setup and Add UI Smoke Coverage

Unit coverage is broad, but the current test lane does not launch Compose UI, some temp directories are not cleaned up, and several coroutine tests still use runBlocking. This phase raises the floor.

GoalTest infrastructure gives reliable cleanup, consistent coroutine scheduling, and at least one device/emulator-backed Compose smoke path for top-level app wiring.
Specific editsAdd a temp-directory helper or JUnit rule for file-backed repository tests; migrate coroutine tests in core-domain and core-stubs from runBlocking to runTest; add app/src/androidTest with a minimal Compose smoke that can open the app shell and assert stable top-level UI/navigation labels using stubbed or deterministic state where possible.
Commands./gradlew :core-data:test :core-domain:test :core-stubs:test; ./gradlew :app:connectedDebugAndroidTest when an emulator or device is attached.
AcceptanceTemp files are cleaned up, coroutine tests use test dispatchers where practical, and the instrumentation lane is documented as device-required rather than silently part of every local JVM run.

Work Plan

  1. From the repository root, run git status --short, ./gradlew test, and ./gradlew lint. Paste concise output into the appendix. If lint output differs from this plan, update the Phase 1 task list before editing.
  2. Fix lint in the smallest possible commits. Use URLDecoder.decode(value, StandardCharsets.UTF_8.name()) for minSdk 26 compatibility, explicit MediaMetadataRetriever.release() in a finally block, and targeted Media3 @OptIn(UnstableApi::class) annotations near the APIs that require them.
  3. Add androidx-lifecycle-runtime-compose to gradle/libs.versions.toml and app/build.gradle.kts, then migrate LocalLifecycleOwner imports in TheoriaApp.kt, SearchScreen.kt, and ViewerScreen.kt.
  4. In core-data, introduce a single write path for JSON files. Prefer a small internal helper such as JsonFileStore or writeJsonAtomically() that handles parent directory creation, temp writes, and replacement. Do not change public repository interfaces unless a test proves the interface itself is the problem.
  5. Convert risky enum parsing into local tolerant decoders. For Codex posts and items, an unknown SourceKey should drop the invalid item/post while preserving the rest. For queries, unknown SortMode should fall back to the current default sort, and unknown source mode should fall back to unified mode unless a better local default is already established.
  6. Extract media request and download construction under app/src/main/java/com/theoriacodex/app/media/. Keep Android-only calls in the app module. Keep pure candidate selection in existing testable helpers where possible.
  7. Replace call sites one at a time: Search image requests, Viewer image requests, Viewer downloads, then app-level post downloads. Run focused app tests after each replacement.
  8. Split TheoriaApp.kt by workflow only after the previous phases are green. Start with dependency construction because it is easiest to test through object creation, then move update, deep link, Codex transfer, likes sync, and viewer launch/session workflows.
  9. Add or modernize tests alongside every move. Use coordinator tests for workflow policy, repository tests for persistence survival, and app instrumentation only for UI wiring that cannot be proven on the JVM.
  10. Finish by updating this plan, working_list.md, and AGENTS.md. Update README.md only if behavior visible to users changed.

  • Observation: Media3 UnstableApi is an AndroidX opt-in annotation, not a Kotlin opt-in marker. Evidence: Kotlin compile warned when @file:OptIn(UnstableApi::class) was used, and the warning disappeared after switching to @file:androidx.annotation.OptIn(UnstableApi::class).

Idempotence And Recovery

All planned work should be additive and safe to stage in small pieces. The Gradle commands are safe to rerun. The duplication scan is read-only except for temporary package download/cache behavior from npx. Do not run destructive git commands to recover; inspect git diff and revert only the files changed by the current phase if a local experiment needs to be abandoned.

For atomic write work, preserve the previous file until the new file is fully written. If a temp file remains from a failed run, the read path should ignore it. If replacement fails on a filesystem, report the write failure rather than deleting the original state. Tests should simulate at least the visible recovery guarantee: after a failed replacement, the repository can still read valid old state.

For TheoriaApp.kt extraction, move one workflow at a time and keep adapter functions at the old call site until tests prove the new collaborator owns the behavior. If a workflow extraction becomes noisy, stop after compiling, update this plan with the actual boundary, and continue with the next smallest seam.
