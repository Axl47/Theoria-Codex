ExecPlan: Cross-Source Tag Affinity

When this plan is complete, a Like on one source teaches For You about the same interest on the other tag-compatible sources. Liking a Pixiv post tagged 初音ミク (translated by Pixiv as "Hatsune Miku") makes hatsune_miku a candidate seed on Danbooru, Gelbooru, AIBooru and Rule34.xxx. Liking a Gelbooru post tagged hatsune_miku can likewise seed Pixiv with 初音ミク. Pixiv tag chips show the English translation beside the native tag, and still search the native tag.

Purpose / Big Picture

For You currently learns each source separately. ForYouCoordinator.buildSeedBySource groups Likes by source, so a source the user never liked anything on gets no personalized seed at all. The same person's taste is spread across sources, and the strongest bridge already exists: Pixiv sends an English translated_name for many tags, and the booru sources use English underscore tags. Once that bridge is used, Likes anywhere improve recommendations everywhere it can map.

To see it working, like several Pixiv posts that share a translated tag, with no Danbooru Likes. Open For You with Danbooru enabled: Danbooru gets a seed built from the shared English tag instead of only trending tags.

Context And Orientation

Terms. A source is a provider adapter (SourceKey). Taxonomy is the typed tag list on a Post (PostTaxonomyTerm: value, facet, namespace, count); tag chips are built from it. Training tags are the tags stored with a Like (LikedPost.tags), computed by trainingTagsFor. For Pixiv these are deliberately native tags only, so a native tag and its translation never count twice. A seed is the 1–2 tags For You searches per source. A concept key (new) is a source-neutral spelling used only to compare tags across sources.

Research: Pixiv vs. Booru Tag Data

AspectPixivDanbooru / AIBooruGelbooru / Rule34.xxx
Who tagsThe artist (and sometimes viewers). Free-form, mostly Japanese, spaces allowed.A curated community with aliases and implications.Community; less curated.
SpellingMixed case and full-width or half-width forms. Native qualifiers use parentheses, e.g. ラム(リゼロ).Lowercase, ASCII, underscores. Qualifiers like saber_(fate).Same as Danbooru, but the API returns HTML entities (&#039;, &amp;).
CategoriesNone in the API.Typed strings (tag_string_general/character/copyright/artist/meta). The adapter reads only the untyped tag_string.Only via the tag API; posts are untyped.
Translationtranslated_name in the Accept-Language language, when Pixiv has one.Wiki other_names hold Japanese names. Danbooru's own Pixiv import uses them.None.
MarkersNNNusers入り popularity, R-18/R-18G rating, オリジナル.Meta tags such as highres, absurdres, commentary_request.Similar metadata tags.

How Danbooru maps Pixiv tags (from danbooru/danbooru source): apply NFKC to the Pixiv tag, collapse whitespace to _ and lowercase it, strip \d+users入り, then look it up in wiki other_names. Failing that, it falls back to the normalized name plus alias resolution. This plan copies the NFKC + whitespace + lowercase part for concept keys.

Findings that change code here: (1) translations are lost on posts, and the translation language follows the device locale; (2) the Pixiv search token rewriting is lossy for native tags; (3) Gelbooru/Rule34 tags keep HTML entities, which breaks chips, search, Codex automatic tags and cross-source matching for tags like jojo's_bizarre_adventure; (4) typed English plus Enter on Pixiv doesn't use the translated suggestion. Recorded but not changed: Danbooru meta tags and Pixiv R-18 markers enter training. Changing that alters existing For You behavior and deserves its own decision. animated, itself a Danbooru meta tag, matters to this app.

Phases

Phase 1: Keep Pixiv translations paired

GoalEach Pixiv taxonomy term is a native tag with an optional English translation. One chip shows "Hatsune Miku · 初音ミク" and searches 初音ミク. The suggestion store learns the pairs from every Pixiv result page.
Edits
  1. PostTaxonomyTerm.translation: String? = null (display/learning only; never searched).
  2. New core-domain/.../tags/PixivTags.kt:
    • pixivSearchToken(raw): the single shared Pixiv token normalizer. It strips -, and for ASCII-only (booru-style) tokens also replaces _ with a space and strips trailing (…) qualifiers. Native tags pass through untouched.
    • withRecoveredPixivTranslations(post): legacy upgrade for payloads written before this change. The adapter always appended each translation right after its native tag in canonicalTags, so the pairs are recovered from that order.
  3. PixivSourceAdapter: build taxonomy from native tags with translations. Keep canonicalTags unchanged (native + translation) so Codex automatic tags, clipboard and Codex search options keep matching English. Always request Accept-Language: en-US. Use pixivSearchToken.
  4. Storage: PostTaxonomyTermStorageRecord.translation, with the legacy recovery applied on decode. Codex share taxonomy gets the same field and recovery.
  5. FacetedTagSuggestion.alternateText; CachedSuggestion.fromFacetedSuggestion keeps it; rememberSeenTags passes term.translation.
  6. Chip label shows the translation first and the native tag second.
  7. resolveCommittedInput also matches a suggestion's alternateText.
  8. SearchCoordinator.resolvePixivCompatibilityTags calls pixivSearchToken.
AcceptanceAdapter, storage, share-codec, store, reducer and chip tests pass. A legacy Pixiv payload decodes into paired terms.

Phase 2: Decode HTML-escaped booru tags

GoalGelbooru and Rule34.xxx tags arrive as real tag names (jojo's_bizarre_adventure). Already stored escaped tags still match.
Edits
  • decodeHtmlEntities(value) in core-domain/.../tags/SourceTagNormalization.kt (named and numeric entities; a no-op without &).
  • Apply it in Gelbooru and Rule34.xxx post and tag-suggestion parsing.
  • sourceTagKey/sourceTagsMatch and RecommendationTagNormalization decode for underscore sources, so legacy escaped Likes and automatic tags compare equal.
AcceptanceAdapter and normalization tests pass. Decoding is idempotent for ordinary tags.

Phase 3: Cross-source affinity in For You

GoalTag-compatible sources (Pixiv, Danbooru, AIBooru, Gelbooru, Rule34.xxx) train on each other's Likes. Other sources are unchanged.
EditsNew core-domain/.../recommendation/CrossSourceTags.kt:
  • crossSourceTagKey(tag): decode entities, NFKC, lowercase, _/whitespace → single space.
  • PixivTagDictionary: built from Pixiv suggestions with alternateText in the store. Maps native → concept key, and concept key → the first native tag in store order (the store keeps the most recently seen entries first).
  • CrossSourceTags.trainingDocuments(target, likes, dictionary): the target's native documents first, then other compatible sources' documents translated into the target's vocabulary. Booru targets use the key.replace(' ', '_') spelling; the Pixiv target uses a dictionary lookup. Tags that can't be mapped are dropped, and so are empty documents. Most recent first, capped at max(nativeCount, 24) foreign documents, so native Likes stay at least half of the evidence once there are 24 or more.
ForYouCoordinator.buildSeedBySource and ForYouSectionsLoader.generatedSeeds both use it. Sections already drop tags whose provider count is 0, which filters mapped tags that don't exist on the target.
AcceptanceCoordinator test: Pixiv-only Likes with Danbooru enabled yield a Danbooru seed with the mapped tag. Booru Likes yield a Pixiv seed only through the dictionary. Native-only behavior is unchanged when no foreign documents map.

Surprises And Discoveries

  • Pixiv Likes were already de-duplicated for training (recommendationTaxonomyFor prefers rawTags for Pixiv). Evidence: app-logic/.../TrainingTagsTest.kt.
  • Untyped booru taxonomy means characters and series do train For You on Danbooru and Gelbooru. They are the strongest cross-source bridge.
  • :app:detekt already fails on main with a LongMethod finding in app/src/test/.../tags/PostTagActionLazyLayoutTest.kt, a file this plan does not touch. Left as is.
  • Danbooru was down for maintenance during research, so its behavior was confirmed from its source code instead (WikiPage.normalize_other_name, TagNormalizer, Source::Extractor#translate_tag).

Decision Log

  • Decision: build the translation dictionary from the existing tag suggestion store, not from liked post payloads or a new Likes column. Rationale: no Room migration and no payload decoding per For You run, and it grows as the user browses Pixiv. Trade-off: a liked Pixiv tag maps only once its pair has been seen. Date/Author: 2026-11-06 / Claude.
  • Decision: request Pixiv translations in English regardless of device locale. Rationale: the booru vocabulary is English, and chips show one consistent language. Date/Author: 2026-11-06 / Claude.
  • Decision: keep Pixiv canonicalTags unchanged. Rationale: Codex automatic tags, clipboard and Codex search options already match English names there. Date/Author: 2026-11-06 / Claude.
  • Decision: cap foreign documents at max(native, 24). Rationale: they bridge cold starts but never outweigh what the user liked on that source. Date/Author: 2026-11-06 / Claude.
  • Decision: exact concept-key matching only; no qualifier stripping, alias tables or the HuggingFace dataset. Rationale: smallest design that covers characters, series and common general tags. Date/Author: 2026-11-06 / Claude.

Outcomes And Retrospective

All three phases are implemented and covered by host tests. A Pixiv Like now yields a seed on Gelbooru (hatsune_miku from 初音ミク) once the pair is in the suggestion store, and booru Likes reach Pixiv through the same dictionary. Not yet proven: live Pixiv English translations, Gelbooru's escaped-tag behavior, and the For You result on a device. Future agents: the dictionary only grows as Pixiv results, autocomplete or trending are seen, so existing Pixiv Likes map gradually rather than immediately.

Follow-ups (not in scope)

  • Unified search could send booru tags to Pixiv as dictionary-mapped native tags instead of stripped English.
  • Decide whether Danbooru meta tags and Pixiv rating markers should be excluded from training.

Idempotence And Recovery

No destructive operations or schema migrations. The new JSON fields are optional: old payloads decode as before plus the recovered pairs, and older app versions ignore the field. Each phase is its own commit; revert one with git revert <sha>. Gradle test commands are safe to rerun.
