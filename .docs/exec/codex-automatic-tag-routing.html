Purpose / Big Picture

From a Codex tile, the user opens the existing shared overflow sheet. A Tags section shows each source and its represented canonical tags with a post count. Pressing + moves that source/tag pair into an Automatic section. Thereafter, changing a matching post from unliked to liked saves it into that Codex as part of the same durable operation that updates Likes.

A Codex with several Automatic rules uses OR behavior: matching any rule adds the post once. Unliking or removing a rule never deletes an independently owned Codex membership.

Context And Orientation

An automatic tag is a source plus a canonical tag value. Source awareness matters because providers normalize and interpret tags differently. A profile Codex is a collection whose existing identifier convention associates it with one recommendation profile.

Phases

Phase 1: Durable Rules And Matching Policy

Add a normalized, duplicate-free source/tag list to each Codex and one idempotent repository toggle. Bump Room from schema 3 to 4 with a foreign-keyed child table that defaults existing Codices to no rules and cascades on delete; preserve file-backed compatibility through defaulted fields.

Phase 2: Atomic Like Routing

The service snapshots only Codices belonging to the current profile and passes those IDs into the transaction. On a like transition, Room inserts the system Likes membership and each matching automatic membership in one transaction. On unlike, only system Likes membership is removed.

Phase 3: Overflow Presentation

Reuse current source-scoped tag counts. Show Automatic first with remove actions, then represented tags grouped by source with counts and + actions. Selected tags remain visible in Automatic and are omitted from the available list to avoid duplicate controls.

Phase 4: Bounded Validation

Run one focused host batch. Device installation was outside the implementation task; the user later completed the isolated-Debug acceptance check on 2026-08-12.

Decision Log

  • Decision: store source/tag pairs, not bare strings. Rationale: existing normalization is provider-specific and should not create cross-source surprises. Date/Author: 2026-08-10 / Codex.
  • Decision: persist rules as Room child rows. Rationale: collection deletion owns rule deletion and matching remains queryable in the like transaction. Date/Author: 2026-08-10 / Codex.
  • Decision: rules use OR matching and affect only transitions to liked. Rationale: this is predictable, idempotent, and preserves user-owned collection history. Date/Author: 2026-08-10 / Codex.
  • Decision: pass profile-eligible Codex IDs into the storage transaction. Rationale: profile ownership remains app policy while Room retains atomic writes. Date/Author: 2026-08-10 / Codex.

All test and compile commands are safe to rerun. The Room migration is additive and defaults existing Codices to no rules. Rule toggles and membership inserts are idempotent. No destructive command, connected task, install, database reset, or production-package action is authorized.
